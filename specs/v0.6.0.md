# Taskrail v0.6.0

## Summary

Taskrail `v0.6.0` adds **durable task identity and reviewable archival**.

Through `v0.5.0`, every task remains a direct Markdown child of
`planning/tasks/`. Completed history therefore grows beside runnable work, while
Taskrail's numeric allocation, dependency graph, coverage, reports, prompts, and
loop selection all assume that one physical directory is the complete ledger.
Moving a file by hand makes older binaries silently forget its ID and can cause
ID reuse, missing dependencies, broken path references, and false coverage.

This version separates identity from storage. Live tasks remain under
`<planning-dir>/tasks/`; explicitly archived tasks move to
`<planning-dir>/archive/tasks/`; both roots form one logical ledger. Generated
task references use arbitrary-width decimal keys, while repositories may opt
individual tasks into portable opaque IDs for external-system interoperability.
A shared resolver keeps short references in code and documentation valid across
re-slugging and archival.

Archival is explicit, status-preserving, Git-aware, and reversible. Completed
tasks need a passing verification recorded after completion. Cancelled tasks need
durable cancellation provenance and no open dependents. Exact references to the
old physical path block the move and are listed for deliberate replacement with
the stable task reference. Archived history is immutable until restored.

This version also adds a configurable human-owned `IDEAS.md` sidecar for rough
headings, lists, and prose that are not yet tracked commitments. Reviewed import
routes that source to a spec by default and to tasks only explicitly; Taskrail
never treats free-form entries as executable work or rewrites them mechanically.

Taskrail still does not delete history, synchronize an external issue tracker,
rewrite arbitrary source references, or archive automatically inside the
autonomous loop.

## Goals

- Make a task's stable reference independent of its slug and physical storage.
- Remove machine-integer and three-digit assumptions from generated task IDs.
- Support portable caller-owned opaque IDs without changing generated IDs as the default.
- Resolve live and archived tasks through one deterministic task-reference index.
- Add durable, inspectable cancellation provenance for intentionally abandoned work.
- Move completed and cancelled history out of the live task directory without losing graph, coverage, reporting, or allocation semantics.
- Refuse archival or restoration when tracked prose or code would retain a stale physical path.
- Make archive and restore previewable, transactional, reversible, and safe on native Windows, macOS, and Linux.
- Keep layout upgrades conservative: change the marker and interpretation, never move tasks automatically.
- Preserve v0.5 loop safety by treating storage maintenance as a separate human-invoked workflow.
- Give rough product ideas one discoverable, configurable human-owned source that
  normally flows through reviewed spec adoption before task decomposition.

## Potential Features

### Generated Task Keys And Stable References

Taskrail distinguishes a task's persisted full ID from its stable reference.

Generated full-ID grammar:

```text
T-<digits>
T-<digits>-<slug>
```

Requirements:

- `<digits>` is a positive arbitrary-precision decimal. Readers and writers impose no machine-integer or fixed-three-digit ceiling. New IDs are formatted to a minimum of three digits (`T-001` through `T-999`) and then grow naturally, subject only to the portable filename-component limit below.
- Numeric comparison, collision detection, sorting, and max-plus-one allocation operate on normalized decimal strings, never `int`, floating point, or a JSON number. Implementations may use decimal-string arithmetic or an arbitrary-precision standard-library integer.
- Leading-zero spellings have one numeric identity. `T-1`, `T-001`, and `T-0001-same-key` cannot coexist. Existing spelling is not silently rewritten; generated output uses the minimum-three-digit canonical form.
- A generated task's stable `task_ref` is `T-` plus its normalized decimal padded to at least three digits. Re-slugging and physical archival never change it.
- The optional slug retains the `v0.4.0` lowercase portable-slug contract. The full `id` and filename stem remain equal.
- The complete ID is at most 252 ASCII bytes, keeping `<id>.md` within the common 255-byte filename-component limit. A bare generated key therefore has at most 250 digits. If max-plus-one would exceed that limit, allocation fails before any task or import write and directs the operator to a portable opaque ID; it never wraps, truncates, or reuses a key.
- A title-derived slug is capped again to the bytes remaining after the allocated key and delimiter; if no non-empty slug fits, creation writes the bare key with the existing visible fallback warning. An explicit slug that does not fit is rejected rather than truncated.
- Generated numeric ordering is by arbitrary-precision value, so `T-999` precedes `T-1000`. Numeric-key uniqueness makes a slug tie-break unnecessary.
- Allocation scans the complete live-plus-archive ledger. Archiving never releases a number for reuse.

Stable references are the preferred representation when a durable Taskrail
reference is otherwise authorized in code comments, documentation, commit
subjects, task-body provenance, new dependency entries, and state pointers. This
preference does not require a reference in local Git-visible output and inherits
v0.5's trusted-provenance boundary: repository-visible policy governs generic Git
conventions, but exposing a local Taskrail identity/path in commit metadata needs
caller-owned instruction outside managed planning; auxiliary refs remain
forbidden by inherited postflight. Physical task
paths and generated full IDs with slugs are inspectable locations and labels, not
durable references.

### Portable Opaque Task IDs

Repositories may create a task with a caller-owned opaque ID for interoperability
with external or unusual planning systems.

An opaque ID matches the exact anchored regular expression
`^[A-Za-z][A-Za-z0-9]*(?:-[A-Za-z0-9]+)*$`, does not match the generated
`T-<digits>[-slug]` family, and is at most 252 ASCII bytes. Examples include
`OPS-42`, `JIRA-ABC-123`, and `T-jira-123`.

Requirements:

- Opaque IDs are exact, case-sensitive, and preserved byte-for-byte. Taskrail does not lowercase, transliterate, slugify, trim, truncate, or otherwise normalize one.
- Validation additionally rejects ASCII case-folded filename collisions across the complete ledger and every sibling directory entry, preventing a repository that cannot clone on case-insensitive filesystems. Opaque input whose ASCII fold matches the generated family (for example `t-123`) is reserved and rejected so it cannot block allocator max-plus-one.
- Opaque IDs whose case-folded basename is `CON`, `PRN`, `AUX`, `NUL`, `COM1` through `COM9`, or `LPT1` through `LPT9` are rejected even with the `.md` extension.
- Separators, whitespace, dots, underscores, controls, and non-ASCII text are rejected. The conservative grammar is a portable Taskrail representation, not support for every external tracker syntax.
- An opaque task's stable `task_ref` equals its exact full ID. Opaque IDs have no numeric allocation meaning and are ignored when calculating the next generated number.
- `taskrail task new --id <opaque-id>` opts into this family. `--id` rejects a generated-form value, is mutually exclusive with `--slug`, and may be used with `--title`; the title never derives or changes the opaque ID.
- Opaque IDs are immutable. `task rename` applies only to the slug of a live generated task and rejects opaque or archived targets before writing. Converting or re-keying either family is outside normal layout-3 operation; the collision-only pre-upgrade identity map is the sole migration exception.
- ImportDraft schema versions 1 and 2 retain their exact v0.5 meanings. Schema version 3 extends reviewed transactional v2 with a presence-aware optional string `TaskDraft.id`; only an absent key allocates a generated ID, while present `null`, `""`, or whitespace fails and any other value requires a valid opaque ID. In-draft dependencies remain local `key` values. Older binaries reject schema 3 before interpreting tasks, and v1/v2 decoders continue rejecting `id` as unknown rather than silently allocating another identity.
- Import preflight validates every requested opaque ID, exact and case-fold collision, generated allocation, external dependency, and archive collision for the entire draft before its first write.

Persisted-file classification is separate from validating new `--id` input and
runs in this exact order:

1. An exact positive `T-<digits>[-<portable-lowercase-slug>]` is generated.
2. Any other ASCII-case-fold match of `^t-([0-9]+)(?:-|$)` is numeric-looking legacy, including zero, noncanonical case, and malformed-suffix spellings. Leading-zero spellings that otherwise satisfy the exact generated grammar remain generated and share their normalized key.
3. A value matching the opaque grammar and not the reserved generated-looking fold is opaque.
4. Every other existing value is legacy.

The classifier never reinterprets an existing full ID based on command flags.
New creation admits only generated output or valid opaque input; legacy classes
exist solely for migration compatibility.

### Shared Task Reference Resolver And Inspection

Every task-targeting command and machine relationship uses one resolver over the
complete ledger.

Resolution rules:

- A bare positive `T-<digits>` selector is always a generated stable reference before exact lookup: normalize its decimal and inspect the complete claimant set. Resolve exactly one claimant or refuse an invalid duplicate-key ledger and list all claimants, even when one full ID exactly equals the selector. This prevents exact `T-001` from bypassing ambiguity with `T-1-old`.
- For every other selector, exact full-ID lookup runs first, preserving exceptional legacy addressability such as `T-0`; an exact reserved legacy digest reference then resolves through the index. Any remaining input requires an exact, case-sensitive full ID.
- Opaque IDs therefore resolve exactly; generated slug prefixes, titles, stale pre-rename full IDs, and fuzzy matches do not.
- An invalid duplicate-key ledger makes short lookup ambiguous. Refuse and list every matching full ID, storage class, and repository-relative path rather than choosing one.
- Resolver output carries `task_ref`, canonical full `task_id`, lifecycle status, storage (`live` or `archived`), and current repository-relative path.
- Existing machine-managed full-ID references remain accepted. New writes use stable references. `task rename` rewrites legacy full-ID machine references in live task files and state while stable references need no edit. Task-local loop fields contain no task reference and need no identity rewrite.
- A live generated task cannot be renamed when an archived task contains a legacy full-ID dependency on it, because satisfying that rename would mutate archived history. Refuse and list the archived inbound references; restore and normalize them deliberately first.
- Resolve dependencies before validating them. A task cannot depend on its own stable/full alias, and two spellings resolving to the same task are one duplicate semantic edge and are rejected.
- Every machine relationship applies the same semantic uniqueness after resolution. Dependencies, blocker/current pointers, and follow-up provenance cannot contain stable/full aliases for one task as distinct edges; conflicts list both spellings and refuse.
- One global order applies wherever Taskrail promises deterministic task order: positive generated-key claimants (canonical generated tasks or numeric-looking legacy tasks) first by arbitrary-precision numeric key, opaque tasks second by unsigned ASCII full-ID bytes, and nonnumeric or zero-valued grandfathered legacy IDs last by unsigned UTF-8 full-ID bytes. Numeric-key uniqueness eliminates ties; generated or legacy suffixes never influence numeric order.

Identity representation across surfaces is exact:

- Task frontmatter `id`, filename, and H1 keep the canonical full ID byte-for-byte.
- New dependencies, state `current_task`, blocker identity, and follow-up provenance write `task_ref`; readers retain existing full-ID compatibility and normalize only when that field is otherwise rewritten. Task-local loop policy contains no duplicated stable task reference.
- Machine JSON uses strings universally: `task_id` is full ID, `task_ref` is stable reference, and both are emitted wherever either could differ. No ID or decimal generation is a JSON number.
- Every ID/reference scalar written to YAML is explicitly string-tagged or quoted so values such as `NULL`, `TRUE`, `ON`, `001`, and date-like IDs round-trip as strings. Human text control-escapes full IDs and references.
- Verification artifact subject directories use filesystem-safe `task_ref`;
  task-targeting prompt contract `v2` exposes ID/ref/storage and the resolver-
  provided path. Existing artifact paths remain historical and are never rewritten.
- DOT and Mermaid use an injective encoded node key or deterministic ordinal independent of display labels, so punctuation normalization can never merge mixed-family tasks.

Extend the inherited read-only task inspection command to use the shared
live-plus-archive resolver:

```text
taskrail task show <task-ref> [--path] [--json] [--raw]
```

Default text emits exact task Markdown to non-terminal stdout. To a terminal it
refuses bytes containing controls other than tab/LF unless `--raw` explicitly
accepts exact uninterpreted output; `--raw` is valid only for text/path mode.
`--path` follows the same terminal rule and otherwise emits only the task's exact
canonical current logical path. `--json` safely escapes controls and replaces the
v0.5 result with exact fields `task_ref`, `task_id`, `task_path`, `storage`
(`live|archived`), `content`, and `sha256`; it is mutually exclusive with
`--path`/`--raw`.
Prompts and skills read task/spec bytes through `task show` and `spec show`; they
never construct a live, archive, committed, or local physical path.

All existing explicit task selectors adopt the shared resolver. Lifecycle and
planning writers still enforce their status and storage rules after resolution,
so an archived task produces an actionable "archived; restore first" error rather
than "not found."

### Cancellation Transition And Provenance

Add a first-class lifecycle transition:

```text
taskrail cancel <task-ref> --reason <text> [--dry-run] [--json]
```

Cancelled frontmatter records exact fields:

```yaml
cancelled_at: "2026-08-04T10:00:00Z"
cancellation_reason: "superseded by the supported workflow"
```

Requirements:

- `cancel` accepts a live `todo`, `in_progress`, or `blocked` task. Its reason is trimmed UTF-8 of 1 through 512 bytes, contains no newline or control character, passes the existing portable-note guard, and is escaped in terminal output. The command sets status `cancelled`, records canonical RFC3339-UTC `cancelled_at` and the reason, clears `completion_id`, `completion_generation`, `last_verification_id`, `last_verification_previous_id`, `last_verification_result`, `last_verified_at`, `last_verified_completion_id`, and `verified_completion_generation`, then appends a timestamped implementation note.
- Cancellation preserves the task's paired `loop_policy` and `loop_reason` fields exactly, including their joint absence. A cancelled task is terminal and therefore never a loop candidate regardless of those preserved bytes.
- Cancelling the current task clears `current_task`; cancelling a blocked task removes only its blocker entry. Reconcile idle pointers only when no other task is current; otherwise preserve that active task's summary and next action. Then re-validate.
- Cancellation refuses while any open (`todo`, `in_progress`, or `blocked`) task directly depends on the target. The error lists each dependent so the operator can complete, cancel, or redesign it. A cancelled dependency never satisfies eligibility.
- A legacy cancelled task without provenance may run the same command once to adopt a reason and timestamp without changing its status. A cancelled task that already carries provenance is unchanged and rejected as already cancelled.
- Archived tasks cannot be cancelled. This version adds no uncancel, reopen, or uncomplete transition; restore changes storage only.
- "No open task depends on a cancelled task" is a continuous validation invariant across both roots for newly valid state. Task creation, import, follow-up creation, and every dependency writer refuse such an edge; the explicit valid-with-warning layout-3 migration debt exception remains only until deliberate dependency removal or dependent cancellation.
- Validation requires cancellation fields together when status is `cancelled`, except for the valid-but-warning legacy state defined by layout migration. Persisted timestamps must be canonical RFC3339-UTC and reasons must satisfy the same trimmed UTF-8/length/control/portable-note grammar as the command; non-empty alone is insufficient. Other statuses must not retain cancellation fields.
- Taskrail serializes cancellation reasons and every user-supplied YAML text scalar with explicit string quoting/tagging, re-parses candidate bytes, and requires exact value equality before publication. Colons, hashes, quotes, brackets, leading YAML indicators, and scalar-looking words round-trip byte-for-byte after the command's documented trim; serializer truncation or reinterpretation is a write failure.
- Cancellation constructs and validates the candidate task and state first, writes atomically replaced files under the repository mutation lock, and rolls back every ordinary task/state/post-validation failure. Rollback replaces a path only while current bytes/mode still equal this transaction's published candidate; otherwise it preserves the external edit, retains the recovery lock record, and reports partial state. Partial or rollback failure reports both original/candidate/current snapshots and safe `validate`/`repair` inspection; failure-injection tests cover each boundary.
- `--dry-run` performs the same resolution, dependent, transition, candidate, and validation checks without writing. It reports the target, prior/resulting status, exact fields that would clear, pointer/blocker reconciliation, provenance that would be added, and sorted dependent blockers. Apply and dry-run classify refusals identically.
- Text and JSON results report task reference, full ID, prior status, cancelled status, reason, timestamp, applied state, cleared fields, pointer/blocker reconciliation, and sorted dependent blockers. A refusal exits non-zero with stable `error.code` and one valid JSON error document; a successful preview or transition exits zero.

V0.6 inherits the v0.5 dependency writer and upgrades both operands to the shared
stable-reference resolver:

```text
taskrail task dependency remove <task-ref> <dependency-ref> [--dry-run] [--json]
taskrail task dependency add <task-ref> <dependency-ref> [--dry-run] [--json]
```

Remove deletes exactly one resolved dependency edge from a live open task and
preserves the order of all others. Add appends one stable reference after
rejecting duplicates, self-dependency, cycles, missing or cancelled dependencies,
archived targets, and unstable aliases. Archived completed tasks may be
dependencies but never mutation targets. Existing exact-ID edges remain readable;
remove resolves one semantic edge rather than requiring its stored spelling. Both
preview the complete candidate, reproject state, preserve task-local loop fields,
and re-validate under the inherited mutation transaction. Replacement and bulk
editing remain outside this version.

### Archive Storage And Unified Ledger

Layout 3 recognizes two flat task roots derived from the configured planning
directory:

```text
<planning-dir>/tasks/          # live
<planning-dir>/archive/tasks/  # archived
```

Requirements:

- Direct regular lower-case `*.md` children of both roots form one authoritative task ledger. Storage class is derived from path and is not duplicated in frontmatter; task-like case variants such as `.MD` are rejected rather than silently omitted. Every repository-relative component contributed by planning configuration or the `tasks/archive` suffixes is valid UTF-8, NFC, non-empty, neither dot component, contains no controls or Windows-forbidden `<>:"/\|?*`, has no trailing space/dot or reserved device stem, and has no NFC-plus-Unicode-case-fold sibling alias. Migration and every load fail closed rather than ignore an alternate/colliding tree.
- In committed mode, every command enumerates tracked entries beneath both roots and refuses when a task entry is sparse, skip-worktree, assume-unchanged, missing from the worktree, or otherwise unavailable to the filesystem ledger. Allocation, destination collision, and candidate validation include index-only names before refusing. In local mode, every command instead enumerates the complete effectively ignored managed-overlay roots and refuses external, staged, tracked, aliased, or unavailable task entries. Taskrail never reports against a partial ledger.
- The archive root is optional while empty, is created on the first applied archive, and needs no `.gitkeep`. Deeper directories, symlinked entries, and non-regular Markdown entries are rejected.
- Full IDs, generated numeric identities, stable references, and case-folded filenames are unique across both roots. The same task in both locations is invalid, never a harmless duplicate.
- An archived task has status `completed` or `cancelled` and satisfies that status's archive eligibility. The sole migration exception is adopted pre-layout-3 terminal content whose fields form a valid v0.5 generation/cancellation-debt shape: it remains valid-with-warning and immutable in archive, is never newly archive-eligible, and must be restored before verification/provenance remediation. Open content or any other provenance-incomplete shape is invalid.
- Archived task content is immutable to Taskrail writers. Start, complete, block, unblock, cancel, verify, rename, repoint, task authoring, and import updates reject it. Restore it before mutation. The combined loader is read-only; every writer persists an explicit changed-live-task set and never reserializes unchanged or archived tasks. Archived bytes, mode, mtime, and path remain unchanged during unrelated writers.
- `task new`, imported tasks, and every follow-up are always created live. Follow-ups created by verification or import omit both `loop_policy` and `loop_reason`, encoding inherited implicit hold in their own task bytes; no separate policy is published. A live follow-up may cite an archived completed parent through `--follow-up` without modifying it. Cancelled parents, live or archived, cannot receive open dependency or follow-up edges.
- Dependencies resolve over both roots. An archived completed dependency satisfies eligibility; an archived cancelled dependency remains unresolved.
- Coverage, gap analysis, lifecycle counts, stats, graph edges, ID allocation, verification history, import preflight, and spec linkage consume the combined ledger. Archival alone changes none of their semantic results.
- Status and stats add exact JSON `task_storage: {"live": <n>, "archived": <n>}` and equivalent text. Status retains inherited `storage` mode/root/artifacts context unchanged. Both task-storage values count every ledger task; their sum is stats `total_tasks`. Existing status lifecycle semantics remain (`done` includes completed while cancelled is omitted); stats retains the full status distribution. `STATE.md` gains no storage database or path list, so a pure move does not rewrite it.
- Graph output retains archived nodes and labels their storage. Repair reprojects aggregate state from both roots but never moves a task or chooses between duplicate locations.
- The root loop reads task-local `loop_policy` and `loop_reason` through the combined task ledger. Terminal tasks, whether live or archived, and all archived tasks are never loop candidates; restore changes storage only and does not reactivate lifecycle state or loop eligibility.

Add a strictly read-only inventory command:

```text
taskrail task list [--active-spec] [--storage live|archived] [--status <status>] [--archive-eligible] [--json]
```

It reports stable reference, canonical ID, title, status, storage, path, archive
eligibility, and sorted blockers in global task order. Filters compose;
`--archive-eligible` includes both eligible terminal classes and excludes blocked
candidates while explaining them in the unfiltered view. It never moves work or
turns aggregate status into a bulk archive surface.

`--active-spec` intersects the other predicates using the shared normalized
`spec_ref`-path matcher and includes archived history linked to the active spec.
Default inventory remains complete-ledger. JSON always echoes a non-null `filters`
object with resolved active path or empty string, status/storage values or empty
strings, and `archive_eligible` boolean; `tasks` is an empty array, never null,
when no task matches.

### Archive Eligibility And Verification Metadata

Task frontmatter adds optional task-level verification fields:

```yaml
completion_id: "8b6ec42d90e54a42a6f11c3d2f4d8c90"
completion_generation: "3"
last_verification_id: "b21074ba24284922a3772431816c97f4"
last_verification_previous_id: "46bb70866413442481c46c69a7c51dc2"
last_verification_result: pass
last_verified_at: "2026-08-04T10:00:00Z"
last_verified_completion_id: "8b6ec42d90e54a42a6f11c3d2f4d8c90"
verified_completion_generation: "3"
```

Requirements:

- `complete` retains v0.5's random `completion_id`, treats absent `completion_generation` as zero, increments arbitrary-width decimal generation, clears earlier verification fields, then sets completed. A transition away clears completion and verification binding as applicable. Thus first completion of an upgraded open task writes generation `"1"`.
- `verify` retains v0.5's complete predecessor-linked verification tuple and additionally records `verified_completion_generation`. Every new verification records `last_verification_previous_id` when prior task-level verification exists and requires its persisted omission for the first verification, following the inherited direct-chain rules. A passing completed verification carries matching non-empty completion ID and positive generation bindings. Non-completed or failing verification carries verification ID/result/time plus verified generation `"0"` and no `last_verified_completion_id`; failure preserves but never initializes missing completion metadata. For a migrated v0.5 completed task, the first passing verification preserves an existing valid `completion_id` and initializes only absent completion generation to `"1"`; it generates a completion ID only when absent, then binds both atomically. Outside the explicit migration-debt shape, a present `completion_generation` without `completion_id`, zero/invalid completed generation, a missing verification ID/result/time/verified-generation member, an absent predecessor when prior task evidence exists, a predecessor without matching evidence, or a positive verified generation without matching completion-ID binding is invalid. Any ordinary failure rolls adoption back with the verification write.
- A completed task is archive-eligible only when result is `pass`, non-empty verification/completion IDs agree under v0.5, and verified generation equals current completion generation. Existing completed tasks without these fields must receive a new passing verification after layout upgrade; migration never infers evidence from old notes or ignored artifacts.
- A cancelled task is archive-eligible only with validation-clean canonical cancellation reason/timestamp and no open dependent. Passing verification is neither required nor treated as a substitute for cancellation provenance.
- A failing verification never qualifies completed work for archive. The existing v0.5 advisory for passing verification before completion remains, and a later completion clears that premature pass.
- Verification writes required artifacts first, then transactionally includes any follow-up task, state projection/summary, and target task. A verification follow-up carries implicit hold by omitting both task-local loop fields; there is no separate policy publication. Target metadata is the final eligibility commit marker. Ordinary failure before it cannot qualify archive and rolls back every tracked write; a retry cannot duplicate a partial follow-up. The mutation-lock metadata records transaction ID, phase, and bounded original/candidate digests before publication and is removed only after committed post-validation or complete rollback. Rollback or reporting failure that could leave eligibility metadata retains that recovery record; `validate`, verify retry, and archive refuse the affected state until explicit inspection/recovery proves one coherent outcome and clears it. The structured partial result names every durable output. Validation and failure-injection tests cover each artifact/task/state boundary, rollback race, and summary/marker disagreement.
- Frontmatter remains authoritative persisted input that must decode and validate strictly; canonical timestamps and generation binding make CLI ordering mechanically inspectable without trusting wall-clock comparison. Archive eligibility is recomputed before every preview and apply; no stale preview authorizes a later move.

### Archive And Restore Commands

Add explicit storage commands:

```text
taskrail task archive <task-ref> [--dry-run] [--json]
taskrail task restore <task-ref> [--dry-run] [--json]
```

Requirements:

- Commands apply by default, matching `task rename`; `--dry-run` runs every read-only preflight and reports the exact source, destination, storage transition, eligibility evidence, path-reference blockers, and candidate validity without creating a directory or touching Git.
- Archive resolves one live task, checks status-specific eligibility, refuses an existing destination, and moves it to the archive root without changing task bytes, including frontmatter `loop_policy`/`loop_reason`, status, ID, timestamp, dependencies, or `STATE.md`.
- Restore resolves one archived task and moves the same task bytes, including `loop_policy`/`loop_reason`, to the live root without reopening, unverifying, renaming, reactivating loop eligibility, or otherwise mutating it. An already-live restore and already-archived archive fail clearly.
- Restore may start from structurally readable archived content in a ledger that is invalid only because of this task's current archive storage or a former-live-path reference that the exact inverse candidate demonstrably removes. It reports the tolerated source violations, permits no content/status/identity/dependency violation, and must fully validate the candidate live ledger before success. This narrow recovery path prevents manual-move drift from disabling its own repair command.
- Archived history must be restored before verification, cancellation provenance repair, rename, or any body/frontmatter write. A restored terminal task remains terminal until an independently supported transition changes it.
- Human and successful/dry-run JSON output includes `task_ref`, `task_id`, `from`, `to`, prior/resulting storage, status, applied, eligibility summary, sorted path-reference blockers, `scan_complete`, and sorted `unsupported_paths`. Refusal JSON carries the same available transition/eligibility/scan facts inside exact `error.details`. "Clean" is used only when scan is complete; unsupported tracked scope is a non-zero refusal, not zero blockers. Every refusal has a stable code; rollback failure is distinct. JSON stdout remains one document.
- Neither command activates a spec, changes task-local loop fields, creates tasks, deletes artifacts, or commits the result.

V0.6 emits common envelope `schema_version:2` for every JSON-capable command and
loop result file. Version 2 retains the v0.5 outer member names and exclusivity but
replaces inherited inner shapes where stable references, storage, index snapshots,
or warning forms require it. No v0.6 command emits schema version 1. IDs are strings
and empty collections are `[]`, never `null`:

- Cancel result fields are exactly `task_ref`, `task_id`, `prior_status`, `status`, `reason`, nullable `cancelled_at`, `applied`, non-null sorted `cleared_fields`, nullable `state_transition`, and `dependent_blockers` (sorted task-ref strings). State transition fields are exactly nullable `current_task_before`, nullable `current_task_after`, and `blocker_removed`.
- Dependency result fields are exactly `task_ref`, `task_id`, `dependency_ref`, `dependency_id`, `operation` (`add|remove`), `applied`, non-null ordered `prior_dependencies`, non-null ordered `dependencies`, and `validation` (`valid`, non-null `violations`).
- Archive/restore result fields are exactly `task_ref`, `task_id`, `from`, `to`, `prior_storage`, `storage`, `status`, `applied`, `eligibility`, `path_reference_blockers`, `scan_complete`, and `unsupported_paths`. Eligibility fields are exactly `eligible`, `class` (`completed|cancelled|recovery`), nullable `last_verification_id`, nullable `completion_id`, nullable decimal-string `completion_generation`, nullable decimal-string `verified_completion_generation`, nullable `cancelled_at`, and boolean `cancellation_reason_present`. `recovery` is restore-only for tolerated storage-derived invalidity, always has `eligible:false`, and uses null/false evidence fields. A path blocker is exactly `path`, `line`, nullable `column`, and escaped `excerpt`; unsupported paths are strings.
- Inventory task objects are exactly `task_ref`, `task_id`, `title`, `status`, `storage`, `path`, `archive_eligible`, and non-null `blockers`. Each blocker is `code`, `message`, non-null sorted `task_refs`, and non-null sorted `paths`.

### Durable Path Reference Preflight

Physical paths are not durable references. Archive and restore fail before any
write when durable repository text still names the source path exactly.

Requirements:

- Archive and restore require a non-bare Git worktree whose root equals the Taskrail repository root and support both committed and local layout-3 storage. Results and durable text use canonical logical paths and never expose the local physical overlay.
- In committed mode, the source task is tracked and the worktree/index are clean. Restore additionally permits the narrow exact inverse of the command's sole staged rename when source/destination blobs and modes match and no unrelated change exists. Enumerate tracked paths from the Git index, including sparse or missing worktree entries. Every scan candidate rejects skip-worktree/assume-unchanged and requires stage-0 mode/blob to be semantically clean against the worktree; index and worktree disagreement refuses rather than choosing one.
- In local mode, the source is a regular managed-overlay task that is untracked, unstaged, effectively ignored, and reached without symlink, junction, reparse, mount, or sibling alias substitution. The scan combines clean tracked repository text with every supported managed local semantic file, translating physical overlay locations to logical paths before matching. Untracked files outside the managed overlay remain unsupported rather than silently omitted.
- Both modes inspect UTF-8 and BOM-marked UTF-16 text plus tracked symlink target text without following links; fail closed on unreadable, missing, gitlink, binary, unsupported encoding/filter, or incomplete classification scope. Human and machine results set `scan_complete:false` and list each unsupported path; they never call zero blockers clean.
- Search the target task and all other supported durable text. Match canonical repository-relative `/`, Windows `\`, and lexically resolvable Markdown/file-relative spellings with conservative ASCII case-folded comparison on every host, in prose, code strings, links, and suffixes such as `#anchor` or `:line`; do not match a longer filename such as `.md.bak`. For Markdown/autolink destinations, parse the destination and decode valid percent escapes exactly once before lexical comparison; malformed escapes or a decoded separator/control ambiguity refuse classification. Language-generated, concatenated, non-link percent encoding, encoded-without-BOM, and runtime-constructed paths remain explicitly outside deterministic detection.
- Each blocker reports repository-relative `/` path, one-based line, one-based Unicode-scalar column or `null`, and a bounded control-escaped excerpt around the match, sorted by path and location. It never prints an unlimited source line or raw terminal controls. The remedy names the stable `task_ref` and rerun command.
- Do not rewrite a source file, convert a link, or leave a redirect/tombstone automatically. The operator replaces stale paths deliberately, normally with `task_ref`; a predicted destination path inside the target task is itself an archive blocker because immutable self-reference would make restore impossible.
- Strictly decoded Taskrail review artifacts have one narrow exception: only top-level `task_path` in a valid task-review `review.json` using retained v0.5 schema version 1 or current v0.6 schema version 2 is historical metadata bound to that artifact's task identity and digest and does not block rename/archive. Prose, recommendations, evidence, every other schema field, unknown JSON, malformed review files, and any other path occurrence retain ordinary blocking behavior.
- Restore applies the same rule to exact archive-path references before moving back to live storage.
- Layout-3 `validate` reports a former live-path reference to an archived task, or a former archive-path reference to a live task, catching manual moves and interrupted unsupported tooling. In Git it uses the storage-mode classifier above. In a supported non-Git repository it scans canonical regular files beneath the configured root, excluding `.git`, Taskrail runtime-lock data, and configured ignored artifact roots; unreadable, special, or unsupported-encoding content is a named incomplete-scan warning, while archive/restore remains unavailable outside Git.
- Bare generated or opaque task references are not globally validated in arbitrary prose. Test fixtures, external issue identifiers, planned tasks, and historical references may legitimately resemble a Taskrail ID.

### Atomic Git-Aware Moves And Recovery

Archive and restore are one-file durable transactional moves with conservative
rollback. They use the shared v0.5 `taskrail recover <transaction-id>` surface;
v0.6 envelope version 2 extends snapshots with nullable Git-index states where
the committed branch uses them.

Requirements:

- Finish validation, eligibility, path-reference, destination, canonical-containment, and candidate-ledger preflight before creating directories or changing the worktree. Open and retain no-follow handles/identities for repository root, source parent, and the destination's nearest existing ancestor. Immediately recheck bytes/mode, Git stage, destination absence, references, eligibility, and handle ancestry. Symlink, junction, reparse, mount/identity substitution, unsupported handle-relative operations, or outside-root uncertainty fails closed.
- In committed mode require a stage-0 source blob/mode, clean Git semantic comparison, and no index flags. Raw worktree bytes may differ when Git built-in clean conversion explains it. Compare effective source/destination attributes; accept CRLF/encoding only when `git hash-object --path` reproduces the blob and destination attributes are equivalent, and refuse required/external filters or indeterminate conversion. Local mode instead durably snapshots exact source bytes/mode, destination absence, complete managed-local consumed-set digests, and the unchanged visible Git status/index; it invokes no Git staging operation.
- After preflight, create missing destination components one at a time relative to the retained nearest-ancestor handle, no-follow bind each new component, and then bind destination parent. Move with platform-native handle-relative no-follow rename semantics, not a second path-resolving `git mv`. Committed mode stages exactly source/destination through non-interactive Git and verifies the preserved blob/mode and expected rename. Local mode performs the same no-replace filesystem move beneath the overlay, validates the unified logical ledger, and proves the Git index and visible status remain unchanged. Both preserve bytes/mode and use compare-and-swap rollback.
- Before commit success, rerun eligibility, path scan, attributes, candidate-ledger validation, and the complete consumed read-set digest against the retained handles and current index/worktree. Any new reference, attribute/index/input change, or lock-phase mismatch triggers conditional rollback; no preflight snapshot alone authorizes the move.
- On ordinary failure after a move, reverse filesystem and index state and remove every directory created by the command in reverse order when empty. Each reversal is compare-and-swap: current source/destination bytes, mode, and index entries must still equal the transaction's published move state. If an external process changed any component, preserve it, retain recovery ownership, and report rollback failure rather than overwrite it. A successful rollback leaves task bytes, mode, paths, Git index, and state exactly as before.
- A rollback failure reports both paths, `git status`, `git ls-files --stage`, bounded byte comparison, the original and rollback errors, and non-destructive inspection commands. Taskrail never deletes one side, chooses between duplicates, resets Git, or fabricates a missing task. Repair explicitly refuses content/location ambiguity.
- Archive/restore forward interruption to any active Git staging process, wait for it, inspect retained directory identities plus filesystem and applicable index/local snapshots, then either complete rollback or report a classified source-only, destination-only, both-path, neither-path, ancestor-substituted, or snapshot-disagreement recovery state. Neither-path guidance relies only on durable transaction and Git/local snapshot evidence, never inference from absent data.
- Every task/state/layout/config writer inherits the v0.5 fail-closed repository mutation protocol held from initial resolution through final write or rollback. Multi-file lifecycle writers construct and validate candidate state, atomically replace only their explicit write set, and use compare-and-swap rollback with structured partial diagnostics. A partial/rollback failure retains transaction/recovery metadata and lock ownership for explicit shared recovery; no later writer or archive operation may bypass it.
- Legacy ImportDraft v1 apply upgrades its v0.5 normal transaction to durable crash recovery in v0.6. Its scaffold/body interpretation and handled-failure all-or-none behavior remain compatible; v0.6 adds the durable manifest and shared recovery fence before publication.
- The v0.5 loop delegates its Git lock to child writers with a per-invocation token; delegated children do not reacquire or release it. Archive and restore are prohibited under delegated loop ownership. Layout migration holds the same lock from original-marker inspection through final validation/rollback and refuses to restore an older marker if any semantic state changed concurrently. Failure to acquire or validate ownership is fatal. Locks are local, not distributed.
- Before first publication, the writer durably stores under the private no-follow lock root an exact manifest plus original bytes/modes/index entries for every write-set path and candidate digests. It fsyncs backup files and parent directories before changing semantic state, then fsyncs published files/directories before marking committed. Clean commit or complete rollback removes only that transaction's backups after durable outcome; abrupt death at every boundary leaves enough bytes and phase data to recover without inference.
- Inherited recovery refuses a live owner. The v0.6 manifest represents path and applicable index absence explicitly as snapshot values. Restore accepts a crash-partial per-component mix where each current value, including expected absence, equals recorded candidate or original; it restores candidate-valued components from backups, leaves original-valued components unchanged, fully validates all-original, then clears. Accept requires every component to equal the complete candidate and validation to pass. Unexpected presence/absence, a value matching neither snapshot, invalid result, or other external state preserves data/backups and refuses. Recovery uses no reset/checkout and is failure-injected transactionally.
- Every read-only surface, including task show/list, status/stats/graphs, coverage/gaps, validate/repair preview, prompt resolution, archive/restore dry-run, path scanning, and migration/recovery preview, rejects an active publication/recovery phase. It snapshots and rechecks the complete consumed set: task/spec/state/config/prompt bytes, lock phase, Git index entries/flags, attributes, and scanned tracked/worktree files as applicable. Task-local loop fields enter every applicable read set through the containing task bytes, never through a separate policy file. Output occurs only when the full read-set digest and lock phase remain unchanged; internal validation by the owning writer uses its explicit candidate snapshot instead.

### Layout 3 Migration And Compatibility

Physical archival changes which files comprise the ledger, so `v0.6.0` raises the
supported layout version from 2 to 3.

For an otherwise valid source layout whose existing IDs collide only under the
new identity/portability rules, migration accepts a narrowly scoped reviewed map:

```text
taskrail init --identity-map <map.json> [--apply] [--json]
```

Requirements:

- The strict map is `schema_version:1` plus non-null `mappings`; each unique entry is exactly `from` (existing exact full ID) and `to` (new valid opaque ID). Preview is default. It is accepted only during an upgrade to layout 3, only for IDs named by candidate collision violations, and must map enough members to make every collision unique. For each positive numeric collision, exactly one original claimant must remain so migration never releases that historical key. Non-colliding/general re-key requests and use after layout 3 are rejected.
- Source-layout references are interpreted with their old exact-full-ID semantics before mapping. Apply atomically rewrites mapped task filename/frontmatter/H1 and every known machine relationship in tasks and state, but no arbitrary prose, code, artifacts, or history. It preserves paired task-local `loop_policy`/`loop_reason` values or their joint absence and never reads or rewrites a separate policy file. Durable old physical-path references must be repaired before apply. The complete mapped ledger, case/Unicode portability, dependencies, task-local loop fields, and state validate before publication.
- Mapping, marker, and any required multi-hop skill outputs are one durable mutation transaction under the common backup/recovery protocol. Failure publishes none or retains recoverable evidence. Output reports every old/new ID/path and rewritten machine field. No redirect, alias, or reusable old numeric key remains.
- V0.6 init replaces the inherited result by adding non-null `identity_mappings` and `rewrites` after `continuation_notes`; both are `[]` outside identity-map migration. Each identity mapping is exactly `from_task_id`, `to_task_id`, `from_path`, and `to_path`. Each rewrite is exactly `path`, `field`, `from`, and `to`, ordered by path, field, and original value. All other inherited init fields retain their exact meaning.

- Normal version-aware init previews and applies `2 -> 3`, or the ordered `1 -> 2 -> 3` path when upgrading an older repository. Every intermediate contract is honored. A `1 -> 2 -> 3` apply accepts inherited `--confirm-quiescent` and exactly one of `--extract-continuation-notes` or `--drop-continuation-notes` when required. A direct `2 -> 3` invocation rejects all three as inapplicable.
- A direct `2 -> 3` migration without `--identity-map` changes
  `.taskrail/config.yml` and creates the configured IDEAS template only when that
  path is absent. It never moves tasks, creates the archive root, rewrites
  IDs/references, backfills verification or cancellation metadata, refreshes
  skills, or edits `STATE.md`; an existing ideas file is preserved byte-for-byte,
  and the reviewed collision-map exception has the explicit larger write set
  above.
- A `1 -> 2 -> 3` invocation is one transaction. It removes schema-1 continuation notes and the rendered state Notes section, creates the absent IDEAS template, and when `--extract-continuation-notes` is selected creates the absent human NOTES sidecar, on the same boundary as the marker. If committed packaged-skill destinations exist, apply requires the v0.5 combined `--with-skills --force` consent, stages the current v0.6 packaged bytes (not an observable intermediate v0.5 copy), validates parity/version against the layout-3 candidate, and publishes state, notes, ideas, skills, and the final marker atomically. Repositories without installed skills do not create them. Failure restores the original state, marker, and every original skill byte/mode and removes only the transaction's newly created notes/ideas files; no intermediate state schema, marker, skill version, or extraction survives.
- Preview validates the source layout and candidate combined ledger and reports marker change plus legacy/nonportable IDs, completed tasks lacking generation adoption, cancelled tasks lacking provenance, portability collisions, and manually created archive content. It writes nothing. A multi-hop invocation is one transaction from its original marker to 3, not a partially successful stop at 2.
- Apply rechecks the original marker and repository, atomically replaces the marker, validates under layout 3, and restores the invocation's original marker if any hop or post-validation fails. Rollback failure reports both errors and any intermediate interpretation.
- If an archive root exists under layout 1 or 2, commands refuse to ignore it. Migration treats absent/empty roots as no content and does not create them. Non-empty content is adopted only when every entry is tracked, direct, available, candidate-valid terminal history that is eligible or exact v0.5 debt, with no post-map ledger collision, complete path scan, and clean Git state. Preview lists each file, eligibility/debt, and `adopt_existing_archive`. Without an identity map, apply changes no task byte/path; when a mapped collision claimant is already in the pre-layout archive, the reviewed mapping rewrite is the sole explicit exception before archive immutability takes effect. Adopted debt stays immutable and requires restore before remediation. Untracked, open, unlisted-ineligible, sparse, duplicate-after-map, unreadable, or path-blocked content is a blocker. Older binaries refuse layout 3.
- Layout-3 local promotion includes live and archived tasks, the configured ideas file, state, specs, notes, prompts, and durable reviews in one candidate. It preserves each task's live/archive storage class, excludes runtime/recovery/artifacts, and refuses unknown durable local entries rather than omitting them.
- Every v0.6 semantic writer, including ordinary lifecycle writers, opaque creation/import, stable-reference writes, verification metadata, cancellation, archive, and restore, requires layout 3 first. Read-only inspection and init migration may read older layouts. This prevents a layout-2 binary from later erasing unknown v0.6 metadata or misreading references.
- Before layout-3 apply can publish its marker, every inherited semantic writer is already capable of combined-ledger resolution/allocation, explicit live-only write sets, and archived-target refusal behind the layout-3 guard. Migration activation cannot create a window in which layout 3 is accepted but ordinary writers still use live-only identity or mutate archived history. Later exhaustive writer-sink verification retains its own release task.
- Root discovery inherits v0.5 Git-root and `.taskrail/config.yml` ancestry behavior. When both exist, configured Taskrail root must equal the worktree root for Git-dependent loop/archive/restore behavior; ordinary non-Git lifecycle writers use the repository-root-local mutation lock.
- Existing generated task filenames, IDs, body headings, dependencies, and state pointers remain byte-identical through migration unless explicitly named by the collision-only identity map. Legacy full-ID machine references remain supported. Every existing ID must be valid UTF-8 and equal its filename stem; invalid encoding remains a violation. A legacy ID is `portable-safe` when it is 1 through 252 ASCII bytes, matches `^[A-Za-z0-9][A-Za-z0-9._+-]*$`, has no trailing dot or Windows reserved device stem, and has no exact, ASCII-fold, or NFC-plus-Unicode-case-fold sibling/ledger collision. Portability and numeric class are independent: every positive numeric-looking legacy ID uses canonical `T-<key>` as task_ref; any other portable-safe legacy uses exact ID; any other nonportable legacy uses `L~` plus lower-case SHA-256 of exact UTF-8 full-ID bytes. Digest refs are at most 66 ASCII bytes and exact-full-ID/digest collisions are invalid. Every portable-safe legacy class may archive when otherwise eligible; every nonportable legacy is warning, immutable, and non-archivable but can migrate and participate through its safe reference. Structured writers quote/escape strings and human diagnostics control-escape full IDs. No normal layout-3 legacy creation/re-key exists.
- Layout 3 preserves the inherited paired task-local `loop_policy`/`loop_reason` fields exactly, including joint absence; migration neither externalizes them nor creates a separate policy representation.
- A numeric-looking legacy ID claims a generated key only when normalized decimal is positive, participates in collision/allocation/short lookup/generated-key ordering, and never releases history. Zero-valued legacy has no allocation meaning, sorts in the final legacy class, resolves exactly by full ID, and uses exact ID or digest task_ref according to the portability matrix.
- A task is generation migration debt only when it is completed without v0.6 generation metadata or carries at least one valid v0.5 completion/verification field without the corresponding v0.6 generation. A fresh/open v0.6 task with no such fields is not debt. Valid v0.5 debt includes completed no-metadata, completion ID only, completion ID with bound pass/unbound fail, and non-completed pass/fail records without binding. Migration never backfills and none qualifies archive. On next verify, completed pass preserves/generates completion ID and adopts generation `"1"`; completed fail preserves any completion ID but leaves completion generation absent/debt while writing fail generation `"0"`; non-completed pass/fail writes generation `"0"` and removes debt. Next complete writes/preserves ID and generation `"1"`. Completed-debt-plus-fresh-fail is the only hybrid; otherwise any generation field switches to strict v0.6 and unlisted partial combinations are invalid.
- A live legacy cancelled task with neither cancellation field is valid-but-warning layout-3 migration debt. A partial field pair is invalid. It remains archive-ineligible, and `cancel --reason` may adopt provenance while any number of such warnings remain; the warning disappears per repaired task. Newly written cancellation always requires both fields.
- An open dependency on a legacy cancelled task is likewise valid-but-warning migration debt, not a migration blocker. `task dependency remove` or cancellation of the dependent is permitted while such warnings remain; newly created edges are rejected and each repaired edge removes its warning.
- Validation text renders migration debt to stderr while retaining zero exit and `state valid with warnings`. JSON adds a non-null `warnings` array with stable codes, task references, and remediation; `violations` remains the only validity gate. Migration preview/apply returns the same warnings, and tests prove they disappear after remediation.
- For a direct `2 -> 3` upgrade, documentation requires the separate explicit skill refresh after binary upgrade. Multi-hop installed-skill handling follows the atomic rule above. Before any v0.6 semantic write, rollback may revert the marker/skill commit after confirming no archive content exists; hand-lowering the marker is always unsupported.
- After any v0.6-only ID, stable machine reference, cancellation/verification metadata, or other semantic write, downgrade is unsupported without reverting every such reviewed commit. Restoring archived tasks alone is insufficient. Release tests prove older-binary refusal; Taskrail provides no lossy automatic downgrade or normalization exporter in this version.

### Unified Workflow And Loop Integration

All workflow surfaces must understand stable references and archive storage without
turning archival into task execution.

v0.6 inherits rather than redesigns v0.5's task-local loop policy. The optional
`loop_policy` and `loop_reason` frontmatter fields are a paired value on each task;
both missing means implicit `hold`. The root `taskrail loop` command is their only
selection consumer. Validation and the `task loop` management family inspect or
mutate the pair, while other selectors and lifecycle commands do not interpret it;
there is no separate queue or policy file.

Requirements:

- V0.6 replaces the inherited task-loop row with exact fields `task_ref`, `task_id`, `storage`, `status`, `active_spec`, `source`, `effective_policy`, `reason`, `eligible`, non-null `held_dependencies`, and `disposition`. `held_dependencies` contains stable task-reference strings. Dry-run `selected_task`, task rows, remaining work, and diagnostic policy objects all use this replacement shape.
- V0.6 envelope version 2 replaces the inherited loop `last_iteration` object by adding exact `task_ref`, `storage_before`, `storage_after`, and nullable `cancellation` to all inherited fields. Cancellation, when present, is exactly `reason`, `cancelled_at`, `task_ref`, and `task_id`. The invocation diagnostic otherwise retains v0.5 fields and nullability.
- New task-review publications use artifact schema version 2, retain the inherited four-field prompt-resolution binding, and add required `task_ref` immediately before snapshot `task_id`; both resolve to the same task at publication. The ID and `task_path` remain immutable historical snapshot metadata, and rename/archive never rewrites either review schema. Existing schema-v1 artifacts remain valid historical evidence without current prompt re-resolution.
- Workflow-adversarial index/report schema version 2 retains report-local prompt resolution and replaces optional historical `task_id` with an optional paired `task_ref` and `task_id`; tracked findings require both. The first v0.6 publication over a v1 index mechanically resolves every stored exact ID, constructs a v2 candidate under the inherited report/index transaction, and refuses ambiguity or a missing claimant without changing v1 memory. Immutable v1 reports remain unchanged, and the index does not duplicate report prompt bindings.

## Caution

Do not turn archival into deletion, lifecycle status, or a second task database.
Task frontmatter remains authoritative; storage is a path-derived classification;
both roots are always one ledger. Archive and restore preserve identity and status.

Do not make opaque mean arbitrary bytes. Restrictive ASCII and filename limits are
the portability contract. Do not silently normalize an externally meaningful ID,
guess at case, fuzzy-match a slug, or expose an arbitrary-width number as JSON
numeric data.

Do not rewrite code or prose to make a move succeed. Refusal with exact locations
is safer than a language-agnostic source rewrite. Likewise, archived immutability
is more important than making every existing writer operate in both roots; restore
first when delivered history genuinely needs revision.

Path preflight guarantees defined textual spellings, not semantic discovery inside
arbitrary binaries or language-generated strings. Unsupported tracked binary,
encoding, gitlink, or filter scope is disclosed and refuses archive/restore rather
than producing a false clean claim. Operators retain responsibility for generated
or runtime-constructed references outside the deterministic scanner contract.

The archive root reduces live-directory noise, not historical accounting. Status,
coverage, stats, and graph history still include archived tasks. Repositories that
want deletion or retention policies need a separate specification.

## Recommendation About LLM Support

Unchanged: do not add direct model or provider calls to Taskrail core. Identity,
resolution, path scanning, migration, and file moves are deterministic CLI work.
Prompts and skills may explain the workflow, but the binary neither asks a model
whether a task is safe to archive nor delegates collision or recovery decisions.

## Explicitly Excluded

Continue to exclude:

- task deletion, pruning, compression, retention schedules, or garbage collection;
- automatic archival on `complete`, `verify`, release, spec activation, or loop success;
- archive daemons, background jobs, bulk age-based movement, or remote archive storage;
- a new `archived` lifecycle status or storage field duplicated in task frontmatter;
- recursive or caller-configurable archive sharding in this version;
- archive or restore of untracked tasks outside the validated managed local overlay, non-Git repositories, or a Taskrail root that differs from its Git worktree root;
- opaque-ID normalization, fuzzy matching, aliases, or general/post-layout re-keying and generated/opaque conversion outside the collision-only migration identity map;
- arbitrary Unicode, punctuation, path separators, dots, underscores, or unbounded filename components in opaque IDs;
- rewriting arbitrary code, prose, Markdown links, Git history, commits, or verification artifacts during archive/restore;
- tombstone files, symlinks, redirect stubs, or path aliases left in the live task directory;
- treating bare ID-like strings in arbitrary prose as validation errors;
- mutation of archived task content without an explicit restore;
- uncancel, reopen, uncomplete, or status changes performed by restore;
- cancellation that silently strands open dependents;
- external issue-tracker synchronization or ownership of external identifier lifecycles;
- machine-assigned idea IDs, per-entry idea status/counts, automatic `BACKLOG.md`
  migration, source-range rewriting, duplicate inference, round-trip
  synchronization, or direct task creation from IDEAS without explicit review;
- semantic inference of archive readiness beyond recorded status-specific metadata;
- Git commit, push, merge, reset, or rollback beyond reversing the command's own file move; and
- bypassing layout compatibility so v0.6 archive support can land before v0.5 layout 2.
