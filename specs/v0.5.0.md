# Taskrail v0.5.0

## Summary

Taskrail `v0.5.0` adds **autonomous workflow integrity and reviewable planning**.

Through `v0.4.0`, Taskrail established deterministic task state, active-spec
selection, reviewable import drafts, structural coverage and gap reports, and a
packaged skill set. Adopters can drive those primitives with an external coding
agent, but Taskrail does not yet provide a portable outer loop or a reusable
workflow-prompt surface. Repositories therefore assemble their own shell runner,
unattended-selection rules, prompts, and post-run checks. Those copies are useful, but they
drift and are commonly platform- or provider-specific.

The existing skill contract also has a concrete lifecycle defect. The packaged
`autonomous-backlog` and `autonomous-task` skills run `verify` and then say, in
prose, to finish as `completed` or `blocked`; neither invokes `complete` or
`block`. Because `verify` is not a lifecycle transition, a nominally successful
run can remain `in_progress`, and a run that cannot proceed can leave no recorded
blocker.

This version fixes that lifecycle contract and builds on it in bounded ways:

- one versioned machine-result envelope for agent-consumed commands, including
  lifecycle writers and a separate result file for streamed loop execution;
- an explicit local planning mode that keeps Taskrail metadata ignored in a
  non-adopting repository while still allowing reviewed product-code delivery;
- a cross-platform, foreground `taskrail loop` command that starts one fresh,
  caller-supplied external process per explicitly allowed task, runs sequentially
  by default, and can explicitly execute one dependency-ready frontier in
  isolated shallow clones before serial local or review-adapter integration;
- a versioned catalog of built-in workflow prompts with deterministic rendering,
  repository-local replacement, prompt-bound review publication, and
  outcome-focused task authoring;
- stronger prompt and skill workflows for post-spec, existing-task, and
  adversarial spec-to-task review before any draft is applied, backed by one safe
  review publisher;
- report-only adversarial workflow testing with compact cross-run memory of
  findings and tested surfaces;
- Agent Skills-compatible version metadata with legacy marker reads and retained
  package parity/skew guarantees; and
- a lightweight skill handoff from reviewed OpenSpec or Spec Kit artifacts into
  Taskrail's existing spec, import, and decomposition flows; and
- human-owned repository notes plus maintainer-run behavioral evaluation of
  shipped skills without provider logic in the binary; and
- one focused implementation review by default, risk-justified additional lenses,
  and a non-recursive final-diff review whose repairs may close through objective
  evidence instead of manufacturing avoidable follow-up work.

Taskrail still does not call a model, know about model providers, interpret a
skill, or silently write judgement-derived planning state. The binary owns the
mechanical boundary: selection, policy validation, prompt resolution, process
execution, and postconditions. The external agent owns semantic implementation
and review. Humans still decide which spec findings and task drafts become
committed state.

## Goals

- Settle one normative lifecycle order and make every full-task skill and built-in task prompt lifecycle-complete against it.
- Give agents one strict JSON success/error contract across every command result they consume.
- Provide a portable autonomous loop without parallel shell implementations or
  provider-specific adapters: sequential by default, with an explicit bounded
  isolated-clone mode that schedules only a dependency-ready frontier, publishes
  independently valid successes, and launches no replacement work after a bad,
  blocked, stale, or incomplete worker or integration result.
- Separate lifecycle status from optional task-local loop policy without a queue, global barrier, or second database.
- Make workflow prompts versioned, deterministic, inspectable, and locally replaceable, and bind published review observations to the exact prompt resolution current at publication.
- Make task bodies outcome-focused and give acceptance criteria concrete but implementation-neutral verification designs.
- Review existing tasks semantically without duplicating the post-spec lens family or mutating tracked work directly.
- Keep packaged skills within the Agent Skills frontmatter format while preserving version-skew detection and byte-exact mirrors.
- Provide a lightweight, reviewed OpenSpec and Spec Kit handoff without a binary adapter, synchronization layer, provenance claim, or automatic apply.
- Improve decomposition with requirement traceability, explicit verification planning, and a fresh adversarial review before `import --apply`.
- Productize post-spec consistency, gaps, additions, and adversarial lenses plus post-implementation workflow-adversarial review.
- Add opt-in active-spec statistics without hiding repository-wide history by default.
- Test shipped skills and built-in prompts mechanically on every change, and evaluate changed skills against released baselines through a manual maintainer suite before release.
- Preserve useful repository-wide human context in a human-owned notes sidecar rather than generated `STATE.md` continuation prose.
- Let one user keep Taskrail planning locally in a repository that has not
  adopted Taskrail, without dirtying ordinary Git status or weakening explicit
  promotion into committed planning.
- Keep explicitly installed local skills discoverable at their normal assistant
  paths without exposing them to Git, hiding adopter-owned assistant content, or
  teaching agents physical local-storage paths.
- Run implementation review through one broad round and one fresh reviewer by
  default, with risk-justified additional lenses, a repository-selected maximum
  of one or two rounds, and a conditional non-recursive final-diff review, while
  keeping other review workflows on their own contracts.
- Keep semantic findings advisory and reviewable until a human adopts one or applies a task draft.

## Potential Features

### Repository Discovery, Locking, And Recovery

Taskrail discovers one managed repository before command-specific work. In a Git
worktree, the configured Taskrail root and worktree root must agree for Git-bound
commands. Outside Git, ordinary read and semantic-write commands walk ancestors
to the nearest valid `.taskrail/config.yml` and use its directory as the managed
root; ambiguous roots refuse. `loop`, local mode, committed delivery checks, and
other commands whose contract explicitly requires Git remain unsupported outside
a non-bare worktree.

Every semantic writer uses one repository mutation lock. Git worktrees place it
beneath the Git common directory so linked worktrees coordinate. A discovered
non-Git repository places it beneath its root-local `.taskrail/runtime/`. Lock
identity never depends on the invocation directory. Metadata records a random
lower-case 32-hex lock ID, canonical command, PID, host, start time, repository
identity, storage mode/root, nullable transaction ID, executable digest when
delegated, and only a delegation-token digest.

Command surface:

```text
taskrail lock status [--json]
taskrail lock clear <lock-id> --expect-sha256 <digest> [--json]
taskrail recover <transaction-id> [--take-over-lock <lock-id> --expect-sha256 <digest>] [--apply] [--json]
```

Requirements:

- `lock status` is read-only and reports absence or the exact owner metadata and
  raw-file digest. `lock clear` removes only that unchanged named lock, refuses a
  provably live same-host owner, and requires the operator-selected ID and digest.
  Taskrail never auto-clears by PID, host, or age because those signals are not a
  distributed lease.
- `lock status` remains admitted while a recovery fence exists so an operator can
  inspect the owner blocking recovery. `recover --take-over-lock` requires the
  paired exact lock ID and raw-file digest in preview and apply, requires that
  lock's transaction ID to match the requested transaction, and refuses a
  provably live same-host owner. Preview is read-only. Apply compare-and-deletes
  only those unchanged lock bytes, acquires recovery ownership, and then performs
  the mechanically derived recovery action. A different-host owner is never
  inferred dead; supplying its exact observed identity is explicit operator
  authorization. Changed bytes, identity mismatch, or a lost acquisition race
  refuses without changing transaction state.
- A normal transaction holds the lock, snapshots its complete read/write set,
  builds and validates candidates before publication, atomically replaces each
  file, and compare-and-swap rolls back handled failures. Its all-or-none promise
  covers handled command failures, not abrupt process or host death.
- Durable transactions additionally record original presence/bytes/modes,
  candidate digests, path identities, owning command, and durable phase beneath
  the lock root before the first semantic publication. An interruption leaves a
  recovery fence that blocks affected reads and writes.
- Durable recovery is required for layout migration, explicit or implicit local
  initialization, local promotion, workflow report/index publication, and
  ImportDraft v2 apply. Spec/task/decomposition directory publication uses its
  single no-clobber directory commit point. Other v0.5 writers use normal
  transactions unless their section explicitly says otherwise.
- `recover` previews exactly one mechanically safe action: `restore_original`,
  `accept_candidate`, or `clear_fence`. Apply performs only that action. Restore
  changes components still equal to recorded candidate bytes; accept requires the
  complete candidate and command-specific validation; clear requires no semantic
  candidate publication. Unexpected bytes refuse with `write_conflict` and are
  never overwritten. Recovery is itself interruption-safe and never uses Git
  reset, checkout, or semantic inference.
- The exact lock and recovery result objects, phases, path rules, error subsets,
  and deterministic ordering live in the normative machine API companion.

### Canonical Transition Order

Define one normative order for a tracked-work run in
`docs/workflow/autonomous-contract.md`, and cite that contract from the skills,
built-in prompts, `AGENTS.md`, and tests rather than inventing a different order in
each surface.

Recognized branches:

```text
completed-pass: validate -> start -> implement -> checks -> complete -> verify pass
blocked-fail: validate -> start -> block --reason -> verify fail -> stop
rework-fail: validate -> start -> verify fail -> stop (remains in_progress)
```

In v0.5, `<task-id>`, `task_id`, dependency values, blocker identities, and
task-valued result fields always mean the exact full persisted task ID, including
any slug suffix. A bare numeric prefix is valid only when it is itself the exact
full ID. v0.5 defines no `task_ref` field or stable-reference resolver; those
begin in v0.6.

Requirements:

- `complete` precedes `verify --result pass`; verification records an already-finished implementation and neither decides nor performs its lifecycle transition.
- `complete` is never called for a failing or blocked run. Failure leaves the task `blocked` with a reason or `in_progress` for deliberate rework; `verify --result fail` is never described as blocking it.
- "Terminal branch" means the current autonomous run ends. `blocked` remains reversible through `unblock`, not immutable delivered history.
- A direct operator may create follow-ups before `complete` with `task new` or
  during verification with `verify --create-followup`; both re-project state and
  omit loop-policy fields. Under loop delegation, `verify --create-followup` for
  the selected task is the only permitted task creator. A delegated child may
  create every independently meaningful out-of-scope follow-up it discovers;
  v0.5 imposes no numeric cap, but every new task must be named by a fresh
  verification report for the selected task and remain implicitly held.
- A full-task skill or built-in task prompt names both success and cannot-proceed branches; "finish as completed or blocked" is insufficient.
- Every writer's exit is checked before the next command. If `complete` succeeds but passing `verify` fails to execute, stop as `completed-unverified` and rerun only passing verification after inspection; never repeat `complete` or compensate with `block`. If a later independent audit records fail on completed work, keep delivered history completed, create a follow-up when action is required, and report `completed-audit-fail` rather than rework/block.
- An operator may deliberately relinquish interrupted or rework-pending active work with `taskrail task release <task-id> --reason <text> [--dry-run] [--json]`. Release changes one `in_progress` task back to `todo`, preserves completion and verification history plus task-local loop policy, appends the reason to Implementation Notes, and never fabricates blocker history. It clears both current-task fields when they name the target, then reprojects status summary, blockers, next action, and idle state from the complete candidate ledger. A missing, stale, unrelated, or contradictory active pointer refuses `repository_invalid` rather than being cleared. Delegated loop children cannot release work.
- Release reason uses the loop-reason grammar: trimmed UTF-8 of 1 through 512 bytes, no newline/control character, and the portable-note guard. Apply updates the task timestamp; if state points to another task or represents a contradictory active pointer, it refuses `repository_invalid` rather than clearing unrelated state.
- Release result fields are exactly `task_id`, `prior_status`, `status`, `reason`, boolean `applied`, nullable `current_task_before`, nullable `current_task_after`, boolean `current_task_cleared`, `task_sha256_before`, `task_sha256_after`, and `validation` with boolean `valid` plus non-null common violations. Dry-run has `applied:false` and the candidate digest; apply reports the published digest. Errors use `invalid_arguments`, `not_initialized`, `incompatible_layout`, `migration_in_progress`, `task_not_found`, `invalid_status`, `invalid_reason`, `repository_invalid`, `lock_held`, `delegated_write_refused`, `write_conflict`, `recovery_pending`, `partial_write`, or `rollback_failed` with common details.
- `complete` records a new non-empty random lower-case 32-hex task `completion_id` and clears all prior task-level verification fields. `start`, `block`, `unblock`, and `task release` preserve the task's current completion and verification fields exactly. Every verification replaces the task's latest tuple: `last_verification_id`, nullable `last_verification_previous_id`, `last_verification_result`, and `last_verified_at`; `last_verified_completion_id` is present only for a passing verification bound to the current non-empty `completion_id`. The previous ID is null when no task-level predecessor exists and otherwise equals the exact preflight `last_verification_id`.
- Verify JSON and `report.json` use `verification_id`, nullable `previous_verification_id`, `result`, and nullable `observed_completion_id`. State stores the latest repository-level `last_verification_id`, optional `last_verification_previous_id`, and optional `last_verified_completion_id`; `complete` and every other non-verification writer preserve that repository-level historical tuple. The task note is `- <time>: verification <result> id <verification-id> previous <id|none> completion <id|none>`, and artifacts use `<timestamp>-<verification-id>`.
- A verification chain is valid only when a non-null predecessor identifies the exact prior task-level verification and its report. A current pass requires completed status, non-empty completion ID, and equal non-empty observed ID across all surfaces. A completed audit fail must directly follow the fresh bound pass from the same loop iteration: its `previous_verification_id` equals that pass ID. Wall-clock ordering cannot repair a missing or broken chain.
- Report-chain availability is checked when `verify`, loop postflight, or another
  producer claims fresh evidence in its current artifact workspace. Persisted
  task/state validation checks the closed metadata combinations and predecessor
  IDs but does not require gitignored reports to survive cleanup or a Git clone;
  absent producer-local reports mean freshness cannot be re-attested there, not
  that portable committed lifecycle state becomes invalid.
- A first post-upgrade pass over legacy completed history atomically adopts a new completion ID and binds it; a fail records no observed completion and does not adopt. Passing/failing verification before completion uses `none`. Legacy completed work remains delivered for compatibility but is not a current bound pass until adoption.
- The canonical state summary is `<pass|fail> for <task-id> at <RFC3339-UTC> id <verification-id>`. Freshness requires an ID absent from the preflight artifact/summary snapshot, valid predecessor linkage, and exact agreement across state, task note, and `report.json`; wall-clock order alone is insufficient.

The valid task-level metadata combinations are closed:

| Lifecycle shape | `completion_id` | Latest verification tuple | Completion binding |
|---|---|---|---|
| `todo`, `in_progress`, or `blocked` before any verification | absent | absent | absent |
| any non-completed status after verification | absent | complete tuple, chained when a predecessor exists | absent |
| newly completed | required | absent because `complete` cleared prior task verification | absent |
| legacy completed before adoption | absent | absent or legacy pre-ID history only | absent |
| completed after fail or unbound pass | required, except legacy pre-adoption fail | complete tuple | absent |
| completed with a current pass | required | complete tuple | equal to `completion_id` |

A partial tuple, a fail with a completion binding, a binding unequal to the
current completion ID, a non-completed binding, or a predecessor without matching
prior evidence is invalid. Optional fields are omitted rather than empty or null
in persisted YAML.

#### Lifecycle-Complete Skill Flows

Rewrite `autonomous-backlog` and `autonomous-task` to use explicit commands for
both terminal branches.

Requirements:

- The success branch invokes `${TASKRAIL:-taskrail} complete <task-id> --note "..."` before `${TASKRAIL:-taskrail} verify <task-id> --result pass --summary "..."`.
- The cannot-proceed branch invokes `${TASKRAIL:-taskrail} block <task-id> --reason "..."` before `${TASKRAIL:-taskrail} verify <task-id> --result fail --summary "..."`, never invokes `complete`, and then stops.
- Both branches preserve the Taskrail source-checkout freshness guard immediately
  before every state writer.
- `autonomous-verify` remains a separate verification workflow and may verify a
  task whose lifecycle transition already happened.
- Regenerate committed `.agents/` and `.claude/` copies from `internal/taskrail/skills/` so package parity remains byte-exact.

### Agent Skills Format And Version Metadata

Keep every packaged `SKILL.md` within the Agent Skills frontmatter format while
retaining Taskrail's installed-copy skew detection.

Requirements:

- Packaged skills use the standard top-level fields: required `name` and `description`, plus optional `license`, `compatibility`, `metadata`, and `allowed-tools`. Taskrail-specific data belongs under `metadata`; no new custom top-level field is written.
- Installed copies written by `taskrail init --with-skills` or `taskrail init --local --with-skills` carry `metadata.taskrail_version` as a non-empty YAML string, for example `metadata: {taskrail_version: "v0.5.0"}`. Writers emit only this nested form and preserve other valid metadata entries.
- Readers continue accepting the legacy top-level `taskrail_version` string. A file containing both locations is accepted only when their string values match; conflicting dual markers are an invalid skill marker and fail the install/refresh operation rather than choosing one. A subsequent successful writer refresh normalizes a matching dual or legacy-only marker to nested-only form.
- Missing markers retain the existing parity-aware behavior: a marker-free installed copy byte-identical to the embedded package is not skewed, while a divergent marker-free copy remains unknown-version. Nested and legacy markers feed the same advisory running-version skew check and `--force` remedy; marker location does not create a second skew policy.
- Remove the non-standard `argument-hint` top-level field from packaged skills and both committed mirrors. Invocation arguments remain documented in skill prose rather than private frontmatter.
- Embedded package sources and committed `.agents/`/`.claude/` copies remain marker-free and byte-identical. Version stamping occurs only in installed output, and package parity and destination skew checks remain separate guarantees.

### Storage-Neutral Packaged Skills

Make the complete packaged skill set operate through Taskrail's active storage
context instead of treating logical managed paths as physical filesystem paths.
This applies equally to the inherited skill set and every skill added in v0.5.

Requirements:

- Skills invoke `${TASKRAIL:-taskrail}` without a storage-mode flag. Repository
  discovery selects committed or local storage; a skill never reads
  `.taskrail/config.yml` to reproduce that decision.
- Skills use `--json` whenever they consume IDs, paths, warnings, eligibility,
  previews, lifecycle outcomes, storage mode, or failure details. Exact content
  commands may remain text when their bytes are the workflow input.
- Managed task, spec, and durable review bytes are read through `task show`,
  `spec show`, and `review show`. Logical `planning/...`, `specs/...`, and
  `.taskrail/prompts/...` paths remain identifiers and citation targets, not
  authority to open a filesystem path directly.
- No packaged skill prepends, derives, opens, stages, or publishes a semantic
  `.taskrail/local/...` path. A physical transient path is usable only when an
  exact Taskrail result reports it for that purpose, such as status
  `storage.artifacts_dir`; durable output returns through the applicable Taskrail
  writer.
- Skills that need delivery behavior consume the active storage mode reported by
  Taskrail. Committed-mode workflows preserve their complete implementation plus
  Taskrail metadata delivery contract; local-mode workflows never force-add
  ignored Taskrail bytes and commit only visible product changes when a commit is
  required.
- In local mode, built-in prompts and packaged skills minimize Git-visible
  provenance: they do not derive commit subjects, bodies, trailers,
  author/committer identity, attribution, refs, or unrelated visible-file text
  from ignored Taskrail task/spec/review content, IDs, logical managed paths,
  verification identities, or storage details. They follow repository-visible
  commit, identity, attribution, signing, hook, and ref policy, never change Git
  identity configuration, and never invent Taskrail or agent attribution.
  Repository-visible policy frozen before the workflow governs generic commit,
  identity, signing, hook, and ref conventions, but only a caller-owned instruction
  outside managed Taskrail content may authorize exposing a local Taskrail
  identity or path in commit metadata; planning-derived policy cannot
  launder that authority across runs. Outcome-required product bytes may mention or
  implement Taskrail requirements. This
  is output minimization, not a confidentiality claim.
- Skills never invoke `local promote` or expose ignored local skills without an
  explicit human request. Installation, refresh, semantic promotion, and skill
  promotion remain separate operator choices.
- Deterministic contract tests exercise every packaged skill against committed and
  local fixtures, use decoy logical paths to detect direct filesystem access, and
  preserve provider independence, source-checkout freshness guards, package
  parity, and Agent Skills conformance.

### Uniform Agent Machine Results

Make `--json` one stable agent API instead of a collection of command-specific
success structs plus human-only failures.

Requirements:

- `specs/contracts/v0.5.0-machine-api.md` is the co-normative complete
  command-by-command inventory for envelope schema version 1. This feature spec
  owns behavior and invariants; the companion owns exact JSON fields, nested
  shapes, nullability, ordering, warning variants, command/error subsets, and
  report-result exit exceptions. Implementation structs and generated JSON Schema
  files are never independent authorities.
- Every public command that supports `--json` emits exactly one schema-versioned JSON document with exact top-level fields `schema_version:1`, `command`, non-null `warnings`, and exactly one of `result` or `error`. Empty arrays are `[]`, never `null`; diagnostics never contaminate stdout. Command-local warning fields disappear; every warning is present only in the envelope array.
- `start`, `complete`, `block`, task-loop policy mutators, task release, and every review publisher gain `--json`. Their text behavior remains human-oriented. Existing structured commands move to the common envelope as one documented v0.5 compatibility break; no hidden legacy-output switch is added.
- Start result fields are exactly `task_id`, `status:"in_progress"`, `updated_at`, and `validation`; complete fields are exactly `task_id`, `status:"completed"`, `updated_at`, `completion_id`, and `validation`; block fields are exactly `task_id`, `status:"blocked"`, `reason`, `updated_at`, and `validation`. Each validation object is exactly boolean `valid` and non-null ordered common violations. These writers use only applicable common lifecycle/write error codes and common details.
- An envelope contains `result` when the selected command completed its specified operation. A completed read-only report may exit non-zero only where its command contract explicitly makes reported findings gating: inherited invalid `validate`, inherited `coverage --min`, inherited `coverage --gaps --fail-on`, `task loop list` with non-empty `violations`, and `loop --dry-run` with `action:"invalid"`. They remain `result` envelopes. Every writer refusal and every inability to produce the promised report is an `error` envelope. Warnings never change exit status.
- `error` always has stable `code`, `message`, and exact version-specific `details`. Human and JSON modes have identical exit classification. Once a command is selected, argument, preflight, conflict, validation, partial-write, rollback, and recovery failures use the envelope rather than falling back to prose-only stderr.
- `command` is the selected command's canonical path after `taskrail`, with command tokens joined by one ASCII space and aliases normalized. It contains no executable name, flags, `--`, or operands; examples are `task loop list` and `loop`.
- The closed v0.5 error-code registry is `invalid_arguments`, `not_initialized`, `incompatible_layout`, `migration_in_progress`, `repository_invalid`, `validation_failed`, `task_not_found`, `review_not_found`, `invalid_status`, `invalid_reason`, `invalid_digest`, `source_changed`, `invalid_proposal`, `destination_exists`, `path_blocked`, `git_state`, `lock_held`, `delegated_write_refused`, `prompt_not_found`, `prompt_invalid`, `policy_invalid`, `dependency_exists`, `dependency_absent`, `dependency_cycle`, `cancelled_dependency`, `write_conflict`, `recovery_pending`, `partial_write`, `rollback_failed`, `unsupported`, `result_file_publish_failed`, plus the loop postflight codes `blocked_fail`, `rework_fail`, `completed_unverified`, `completed_audit_fail`, `child_failed`, `no_progress`, `invalid_postflight`, `batch_partial`, `batch_failed`, `integration_failed`, and `adapter_failed`. Commands select the narrow applicable code; no command-specific free-form code is permitted.
- Every error `details` object has exactly boolean `applied`, non-null ordered `violations`, non-null ordered `paths`, non-null ordered `snapshots`, and nullable `recovery`. A violation has exactly `code`, `message`, and nullable `path`; a snapshot has exactly `path_kind` (`managed|worktree|git`), `path`, plus nullable lower-case `original_sha256`, `candidate_sha256`, and `current_sha256`. Managed paths are logical semantic paths, worktree paths include skill and local runtime destinations, and Git paths are canonical absolute paths for effective Git metadata such as the resolved exclusion store. Recovery has exactly `transaction_id`, `command`, and `phase`. Unused arrays are `[]`, and commands put subject-specific facts in violations rather than adding ad hoc detail fields. The loop result-file exception uses its exact diagnostic object as details instead, as specified below.
- Warnings are a closed discriminated union. `unknown_skill_version` and `skill_version_skew` have exactly `code,message`; `empty_derived_slug` has exactly `code,message,task_id`; `selected_off_spec`, `selected_non_active_spec`, and `skipped_non_active_spec` have exactly `code,message,task_id,spec_ref,active_spec_path`; `local_initialized` has exactly `code,message,storage_mode:"local",storage_root:".taskrail/local"`; `local_head_drift` has exactly `code,message`, nullable `origin_branch`, `origin_head`, `current_branch`, and `current_head`; and `verify_pass_before_complete` has the exact fields specified below. Later versions add warning variants explicitly; no free-form warning shape is allowed.
- Skills invoke `--json` whenever they consume IDs, paths, warnings, eligibility, diffs, previews, lifecycle outcomes, or failure details. Commands whose product is content for a human or external agent, such as prompt text and emitted prompt bodies, may intentionally use exact text.
- Init result fields are exactly `outcome` (`created|adopted|current|migration_preview|migrated|retrofit_preview|retrofit_applied`), `from_version`, `to_version`, boolean `applied`, `storage_mode`, `config`, non-null ordered `writes`, non-null ordered `notes`, non-null ordered `skills`, non-null ordered `skill_exclusions`, non-null `continuation_notes`, and nullable `validation`. Config is exactly `path`, `action` (`create|preserve|migrate`), and `candidate_sha256`; each write is `path`, `kind` (`config|spec|state|task|note|skill|review|runtime`), and `action` (`create|preserve|refresh|remove`). Each note is exactly `path`, `file_action` (`create_template|preserve|none`), nullable `continuation_action`, and non-null `continuation_choices`; choices contain applicable `extract|drop` values in that order, preview uses null action when operator selection is required, and apply records the selection. Each skill is one installed file with `path` and `action` (`create|preserve|refresh`); each skill exclusion is one packaged-skill destination subtree in each supported assistant root with `path` and `action` (`create|preserve`). A skill refusal is an error envelope, never a successful `refuse` action. Continuation notes are decoded strings. Validation uses the exact common shape. Preview and apply expose the same candidate paths and choices; absent prior layout uses `from_version:0`.
- Status JSON additionally reports exact `storage` with `mode`
  (`committed|local`), repository-root-relative `root` (`.` for committed and
  `.taskrail/local` for local), and repository-root-relative physical `artifacts_dir`
  resolved from the active storage context, so skills can select delivery behavior
  and transient staging without opening the layout marker or reconstructing a
  configured path. The reported directory designates transient storage and is
  never a durable citation or publication destination. In a Git repository each
  producer/publisher must prove its selected path effectively ignored, untracked,
  and unstaged before use; outside Git it is transient without an ignore claim.
  Init returns `skills:[]`
  and `skill_exclusions:[]` when `--with-skills` is absent. An ordinary committed
  install also returns `skill_exclusions:[]`; a local install or refresh reports
  every packaged file destination and one exact skill-subtree exclusion in each
  supported assistant root, in deterministic path order. A committed
  pending-skill refresh preserves and reports its existing managed exclusions;
  only `local promote --with-skills` removes them. Local skill paths remain their
  normal repository-relative assistant discovery paths and never gain a
  local-overlay prefix.
- `taskrail loop` execution keeps child stdout/stderr streaming and therefore does not put its final envelope on stdout. When `--result-file <path>` is supplied, it atomically creates one no-clobber common-envelope document containing the final outcome and all postflight diagnostics. Dry-run continues using ordinary `--json`.
- `schema_version` versions the complete machine document, including every
  inherited result, warning, error detail, enum, nullability rule, and semantic
  interpretation, not only the outer member names. v0.5 emits version 1 for every
  command and loop result file. Any later incompatible change to an inherited
  shape increments the one outer version for every command emitted by that
  release. New command paths may join an existing generation only when they do not
  alter an inherited document. Strict golden decoders reject unsupported versions
  and unknown or missing fields within a supported version.

### Workflow Prompt Catalog And Overrides

Add a read-only `taskrail prompt` command family backed by prompts embedded in the
binary separately from the packaged skill tree.

Command surface:

```text
taskrail prompt list [--json]

taskrail prompt render <prompt-id> [--contract <version>] [--task <id>] [--spec <version-or-path>] [--spec-review <path>] [--draft <path>] [--trace <path>] [--memory <path>] [--review <path>] [--max-review-rounds <n>] [--json]
```

The initial prompt contract is version `v1` and contains these stable IDs:

- `task-implementation`
- `task-authoring`
- `task-review`
- `spec-consistency`
- `spec-gaps`
- `spec-additions`
- `spec-adversarial`
- `task-decomposition`
- `task-decomposition-adversarial`
- `workflow-adversarial`
- `loop-integration`

Resolution requirements:

- Built-ins have deterministic registry order; `prompt list` returns every ID, contract version, and whether a local replacement exists.
- `show`/`render` default to the newest contract supported for that ID; `--contract v1` selects exactly one retained version and its `.taskrail/prompts/v1/` override. Unknown ID/version pairs fail. Adding v2 never changes, migrates, or shadows explicit v1 resolution; list reports every supported pair.
- A repository may replace a complete built-in only at `.taskrail/prompts/v1/<prompt-id>.md`; there is no merging or composition language. Replacements are UTF-8 without BOM, non-empty, and at most 256 KiB. `prompt show` resolves one by default, `--builtin` returns embedded bytes, and any invalid replacement fails without fallback.
- `prompt render` loads requested context, substitutes only declared placeholders, and rejects unknown or unresolved tokens. A token is exactly `{{NAME}}` with `NAME` matching `[A-Z][A-Z0-9_]*`; validation precedes one non-recursive substitution pass. Other braces are literal, authors avoid literal token-shaped text, and `v1` has no escape or action syntax.
- Exact declarations are: `task-implementation`: `TASK_ID`, `TASK_PATH`, `ACTIVE_SPEC_VERSION`, `ACTIVE_SPEC_PATH`, `IMPLEMENTATION_REVIEW_MAX_ROUNDS`, `STORAGE_MODE`; `task-authoring` and `task-review`: `TASK_ID`, `TASK_PATH`, `SPEC_VERSION`, `SPEC_PATH`, with `task-review` additionally declaring `REVIEW_PATH`; each spec lens: `SPEC_VERSION`, `SPEC_PATH`, `REVIEW_PATH`; `task-decomposition`: `SPEC_VERSION`, `SPEC_PATH`, `SPEC_REVIEW_PATH`, `TRACE_PATH`, `DRAFT_PATH`; `task-decomposition-adversarial`: those five plus `REVIEW_PATH`; `workflow-adversarial`: `SPEC_VERSION`, `SPEC_PATH`, `MEMORY_PATH`, `REVIEW_PATH`. Templates may use a subset; any other token fails.
- `loop-integration` is a built-in-only coordinator template rather than a public
  `prompt render` subject. It declares `INTEGRATION_ROLE`, `TASK_ID`, `TASK_PATH`,
  `SPEC_VERSION`, `SPEC_PATH`, `BASE_HEAD`, `CURRENT_HEAD`, `CANDIDATE_HEAD`,
  `CONFLICT_PATHS`, `WORKER_EVIDENCE_PATH`, and `STORAGE_MODE`. The coordinator
  resolves it through the same versioned registry and local replacement rules,
  freezes its exact template and rendered digests before launching each
  integration child, and supplies only validated coordinator-owned values. For
  the aggregate role, task/candidate/conflict values are empty and the template
  must not declare their tokens. `prompt list` and `prompt show` expose the
  template; direct `prompt render loop-integration` is `invalid_arguments` because
  callers cannot construct its privileged integration context.
- Placeholder values are UTF-8 text and repository-relative paths, never embedded file contents or shell-escaped fragments. Templates provide no conditions, loops, includes, shell interpolation, or environment expansion.
- Every task/spec path placeholder is a canonical repository-relative logical path. In committed mode it also names the physical path; in local mode Taskrail maps it beneath `.taskrail/local/`. A prompt or skill must not assume that opening the logical path directly reaches managed bytes.
- Built-in prompts and packaged skills read a selected task through `taskrail task show <task-id>` and a selected spec through `taskrail spec show <version>`. These commands resolve the active storage context. `TASK_PATH`, `SPEC_PATH`, and `ACTIVE_SPEC_PATH` remain logical paths for identification, citations, reviewed proposals, and durable output; physical overlay prefixes are never rendered.
- `SPEC_REVIEW_PATH` and `MEMORY_PATH` are likewise logical durable-review paths and are read through `review show`. `REVIEW_PATH`, `DRAFT_PATH`, and `TRACE_PATH` identify transient proposal files under the physical `artifacts_dir` reported by status storage context; these output/staging placeholders may contain `.taskrail/local/` in local mode and are never copied into final review JSON. In Git, rendering refuses a selected proposal path unless it is effectively ignored, untracked, and unstaged; outside Git it enforces transient-root containment without claiming ignore state. This is the sole physical-overlay exception in rendered prompt text.
- `task-implementation`/`task-authoring` require `--task`; task-review requires `--task --review`; each spec lens requires `--spec --review`; decomposition requires `--spec --spec-review --trace --draft`; decomposition-adversarial adds `--review`; workflow-adversarial requires `--spec --memory --review`. `--max-review-rounds` is accepted only for `task-implementation`, overrides the repository value for that render, and must be an integer from 1 through 2. Undeclared context flags fail; task-derived prompts derive spec from the task's `spec_ref`.
- `--spec` accepts a version such as `v0.5.0` or its matching versioned Markdown file under the configured specs directory; arbitrary Markdown paths are rejected. `SPEC_VERSION` derives from that filename and `SPEC_PATH` is repository-relative. Task-derived spec context rejects a missing or invalid reference.
- Text output is exact content. `prompt list --json` result has exactly non-null `prompts`; each ordered entry is exactly `id`, `contract_version`, `source` (`builtin|replacement`), and nullable `replacement_path`. `prompt show/render --json` result has exactly `id`, `contract_version`, `source`, nullable `replacement_path`, `content`, lower-case `sha256`, and lower-case `template_sha256`. `sha256` hashes the exact returned content. `template_sha256` hashes the exact resolved template bytes before substitution; it equals `sha256` for `show` and may differ for `render`. Built-ins use null replacement path; empty lists are `[]`.
- A prompt-produced durable review observation records exactly `prompt_id`, `prompt_contract_version`, `prompt_template_sha256`, and `prompt_source` (`builtin|replacement`) immediately after its artifact `schema_version`. The ID and contract are fixed by artifact role, the template digest hashes exact pre-substitution bytes, and source records the effective resolution class even when replacement bytes equal the built-in. This is a publication-time prompt-resolution binding, not proof that an external reviewer received, followed, or was independently instantiated from that prompt. Durable artifacts never record a replacement path or rendered-prompt digest.
- Prompt commands are read-only and never create prompt, memory, or review files. Neither init mode materializes built-ins or placeholders.

Untrusted proposal bundles are staged only beneath `<artifacts-dir>/review-proposals/<type>/<proposal-id>/`; they are ignored transient inputs, never final review evidence, and the publisher neither commits nor treats them as lifecycle artifacts. Final and proposal paths reject managed state, task, spec, source, prompt, Git, and other artifact locations. Canonical paths traverse no symlink/reparse point and siblings cannot alias. Prompt rendering validates the requested proposal path only; immediately before publication the publisher rechecks every proposal and destination ancestor no-follow and fails on substitution. Adversarial decomposition consumes regular files from one proposal bundle.
- Incompatible placeholders, required context, or output meaning require a new contract directory such as `v2`; wording may update `v1`, and a local `v1` file continues replacing it until changed or removed.

### Task Implementation Prompt

The built-in `task-implementation` prompt captures the useful, portable parts of
an unattended implementation workflow without importing repository-specific
test, branch, remote, or provider policy.

Required workflow:

1. Understand the task, domain purpose, user-visible behavior, and affected
   invariants.
2. Before editing, check the task against the outcome-focused sizing rubric and
   confirm that dependencies, decisions, acceptance, and planned evidence make
   it ready to execute. If it contains separable outcomes or cannot reach a
   verified result without unresolved scope, stop for reviewed decomposition or
   clarification rather than implementing an arbitrary slice.
3. Implement the smallest safe change with a failing test first whenever
   practical.
4. Run relevant local tests and checks.
5. Inspect the verified implementation for unnecessary complexity and simplify
   where useful while preserving behavior. Independent simplification delegation
   is optional rather than mandatory; rerun affected checks after any change.
6. Freeze the verified implementation and run one broad implementation-review
   round with one fresh reviewer by default. Choose an explicit lens from the
   task's actual behavior, testing, security, error-handling, edge-case,
   complexity, and domain risks. Use a second or third concurrent reviewer only
   for a distinct independently relevant risk that the first lens is unlikely to
   cover; every reviewer inspects the same frozen snapshot.
7. Classify every finding as `fix-now`, `separate-followup`, `blocked`, or
   `rejected`, with a rationale. Repair every current-scope finding regardless of
   severity. For a test-strength finding, demonstrate that the strengthened test
   detects a deliberate regression before restoring the implementation.
8. After fixing review findings, rerun every affected deterministic check. Do not
   start another broad review merely because implementation or test bytes changed.
   If the effective maximum is two, use a second broad round only when the first
   exposes a distinct unresolved risk that deterministic verification does not
   adequately cover, or repository or task context independently warrants it.
   Freeze the verified repaired candidate before that optional round. Broad review
   never exceeds the effective maximum or two rounds.
9. If review fixes materially change product or test bytes, run one narrow
   final-diff review over exactly the review-induced change. This review checks
   only fix-induced regressions, integration breakage, and behavior drift; it
   never starts another broad round.
10. Record only genuinely separate follow-ups, perform the canonical lifecycle
   branch, and report auditable evidence.

Additional requirements:

- Parent-context self-review does not satisfy independent review, which precedes
  `complete` and passing verification. Use a distinct subagent or fresh context
  when supported; Taskrail does not certify reviewer identity. Simplification may
  be performed by the implementing agent and is not a second independent-review
  obligation.
- One broad review round is one completed group of one to three distinct reviewer
  invocations over the same frozen implementation snapshot. Every reviewer has a
  named, non-duplicative lens and explicit finding dispositions. Use another
  reviewer only when its lens is independently relevant to the task's risk; one
  reviewer is still required. Simplification, self-review, checks, fixes,
  manual-test steps, the narrow final-diff review, and `verify` do not consume the
  broad-round budget. Missing repository policy defaults to `1`; repository and
  per-run values must be integers from `1` through `2` and never clamp.
- One broad round is the normal workflow and the configured value is a maximum,
  not a target. Fixing a finding does not itself justify another broad round.
  After every repair, rerun affected deterministic checks. A clean final-diff
  review permits closure and never recursively triggers broad review. If the
  final-diff review reports a current-scope finding, repair it and rerun affected
  checks. Completion is allowed without another model review when objective
  evidence directly demonstrates closure, such as a regression test, build,
  static check, or deterministic integration or manual reproduction. If adequate
  objective evidence is unavailable, keep the task `in_progress`, record failing
  verification as `rework-fail`, and stop for operator review. A reviewer crash,
  timeout, or malformed output fails closed rather than retrying invisibly.
- These round/disposition rules are semantic prompt and skill behavior, not
  a new mechanical postflight attestation. Taskrail freezes and renders the
  effective broad-round policy and tests the shipped instructions/observable lifecycle
  outcomes, but does not inspect conversations, certify reviewer identity, or
  infer how many external review contexts actually ran.
- The built-in prompt applies the same Taskrail source-checkout freshness guard as
  the packaged skills immediately before every state writer. Pinning the child to
  the loop executable does not prove that executable matches a source checkout.
- Headless execution never guesses around operator decisions, credentials, production data, billed resources, or live consoles; it blocks and stops.
- In committed-mode loop delivery, perform the selected lifecycle branch first,
  then commit the complete implementation plus generated task/state outcome. In
  local mode, commit only visible product changes while ignored Taskrail metadata
  records the lifecycle and verification outcome. Success, blocked, and rework
  branches persist one reviewable local outcome; Taskrail never commits, pushes,
  or claims remote delivery itself.
- Local delivery follows repository-visible commit, identity, attribution,
  signing, hook, and ref policy. The prompt does not copy ignored Taskrail IDs,
  logical managed paths, verification/review identities, storage details, or
  Taskrail/agent attribution into commit metadata or unrelated product text and
  does not modify Git identity configuration. Repository-visible policy frozen
  before the workflow governs generic Git conventions, but only a caller-owned
  instruction outside managed Taskrail content may authorize exposing a local
  Taskrail identity or path in commit metadata; planning-derived policy
  cannot launder that authority across runs. Outcome-required product bytes may
  mention Taskrail.
  This rule prevents incidental private-planning provenance rather than
  suppressing product requirements.
- Implementation-review findings use only `fix-now`, `separate-followup`,
  `blocked`, and `rejected`; no other disposition is valid. A finding is `fix-now`
  when the current change introduced or exposed it, current acceptance/specification
  requires it, the claimed invariant depends on it, or changed evidence is too
  weak. A `separate-followup` requires a distinct outcome: unrelated pre-existing
  behavior, a future-version/non-goal, or unnecessary broad architecture. A
  `blocked` finding names an operator, credential, or destructive-action boundary
  that prevents safe current-scope work. Budget exhaustion never turns current work
  into a follow-up. Low-value, non-actionable observations are `rejected` with
  rationale. Current acceptance, specification, invariant, or evidence findings
  cannot use that mapping to evade repair. Completed independent audits may create
  follow-ups without reopening delivered history.
- Follow-ups cannot offload unfinished acceptance, evidence, or integration owned
  by the current task. Consolidate related observations into the fewest
  independently meaningful outcomes; reject layer, file, test-only,
  documentation-only, speculative, duplicate, and non-actionable fragments unless
  that fragment is itself the observable outcome. When several follow-ups must
  compose, one names and verifies the integrated result.
- A delegated child creates necessary independently meaningful out-of-scope work only through `verify --create-followup`; there is no numeric cap. Every generated follow-up is named in a fresh selected-task verification report, depends on the selected task through the existing follow-up contract, omits `loop_policy` and `loop_reason`, and is therefore implicitly held. The prompt applies the shared sizing rubric; Taskrail enforces provenance and policy but does not semantically judge necessity or size.
- Before proposing a new abstraction, the prompt inventories relevant existing repository primitives and records why extension or reuse is insufficient. Material ambiguity about intended behavior, destructive scope, credentials, or operator policy stops for clarification instead of becoming an invented requirement.
- Requirements are traced to observable acceptance and the cheapest executable or inspectable evidence. Model completion language, self-reported confidence, and a bare test-suite pass never replace repository lifecycle and verification postconditions.

### Outcome-Focused Task Authoring

Ship a built-in `task-authoring` prompt and use this shared body contract for
scaffolded, imported, follow-up, and decomposition-generated tasks. The prompt
command remains read-only; an external agent writes a body proposal, then the
reviewed writer applies it safely:

```text
taskrail task author <task-id> --body <proposal> --expect-sha256 <task-digest> [--dry-run] [--json]
```

Requirements:

- A task states one independently meaningful user, operator, or system outcome and the invariant established, rather than a repository layer or list of files to edit.
- A task is right-sized when one agent can pursue that outcome as one coherent
  implementation, review, and verification unit: its acceptance has a bounded
  observable result, its dependencies and operator gates are explicit, and it
  does not hide another independently valuable outcome.
- **Split test:** split when parts deliver independently useful outcomes with
  separate acceptance or oracles, require materially different dependencies or
  operator decisions, or one part can be completed and verified while another
  remains legitimately deferred. Each resulting task must still establish a
  meaningful outcome, and one task must own any required integrated behavior.
- **Do-not-split test:** keep work together when its code, tests, documentation,
  migration, or cross-layer changes only establish value as one observable
  result. Never split by file, component, implementation phase, discipline, or an
  arbitrary estimate, and do not create coordination-only fragments whose sole
  acceptance is that another task exists or passes.
- Authoring is pre-execution work: the prompt rejects a selected task unless its status is `todo`, so completed and cancelled history cannot be rewritten through this flow.
- Acceptance criteria are observable and name relevant actors, preconditions, state, success, failure, and boundary outcomes where they materially differ.
- `## Verification Notes` maps each criterion to setup, input or action, expected observation, and the cheapest sufficient evidence layer: unit, boundary integration, CLI/workflow, manual, or operator evidence.
- Use a public or durable boundary as the oracle. Mocks, call counts, file existence, process exit, or “the suite passes” are insufficient when the criterion concerns persisted or user-visible meaning.
- Bug fixes and high-risk behavior identify regression-sensitive evidence; when practical, a new or strengthened test is shown to fail against the prior defect or a deliberate relevant perturbation before the implementation is restored.
- Manual probes are reproducible and sandbox-first, name prerequisites and cleanup, and distinguish expected behavior from observed evidence. Non-code tasks name an equivalent inspectable check or explain why a test category is not applicable.
- Address recovery, idempotency, concurrency, security, migration, compatibility, and cleanup only when the outcome or spec makes them relevant; do not add checklist-driven scope.
- Avoid vague instructions such as “add tests” or “verify it works,” but also avoid exact functions, test filenames, mocks, or internal structure unless the public contract or known regression requires them.
- Cross-task workflows place an end-to-end criterion on a task capable of proving integrated delivery; dependency edges alone are not verification.
- `task new` scaffolding asks for planned criterion-to-evidence mapping plus later evidence paths. Task-producing built-ins and skills cite this contract, and the decomposition adversary rejects both shallow and unnecessarily implementation-bound verification notes.
- `task new`, imported tasks, decomposition-generated tasks, and verification or implementation follow-ups omit `loop_policy` and `loop_reason`; reviewed task creation never silently opts work into unattended execution.
- Sizing is semantic reviewer and agent judgement. Taskrail may validate the
  existing body shape, references, dependencies, and review bindings, but
  mechanical completeness does not certify that a task is right-sized.
- `task author` acquires the repository writer lock, rechecks exact task bytes/digest and `todo`, validates the proposal, and atomically changes only Description, Acceptance, and Verification Notes while preserving frontmatter, H1, and Implementation Notes. It re-validates and reports a selected-task-only diff; conflict or failure writes nothing.
- The author proposal is UTF-8 Markdown without BOM, frontmatter, H1, or `## Implementation Notes`. It contains exactly one non-empty `## Description`, `## Acceptance`, and `## Verification Notes` in that order and no other level-2 heading; lower headings are permitted within a section. The writer preserves the decoded proposal section bytes exactly beneath the existing H1 and preserves the existing Implementation Notes bytes exactly.
- Author result fields are exactly `task_id`, `task_path`, `task_sha256_before`, `task_sha256_after`, boolean `applied`, string `diff`, and `validation` with boolean `valid` plus non-null common violations. `diff` is one UTF-8 unified diff with repository-relative logical path headers, LF line endings, and no color or timestamps. Dry-run and apply return the same candidate digest/diff. Delegated loop children refuse before reading a proposal or task. Errors use `invalid_arguments`, `not_initialized`, `incompatible_layout`, `migration_in_progress`, `task_not_found`, `invalid_status`, `invalid_digest`, `invalid_proposal`, `lock_held`, `delegated_write_refused`, `write_conflict`, `recovery_pending`, `partial_write`, or `rollback_failed` with common details.

### Existing-Task Review

Ship one built-in `task-review` prompt and one packaged `taskrail-task-review`
skill for advisory review of an already tracked task. Do not mirror every spec
lens into a second overlapping task-lens family.

Requirements:

- Review one explicitly resolved task and its referenced spec area, relevant existing tasks, dependencies, and repository contracts. Check outcome focus, spec alignment, overlap, dependency direction, observable acceptance, negative and boundary behavior, criterion-to-evidence mapping, public or durable oracles, operator gates, unnecessary implementation prescription, and the shared sizing rubric. State whether the split and do-not-split tests support the current boundary; recommend a concrete split or consolidation when they do not, including which task owns integrated delivery.
- The review stages exactly one `review.json` proposal and publishes it to the absent directory `<planning-dir>/reviews/task/<task-id>/<session-id>/`. Its exact schema-v1 fields are `schema_version` (integer `1`), the four prompt-resolution binding fields, `session_id`, `task_id`, `task_path`, `task_sha256`, `spec_path`, `spec_sha256`, `context_mode`, `generated_at`, and non-null `findings`. Its prompt ID is exactly `task-review` and contract version is exactly `v1`. The publisher resolves the exact full task ID, derives its referenced spec, and requires both current raw-file SHA-256 values to equal the proposal and command bindings. `session_id` is a portable review key equal to the destination basename; `context_mode` is `fresh|same-context`; and `generated_at` is canonical RFC3339 UTC.
- A task-review finding has exactly `finding_id`, `severity`, `evidence`, `impact`, `recommendation`, `disposition`, and `rationale`. Severity is `high|medium|low`; disposition is `open|accepted|rejected|deferred`; IDs are unique within the session; and all textual fields are non-empty. Publication records the reviewed snapshot. A later `task author` change does not retroactively update that review. Final authored bytes require another review only when an explicitly invoked consuming workflow or the human requires it; unchanged bytes and confidence-seeking alone never trigger another session.
- Findings are advisory. Accepted body changes flow through `task author`; dependency changes use explicit dependency commands; newly discovered outcomes use reviewed task creation. The reviewer never changes status, task-local loop policy, specs, dependencies, or task bodies directly.
- A `todo` task may be reviewed and then authored. Other statuses may be inspected but are not rewritten through task authoring. Completed and cancelled history remains read-only; follow-up work is created separately.
- This review is distinct from semantic post-spec lenses, mechanical `coverage --gaps`, unpublished task-set decomposition review, implementation review, and verification. Documentation names each stage rather than calling all of them gap analysis.

taskrail review publish --type spec --proposal <dir> --destination <dir> --spec <version-or-path> --expect-spec-sha256 <digest> [--dry-run] [--json]

- Delegated loop children refuse every review publication type before reading a proposal or durable review subject with `delegated_write_refused` and common error details.
- For task, spec, and decomposition publication, the publisher preserves each proposal file's exact bytes and basename beneath one absent destination directory. Bundle-internal manifest paths are fixed basenames relative to that directory, never staging paths. The spec and decomposition manifests are the sole authorities for membership, role, order, and digest; directory enumeration is never an alternate manifest. Workflow publication writes `report.json` byte-for-byte and Taskrail mechanically derives canonical candidate `INDEX.json` bytes from the prior strict index plus that report.
- All schemas introduced by this version are normatively owned by this specification and by each consuming command's one shared strict decoder. Prompts, skills, examples, implementation structs, and optional generated JSON Schema files are not independent schema authorities. A later version changes meaning only by retaining the old schema explicitly or introducing a new `schema_version`.
- Unless a schema states otherwise, JSON is one UTF-8 object without BOM, duplicate keys, unknown fields, missing required fields, `null`, or trailing values. Arrays are non-null. Digests are lower-case 64-hex SHA-256 over exact raw file bytes. Paths are canonical slash-separated repository-relative paths. Times are canonical RFC3339 UTC. A portable review key is 1 through 128 ASCII bytes matching `^[a-z0-9]+(?:-[a-z0-9]+)*$`.
- Prompt-producing artifact roles map exactly to `task-review` for task review, `spec-consistency`, `spec-gaps`, `spec-additions`, and `spec-adversarial` for their corresponding lens files, `task-decomposition-adversarial` for each decomposition review pass, and `workflow-adversarial` for a workflow report. Manifests, draft/trace files, and the workflow index are digest-bound aggregates or inputs and do not duplicate prompt resolution.
- Preview snapshots and performs every decode, path, digest, identity, cap, referential-integrity, derived-index, prompt-resolution, and destination check without writes. For every prompt-produced observation, it resolves the artifact's explicit role-mandated ID and contract through active storage and requires exact source and template-digest agreement. Apply acquires the common writer lock, rechecks the complete proposal, subject, exact raw configuration-file bytes, and resolved prompt-template snapshots, stages the complete candidate beside its final destination, validates it, and rechecks those identities immediately before the task/spec/decomposition directory commit or workflow recovery fence. It then publishes one complete type-specific logical write set. Configuration-byte drift is `write_conflict`; prompt-resolution failures retain the more specific precedence below. Task/spec/decomposition failure leaves no final directory; workflow interruption may leave fenced recovery bytes handled only by the shared recovery protocol.

### Post-Spec Review Lenses

- **Consistency (`spec-consistency`)**: find contradictions among summary, goals,

  while missing the product intent.

Text and graph comments derive their details and counts from the same ordered issue list.

- `stats --active-spec` fails before output when active version/path is incoherent. Cancelled tasks remain in status totals but excluded from dependency metrics, preserving unfiltered semantics.
- This flag is reporting only. Do not add it to status, coverage/gaps, next, validate/repair, explicit task writers, spec/import/prompt commands, or loop. Those surfaces already have active, global, or explicit-subject semantics that filtering would weaken or duplicate.

### Task-Local Loop Policy

Optional paired fields in each task's existing YAML frontmatter express whether
that task may be selected for unattended execution:

```yaml
loop_policy: allow
loop_reason: "bounded change with deterministic tests"
```

The pair is task-local metadata, not lifecycle status. There is no ordered queue,
global barrier, separate policy file, or second database.

Schema and validation requirements:

- `loop_policy` and `loop_reason` are both present or both absent. `loop_policy` is exactly lower-case `allow` or `hold`. Absence of both fields has effective policy `hold`, source `default`, and deterministic report reason `implicit hold: loop policy is not set`.
- An explicit `loop_reason` is trimmed UTF-8 of 1 through 512 bytes, contains no newline or control character, and passes the existing portable-note guard that rejects concrete gitignored artifact paths. Validation applies the same grammar to persisted reasons; YAML scalar spelling cannot bypass the decoded-value contract.
- Task files remain the sole source of status, priority, dependencies, spec linkage, and loop policy. `STATE.md` does not duplicate the pair, and policy does not add a lifecycle state, dependency edge, ordering key, or provenance record.
- Explicit metadata remains valid on any status so delivered history retains the decision that governed it. Lifecycle transitions, verification, rename, repoint, spec activation, and other task writers preserve both fields exactly and do not reinterpret them.
- `taskrail validate` rejects an incomplete pair, unknown policy, invalid reason, duplicate YAML key, or policy fields outside task frontmatter. It does not require explicit metadata and does not require allowed tasks to belong to the active spec; active-spec scope is a loop selection rule.

Command surface:

```text
taskrail task loop list [--json]
taskrail task loop allow <task-id> --reason <reason> [--dry-run] [--json]
taskrail task loop hold <task-id> --reason <reason> [--dry-run] [--json]
taskrail task loop clear <task-id> [--dry-run] [--json]
```

Mutation requirements:

- `allow` and `hold` atomically set the complete pair; `clear` atomically removes both fields and restores implicit hold. They use exact full task-ID lookup, reject an unknown ID, acquire the repository writer lock, recheck exact task bytes, update the task timestamp, re-project `STATE.md`, and validate before publishing all-or-none.
- Policy mutation is allowed only while the target is `todo` or `blocked`. All three mutators refuse `in_progress`, `completed`, and `cancelled` tasks without writing. An operator decides policy before unattended start or while explicitly reconsidering blocked work; historical metadata is not rewritten through this command family.
- Dry-run reports old, effective, and candidate policy/reason plus candidate validation without writing. JSON uses the uniform agent result envelope. In an initialized repository, apply and dry-run classify the same semantic refusal identically; in an uninitialized worktree, dry-run returns `not_initialized` while apply may perform the separately disclosed implicit-local bootstrap before semantic classification.
- Loop-mutator result fields are exactly `task_id`, `operation` (`allow|hold|clear`), boolean `applied`, `prior`, `candidate`, and `validation`. Prior and candidate each have exactly `source` (`explicit|default`), `effective_policy` (`allow|hold`), `reason`, nullable `persisted_policy`, and nullable `persisted_reason`; default source uses null persisted values and the deterministic implicit-hold reason. Validation is exactly boolean `valid` plus non-null common violations. Dry-run and apply return the same candidate; mutator errors use applicable common task/policy/write codes and details.
- `task new`, import v1/v2, decomposition, `verify --create-followup`, and every other generated follow-up omit both fields. Their effective policy is implicit hold even when the parent was allowed.
- A writer delegated by `taskrail loop` cannot invoke any `task loop` mutator. It also cannot create an explicitly allowed follow-up through another writer or imported draft; delegated task creation accepts no loop-policy input and always emits the absent pair.
- Ordinary `status`, `next`, lifecycle, verification, manual task selection, dependency validation, and spec activation ignore effective loop policy. In particular, a human may start or unblock an implicitly or explicitly held task, and held tasks do not alter ordinary deterministic `next` results.

List and selection requirements:

- `task loop list` is read-only and reports every task in canonical full-task-ID order. Each row has exact fields `task_id` (string), `status` (string), `active_spec` (boolean), `source` (`explicit|default`), `effective_policy` (`allow|hold`), `reason` (string), `eligible` (boolean), non-null canonically ordered `held_dependencies` (full-task-ID strings), and `disposition` (`eligible|held|held_dependency|status_ineligible|off_spec|waiting_dependency|invalid`). Default rows use the deterministic implicit-hold reason above; explicit rows use `loop_reason` verbatim after decoding. `held_dependencies` contains every unresolved effectively held task in that row's transitive dependency closure and is `[]` when none.
- Disposition uses this first-match precedence for files whose required identity fields can be decoded: invalid task, effective hold that blocks at least one live active-spec allowed task, other effective hold, non-`todo` allowed task, allowed off-spec task, allowed task with any unresolved dependency, then eligible. Thus `eligible` is true exactly for disposition `eligible`; `held_dependency` identifies the held task itself, while each affected dependent names it in `held_dependencies` and has `waiting_dependency`.
- `list --json` uses the uniform agent envelope; its exact `result` has non-null `tasks` and non-null common violation objects. Text renders the same fields and never reports a policy-file path. Wholly undecodable task files produce ordered path-bearing violations and no invented row; decodable invalid tasks produce an `invalid` row. An invalid repository that can still be deterministically inspected returns those rows and violations as a completed report result and exits non-zero without writing. Failure to produce that deterministic partial report uses the command's registered error envelope instead.
- Loop candidates are exactly active-spec `todo` tasks with explicit effective policy `allow` and otherwise normal read-only eligibility. Among eligible candidates, use the same priority, dependency, and full-task-ID tie-breaking as ordinary deterministic `status` selection; frontmatter location, policy mutation time, and list order are never ranking inputs.
- A held task is bypassed when selecting unrelated work. An unresolved held task in a candidate's transitive dependency closure appears in that candidate's ordered `held_dependencies` and blocks only that candidate and its dependents; it never creates a repository-wide stop. Other incomplete dependencies retain ordinary eligibility behavior.
- Explicitly allowed tasks that are blocked, off-spec, terminal, already in progress, or waiting on unresolved dependencies are not launched. Their metadata remains inspectable, but selection continues to any independently eligible allowed task. If none exists, loop stops cleanly with action `none` and dispositions explain why.

### Local Planning Mode

Support personal Taskrail use in a Git worktree whose repository has not adopted
or committed Taskrail. The product term is **local mode**; "stealth" is informal
description, not a command or persisted value.

Layout and discovery requirements:

- Explicit setup is `taskrail init --local`. A layout-2 marker records
  `storage_mode: local`; ordinary adopted repositories record
  `storage_mode: committed`. Local specs and planning use fixed physical roots
  `.taskrail/local/specs/` and `.taskrail/local/planning/`; local prompt
  replacements use `.taskrail/local/prompts/`; persisted references retain the
  committed logical namespaces.
- Implicit local bootstrap is available only to these apply/execution writer surfaces: `next`; `start`, `complete`, `block`, `unblock`, and `verify`; `repair --apply`; `task new`, `task rename`, `task repoint`, `task release`, and `task author`; `task loop allow|hold|clear`; `spec add` and `spec activate`; `import --apply`; and executing `loop` without `--dry-run`.
- Implicit bootstrap never installs or refreshes packaged skills and never changes
  an assistant directory or a skill exclusion. Skill materialization requires a
  separately selected `init --with-skills` surface.
- Bootstrap is not performed by `init`, `retrofit`, `local promote`, `review publish`, any preview or `--dry-run` form, `task loop list`, or any other read-only command. Review workflows require prior explicit `init --local` because their untrusted proposal bundle must exist before publication. Those explicit bootstrap and promotion commands retain their own contracts.
- Command selection, arity, required-flag, flag-combination, Git-worktree, and bootstrap-path validation complete before the first bootstrap write. Once those checks pass, bootstrap may remain durable if the requested semantic operation later refuses.
- Successful bootstrap, including a later semantic refusal, emits the common-envelope warning `{"code":"local_initialized","message":<string>,"storage_mode":"local","storage_root":".taskrail/local"}`. No result or error payload gains a command-specific bootstrap field.
- Read-only commands never bootstrap. In an uninitialized repository they fail
  without writes and name `taskrail init --local`; after explicit or implicit
  initialization every command discovers the local marker without another flag.
- Discovery distinguishes worktree root, Git directory/common directory,
  Taskrail storage root, and logical repository paths. Every template, reader,
  writer, prompt, skill, validation rule, artifact guard, and rename operation
  resolves through that context rather than assuming literal `specs/` or
  `planning/` paths.
- Local semantic files retain the committed logical namespace: default
  `active_spec_path`/`spec_ref` values are `specs/...`, task and review paths are
  `planning/...`, and config keeps logical `specs_dir: specs` and
  `planning_dir: planning`. The storage mode maps those logical roots physically
  beneath `.taskrail/local/`; physical overlay prefixes never enter durable task,
  state, spec, note, or final review text.
- Storage mapping occurs inside Taskrail readers and writers. Callers use logical paths and subject commands for managed bytes; they do not prepend `.taskrail/local/` or reconstruct physical semantic paths. External review producers may write only beneath the explicitly reported physical `artifacts_dir`, which is ignored transient staging rather than managed semantic storage.
- Git-visible local delivery contains only outcome-required product content.
  Built-in prompts and packaged skills do not incidentally expose ignored task,
  spec, review, verification, or storage provenance through committed files,
  commit messages/trailers, synthesized identity or attribution, or workflow-
  created refs. Repository-visible policy captured in the preflight snapshot
  governs generic Git conventions, but only a caller-owned instruction supplied
  outside managed Taskrail content may authorize exposing a local Taskrail
  identity or path in commit metadata; ignored planning text and policy
  derived from it cannot launder that authority across runs. Product bytes may
  embody or name Taskrail requirements when required by the outcome. Local mode
  isolates storage and minimizes
  incidental output; it does not make planning input confidential or forbid exact
  logical identities in Taskrail results, rendered prompts, ignored evidence, or
  external result files where their contracts require them.
- Local initialization writes ignored operational origin metadata at
  `.taskrail/local/runtime/origin.json`. Its strict schema has
  `schema_version:1`, canonical `worktree_root`, `git_common_dir`, nullable
  `branch`, nullable `head`, and `initialized_at`. It is not semantic planning,
  never appears in prompts or final reviews, and is excluded from promotion.
- The logical replacement `.taskrail/prompts/v1/<prompt-id>.md` maps physically
  to `.taskrail/local/prompts/v1/<prompt-id>.md` in local mode. Prompt commands
  report only the logical path. A committed replacement at the same logical path
  while local mode is active is mixed state and refuses rather than being merged
  or silently preferred.
- Local initialization writes a uniquely marked block to the effective
  `.git/info/exclude` resolved by Git, then proves every managed local path is
  untracked, unstaged, and effectively ignored before writing content. It never
  edits committed `.gitignore`. Existing tracked/staged content, a conflicting
  `.taskrail` entry, aliases, symlink/reparse traversal, special files, or mixed
  committed/local Taskrail state refuses without changing either location.
- Linked worktrees share exclusion and lock state where Git does. Diagnostics
  identify that scope. Branch or HEAD drift from the origin record emits the exact
  non-gating `local_head_drift` warning and does not by itself prevent ordinary
  work or promotion; it warns that personal planning may describe different
  source history. Documentation warns that `git clean -x`/`-X` can delete ignored
  local state.
- `init --local` leaves `.agents/` and `.claude/` byte-for-byte unchanged and
  creates no skill exclusion. `init --local --with-skills` remains the only fresh
  local skill-install opt-in; an initialized local repository refreshes through
  explicit `init --with-skills --force` without repeating `--local`.
- Local skills are materialized at the normal discovery destinations
  `.agents/skills/<packaged-skill-name>/...` and
  `.claude/skills/<packaged-skill-name>/...`, never beneath
  `.taskrail/local/`. Taskrail manages one exact exclusion for each owned skill
  subtree and never excludes `.agents/`, `.claude/`, or either shared `skills/`
  directory.
- Before the first exclusion or skill write, installation classifies every
  destination across both roots and checks the index, effective ignore state,
  aliases, case/Unicode collisions, symlink/reparse traversal, special files, and
  linked-worktree consequences. Existing adopter-owned or ambiguous content
  refuses the complete operation. On fresh local setup, scaffold, skill files,
  and exclusions share the durable transaction and recovery boundary.
- Marker-free byte-identical parity mirrors remain marker-free. Valid installed
  copies carry nested version metadata; legacy-only and matching-dual copies
  normalize only on explicit forced refresh. Divergent marker-free files,
  conflicting markers, or destination changes after preflight refuse without a
  partial installation.

Inspection and promotion surface:

```text
taskrail local status [--json]
taskrail local path [--json]
taskrail local promote [--apply] [--with-skills] [--json]
```

- Status and path are read-only. Status reports mode and roots, strict origin and
  current Git snapshots, drift classification, exclusions, promotion readiness,
  and violations using the exact companion schema. Path reports `mode`,
  `config_path`, `storage_root`, logical `specs_dir` and `planning_dir`, plus
  physical `prompts_dir`, `artifacts_dir`, and `runtime_dir`. Text renders the same
  information without exposing lock or delegation secrets. In local mode the
  `artifacts_dir` returned here is byte-identical to status
  `storage.artifacts_dir` from the same active storage snapshot.
- An exclusion entry is exactly `path`, `source` (`managed|external`), and boolean
  `effective`; a local violation is exactly `code`, `message`, and nullable
  `path`. Ordered path collections use repository-relative strings.
- Promotion defaults to a complete dry run. It validates local source state,
  destination/index/worktree availability, every linked-worktree exclusion
  consequence, and the committed candidate before writes. Mixed state, an
  affected sibling local installation, or any ambiguous destination refuses.
- Apply uses the durable transaction protocol, stages a committed-layout
  candidate in private storage, switches config storage mode while preserving the
  logical path namespace and every task ID/status/timestamp/body, excludes local
  artifacts/runtime/transaction data, and publishes specs/tasks/state/config plus
  durable NOTES/review files and prompt replacements all-or-none. After the
  committed candidate validates, it removes only source semantic/prompt files
  whose exact bytes were published and then their now-unused managed exclusions.
  Local artifacts and runtime bytes remain excluded from the committed candidate
  and stay beneath the local overlay as ignored transient operator data. Their
  narrow managed exclusion remains effective after promotion; it is removed only
  after those bytes are absent through deliberate operator cleanup. Retaining the
  transient bytes and exclusion is a valid stable committed-mode state, not an
  incomplete migration; v0.5 defines no Taskrail cleanup command or automatic
  deletion for operator-owned transient evidence. Promotion reports them as
  preserved exclusions and leaves ordinary Git status clean.
  An interruption or cleanup failure retains a recovery fence; normal commands do
  not observe committed mode together with a live local semantic source.
- Successful promotion leaves committed Taskrail files visible for operator
  review and staging. Taskrail does not commit them. Skill destinations already
  remain at their normal assistant paths: promotion with `--with-skills`
  validates their unchanged bytes and removes only their exact managed
  exclusions, making those existing files commit-visible without copying or
  rewriting them. Without `--with-skills`, skill bytes and exclusions remain
  untouched. Promotion JSON result is exactly boolean `applied`, `source_mode`,
  `target_mode`, non-null ordered `writes`, `preserved`, `excluded`,
  `removed_exclusions`, and `skills`, plus `validation` with boolean `valid` and
  non-null `violations`; preview returns the same candidate fields with
  `applied:false`.
- Each promotion `writes`/`preserved`/`excluded` entry is exactly `path` and
  `kind` (`config|spec|state|task|note|review|prompt|artifact|runtime`);
  `removed_exclusions` contains strings; each skill entry is exactly `path` and
  `action` (`promote|preserve_local|absent`). Local commands use the closed common
  error registry and details: mixed mode is `repository_invalid`, wrong mode or
  an inapplicable operation is `unsupported`, and exclusion collisions are
  `path_blocked`. Unknown/missing fields fail strict decoding, and text/JSON modes
  classify refusals identically.
- Semantic promotion without `--with-skills` leaves one explicit pending-skill
  state: committed storage with valid Taskrail-owned installed skill bytes and
  their exact managed exclusions. This is the sole committed-mode state in which
  `local promote --with-skills` remains applicable. Its preview/apply has
  `source_mode:"committed"`, `target_mode:"committed"`, empty semantic entry
  arrays, and only skill/exclusion candidates; omitting `--with-skills` or having
  no pending managed skill exclusion is `unsupported`. Once applied, ordinary
  committed-mode rules resume.
- A promotion skill action names the selected candidate independently of apply:
  with `applied:false`, `promote` means the exclusion would be removed after all
  checks; with `applied:true`, it was removed. Preview never claims a completed
  visibility change.

Local mode changes storage and delivery, not task, spec, verification, selection,
or review semantics. Commands that cannot uphold both modes must refuse with a
capability reason rather than silently fall back to committed paths.

### Layout Compatibility And Upgrade

Task-local loop metadata changes unattended selection, so an older binary must
not silently ignore it.

Requirements:

- `v0.5.0` raises layout to `2`. Its final strict marker contains exactly `layout_version`, `specs_dir`, `planning_dir`, `storage_mode`, and `implementation_review_max_rounds`. Storage mode is `committed|local`; broad review maximum is an integer from 1 through 2. Missing review policy resolves to `1` only while constructing a migration candidate, and successful fresh or upgraded output writes it explicitly. Unknown fields and invalid values fail instead of being dropped. Existing repositories migrate as committed; no loop metadata or prompt override is created.
- Layout migration uses `.taskrail/config.yml` itself as the old-binary fence; it creates no second compatibility marker. After acquiring the writer lock and durably recording originals beneath `<git-common-dir>/taskrail/transactions/<transaction-id>/`, but before changing any task, state, note, or skill byte, apply atomically replaces the old marker with this temporary shape:

  ```yaml
  layout_version: 2
  specs_dir: "<canonical logical specs directory>"
  planning_dir: "<canonical logical planning directory>"
  storage_mode: committed
  implementation_review_max_rounds: 1
  migration_fence:
    from_layout_version: 1
    transaction_id: "<random lower-case 32-hex>"
  ```

- `migration_fence` is accepted only in that exact shape by the migration reader. Every other command refuses it as `migration_in_progress`; a layout-1 binary sees layout 2 and refuses before writing. After durable fence publication, apply rechecks every source snapshot, publishes the candidate write set, and post-validates it. Its final operation atomically replaces the fenced marker with the strict final marker, omitting `migration_fence`.
- On ordinary failure, rollback restores candidate-written files first and the original marker last, each only when current bytes still match this transaction's candidate. An interruption leaves the fence and recovery directory in place for explicit shared `recover`; every other command refuses `recovery_pending`. Fence and final-marker publication are each atomic sequential phases of one transaction, not one simultaneous replacement. Already-running old processes cannot honor the lock, which is why apply requires explicit quiescence confirmation.
- Layout 2 raises `STATE.md` to state schema 2 and removes both the
  `continuation_notes` frontmatter field and the rendered `## Notes` section.
  State is a bounded current snapshot, not a per-task/session narrative or
  persistent event log. Task-specific context belongs in task `## Implementation
  Notes`, blocker reasons, portable verification summaries/reports, or follow-up
  tasks. Fresh layout-2 initialization writes schema 2 directly and never seeds
  bootstrap continuation prose. Repository-wide human context may instead live
  in human-owned `<planning-dir>/NOTES.md`; it is not parsed into state or task
  lifecycle data.
- State schema 2 retains schema 1's exact `updated_at`, `active_spec_version`, `active_spec_path`, `current_task`, `current_task_title`, `status_summary`, non-null `blockers`, `next_action`, `last_verification_result`, and non-null `relevant_artifacts`; changes `schema_version` to integer `2`; removes `continuation_notes`; and adds optional `last_verification_id`, optional `last_verification_previous_id`, and optional `last_verified_completion_id`. No other frontmatter key is accepted.
- `last_verification_result` is required and non-empty; fresh state writes `Not yet run`, while schema-1 migration preserves its existing path-free value without inventing an ID. `last_verification_id`, when present, is lower-case 32-hex and the result has canonical form `<pass|fail> for <full-task-id> at <RFC3339-UTC> id <verification-id>`. `last_verified_completion_id` is present only when that same latest verification is a passing completed-task verification bound to the current completion ID. A fail, pass before completion, fresh state, and migrated legacy state omit it.
- Optional verification keys are omitted, never `null` or empty. `last_verification_previous_id`, when present, is lower-case 32-hex and identifies the predecessor recorded by the latest report. A new verification replaces the repository verification tuple and removes a previously present completion binding when the new result is unbound; other state writers preserve the tuple. `relevant_artifacts` remains the required empty portable list.
- Applied fresh init and retrofit create a short commented `<planning-dir>/NOTES.md` template only when that path is absent. Preview reports the candidate; an existing regular file is preserved byte-for-byte, and an alias, symlink/reparse point, or non-regular entry refuses. Default and `--with-skills` modes share this behavior, while preview remains write-free.
- Layout migration uses this command surface in addition to existing init flags:

  ```text
  taskrail init [--apply] [--confirm-quiescent]
                [--extract-continuation-notes | --drop-continuation-notes]
                [--with-skills --force] [--json]
  ```

- Layout-upgrade apply requires `--confirm-quiescent`, the operator's assertion that all older Taskrail processes capable of touching this repository or linked-worktree storage have stopped. It is invalid for fresh init, retrofit, an already-current layout, or preview. Lock and snapshot checks still detect races; the assertion does not make an old process a lock participant.
- Upgrade preview decodes schema 1 explicitly and reports every continuation note and applicable preservation choice. When the decoded list is non-empty, apply requires exactly one of `--extract-continuation-notes` or `--drop-continuation-notes`.
- `--extract-continuation-notes` creates absent `<planning-dir>/NOTES.md` with one clearly labelled imported section, preserving note order and exact decoded text. It never appends to or replaces an existing entry. An existing NOTES file requires manual merge followed by `--drop-continuation-notes`. Empty or absent continuation notes require neither option and reject either as unnecessary; an absent NOTES file receives only the ordinary template.
- Both note options are migration-only and remain accepted for any supported direct or multi-hop upgrade traversing state schema 1. Direct upgrades whose source state is already schema 2 reject both. Schema-2 decoding rejects the removed field rather than letting a later writer erase reintroduced prose. Frontmatter removal, body re-render, note handling, marker publication, and rollback are one transaction.
- Any filesystem entry at the exact configured `<planning-dir>/AUTONOMY.tsv` path is unsupported legacy input: `validate`, `loop`, and layout migration inspect that path without following symlink/reparse traversal and refuse while it exists. Files with the same basename elsewhere are unrelated. The error directs the operator to record the decisions and reasons still intended, remove the legacy entry manually, complete the layout upgrade when needed, then use `taskrail task loop allow|hold <task-id> --reason <reason>` for those tasks and leave all others implicit hold before retrying validation or loop. Taskrail does not parse its contents, infer a translation, or preserve file order.
- Every v0.5 semantic writer (lifecycle/task/spec/import/review publisher and loop execution) requires layout 2 first; layout 1 permits read-only inspection and init migration only, preventing older writers from later erasing v0.5 IDs, v2 references, or loop-policy semantics.
- Once upgraded, older Taskrail binaries refuse the newer layout through the
  existing command-wide compatibility guard instead of ignoring its selection
  policy.
- Migration classifies each Taskrail-owned skill destination before deciding refresh. A marker-free destination byte-identical to the embedded package is a committed parity mirror and remains marker-free; this applies in Taskrail's source checkout and any adopter using the same mirror pattern. Installed stamped, legacy-only, or matching-dual copies require the combined `taskrail init --apply --with-skills --force` and normalize to nested-only version metadata. Divergent marker-free or conflicting-marker copies refuse before any marker/skill change. Repositories without installed copies are not forced to create them, and staged mirrors validate byte parity before marker publication.
- Acceptance covers candidate failure/rollback/interruption, v0.4 layout and skills moving together, older-binary refusal, legacy-file refusal, no preview writes, and preserved task-local loop metadata across refresh. Downgrade is Git reversion of the complete upgrade, never hand-editing the marker.

### Cross-Platform Autonomous Loop

Add a foreground generic process runner:

```text
taskrail loop [--max-iterations <n>] [--max-review-rounds <n>] [--timeout <duration>] [--allow-prompt-override-sha256 <digest>] [--result-file <path>] [--parallel <n>] [--workspace-root <path>] [--clone-depth <n|full>] [--keep-workspaces <never|failure|always>] [--delivery <local|review>] [--review-adapter <path>] -- <command> <args...>
taskrail loop --dry-run [--max-iterations <n>] [--max-review-rounds <n>] [--timeout <duration>] [--allow-prompt-override-sha256 <digest>] [--parallel <n>] [--workspace-root <path>] [--clone-depth <n|full>] [--keep-workspaces <never|failure|always>] [--delivery <local|review>] [--review-adapter <path>] [--json]
```

Execution contract:

- The child command is required for execution and is passed as an argument vector
  directly to the operating system. Taskrail never joins it into a shell string,
  evaluates shell syntax, or names a supported provider.
- A bare executable name resolves through the inherited `PATH`. A path containing
  a separator resolves against the caller's original working directory before the
  child cwd changes to the repository root, then is passed as an absolute path.
- `--max-iterations` is a positive integer and defaults to `1`. There is no
  unlimited value. A caller opts into a longer run explicitly.
- `--parallel` is a positive integer and defaults to `1`. Value `1` preserves the
  inherited sequential loop behavior and rejects clone/delivery-only flags,
  preventing stale parallel intent from being ignored. A value greater than one
  explicitly selects the isolated-clone batch contract below; its effective
  width is capped by `--max-iterations` and the dependency-ready eligible
  frontier, never padded with held or dependency-blocked work.
- `--max-review-rounds` is an optional integer from `1` through `2` and overrides
  `implementation_review_max_rounds` for this invocation. The resolved value is
  frozen across every selected child. It bounds broad implementation-review
  rounds within one child, never reviewers within a round, the one conditional
  final-diff review, child/task count, manual-test retries,
  spec/task/decomposition review, or wall-clock duration. The configured default
  is `1`. Each broad round uses one reviewer by default and no more than three;
  additional reviewers require distinct independently relevant risk lenses.
- `--timeout` is an optional positive Go-style duration applied independently to
  each launched child and frozen for the invocation. Omission means no Taskrail
  wall-clock deadline and preserves foreground operator interruption. Expiry
  terminates the contained process tree, records a timeout process violation, and
  produces `child_failed`; it never permits another task.
- `--dry-run` rejects a child command, performs all read-only repository and task-local loop-policy checks, and supports `--json`. Its completed report has action `run`, `none`, or `invalid`, plus reason, violations, the selected task when action is `run`, and the same per-task entries as `task loop list`; warnings remain the common envelope's top-level array. It includes prompt source, template SHA-256, rendered SHA-256, and rendered content only for `run`; no-work results do not fabricate a selected task or prompt. Valid `run` and `none` reports exit zero. An `invalid` report exits non-zero but remains the report-result exception defined by Uniform Agent Machine Results.
- Dry-run JSON uses the uniform agent envelope. Its exact `result` fields are `action` (`run|none|invalid`), `reason`, nullable `selected_task`, non-null `tasks`, non-null common `violations`, nullable `prompt`, `git`, `lock`, `storage`, `review`, `execution`, and `delivery`. Prompt, when present, has exactly `id`, `source` (`builtin|replacement`), nullable `path`, `template_sha256`, `rendered_sha256`, boolean `override_authorized`, and `content`; built-ins use null path. Git has exactly `head`, nullable `branch`, boolean `clean`, and boolean `detached`. Lock has exactly boolean `available` and nullable string `owner`. Storage has exactly `mode` (`committed|local`) and `root`. Review has exactly integer `configured_max_rounds`, integer `effective_max_rounds`, integer `max_reviewers_per_round` (always `3`), boolean `final_diff_review_required_on_change` (always `true`), and `source` (`config|flag`). Execution has exactly nullable string `timeout` and `timeout_source` (`none|flag`). Delivery has exactly booleans `taskrail_metadata_commit_required` and `product_commit_required`, plus `remote:"not_checked"`. `selected_task`, when present, and every `tasks` entry use the exact list row fields `task_id`, `status`, `active_spec`, `source`, `effective_policy`, `reason`, `eligible`, `held_dependencies`, and `disposition`; neither text nor JSON contains a policy-file path.
- Built-in templates are automatically authorized and report `override_authorized:true`. When a replacement resolves, its exact template SHA-256 must equal `--allow-prompt-override-sha256`; absent or mismatched authorization makes dry-run `invalid` and execution refuses before launch. Supplying the authorization flag when no replacement resolves is `invalid_arguments`, preventing stale operator intent from being silently ignored. Authorization is never computed from rendered content. `template_sha256` hashes exact resolved template bytes before substitution; `rendered_sha256` hashes exact UTF-8 content written to child stdin. Approval trusts only those bytes, not their safety. Prompt source, path, template bytes, and template hash are frozen for the invocation; each selected task's rendering is frozen before launch.
- The loop runs from the repository root and launches one fresh child process per
  selected task. It writes the exact UTF-8 rendered prompt bytes to child stdin,
  adds no framing or newline, closes stdin immediately, and streams child stdout
  and stderr to the corresponding Taskrail streams. Stream-copy failure fails the
  iteration. A provider CLI that cannot consume a finite stdin prompt requires a
  caller-supplied adapter process.
- The child inherits caller-owned environment/authentication. Before launch, copy the running executable bytes to a hash-named, no-replace file under the Git common directory and verify its SHA-256. Taskrail sets exact variables `TASKRAIL` to that staged absolute path, `TASKRAIL_EXECUTABLE_SHA256` to its lower-case digest, `TASKRAIL_DELEGATION_ID` to the random invocation ID, and `TASKRAIL_DELEGATION_TOKEN` to the unguessable secret whose digest appears in lock metadata. A conflicting inherited value refuses. Delegated writers verify repository, storage, invocation, selected task, executable bytes, token, command capability, and field/write-set bounds before joining. Cleanup removes only the invocation's staged copy after contained writers exit.
- `loop` has no `--json` execution mode because streamed child output cannot form one valid Taskrail JSON document.
- `--result-file` is optional for local delivery and required for executing `--delivery review`; absent review-delivery evidence is `invalid_arguments` before repository, workspace, or adapter activity. Dry-run rejects result files and retains its review-delivery preview. The result destination is resolved from the caller's original working directory. Its canonical target must not exist, its parent must already be an existing directory, traversal crosses no symlink or reparse point, and the target is outside the repository worktree, Git directory/common directory, and every managed task/spec/state/prompt/review input. Taskrail atomically creates the regular file without replacement after final postflight, so publication cannot dirty the repository whose cleanliness was reported.
- Result-destination refusal is exact: malformed/empty path is `invalid_arguments`, an existing target is `destination_exists`, and missing/non-directory/forbidden/alias/traversal parent is `path_blocked`; `result_file_publish_failed` is reserved for a destination that passed preflight but cannot be created at final publication. Preflight retains a no-follow identity handle or platform-equivalent identity for the parent; publication rechecks the same canonical parent identity and absent target immediately before no-clobber creation, refusing substitution without following the replacement.
- A result-file document uses `command:"loop"`. Successful invocation-terminal outcomes use `result`; a postflight failure uses `error`, with `error.code` equal to the registered postflight outcome and the same complete diagnostic object in `error.details`. Failure to publish a requested file exits non-zero as registered code `result_file_publish_failed`, never overwrites an entry, and cannot claim that a result file was produced.
- Result destination validation occurs before repository preflight. Once the destination itself is valid, every ordinary terminal refusal attempts to publish exactly one envelope: preflight/argument/prompt/lock refusals use their common error details; a post-child stop uses the diagnostic object below. A handled interrupt drains contained processes and then publishes `child_failed` when possible. Abrupt process/host termination cannot guarantee a result file and leaves the absent destination distinguishable from a completed report.
- The exact post-child invocation diagnostic object has `outcome`, nullable `last_iteration`, `iterations_completed`, nullable `remaining_task`, `validation`, `git`, `storage`, `review`, `execution`, `executable`, non-null `mutation_violations`, non-null `process_violations`, `remote:"not_checked"`, and `next_action`. `iterations_completed` counts children that launched and reached termination/containment postflight; a launch failure has a last iteration but does not increment it. `remaining_task` is null or one exact task-loop list row.
- `last_iteration`, when present, has exactly `task_id`, `outcome`, nullable `lifecycle_candidate`, `child`, nullable `status_before`, nullable `status_after`, nullable `completion_id_before`, nullable `completion_id_after`, nullable `verification_id_before`, nullable `verification_id_after`, nullable `verification_previous_id_before`, nullable `verification_previous_id_after`, nullable `observed_completion_id`, nullable `audit_pass_verification_id`, nullable `audit_pass_observed_completion_id`, `policy`, and `prompt`. The lifecycle candidate is null when invalid final bytes prevent derivation. The two audit-pass fields are non-null only for `completed_audit_fail`, identify its intermediate passing artifact, and bind the same `completion_id_after`; final `observed_completion_id` is null because the final verification is fail. `child` has nullable integer `exit_code`, nullable string `signal`, and boolean `timed_out`; after launch exactly one exit code or signal is non-null, and timeout sets `timed_out:true`. `policy` is one exact task-loop list row. `prompt` has exactly `id`, `source` (`builtin|replacement`), nullable `path`, `template_sha256`, `rendered_sha256`, and boolean `override_authorized`; built-ins use null path.
- `validation` has exactly boolean `valid` and non-null ordered common `violations`. `git` has exactly `ref`, `head_before`, `head_after`, boolean `clean`, boolean `descendant`, and non-null `commits`; commits are full object-ID strings in ancestry order from oldest to newest. `storage` has exactly `mode` (`committed|local`) and `root`; `review` has exactly integer `configured_max_rounds`, integer `effective_max_rounds`, integer `max_reviewers_per_round` (always `3`), boolean `final_diff_review_required_on_change` (always `true`), and `source` (`config|flag`); `execution` has the same timeout fields as dry-run; `executable` has exactly `invocation_id`, `path`, and `sha256` for the staged binary. Each mutation/process violation has exactly `code`, `message`, and nullable `path`, ordered by code, null-last path, then message. `next_action` is non-empty text. No-work before a child uses null iteration and remaining task; iteration limit requires a remaining task. Error details use this same object without adding fields.
- Establish an isolated Unix process group or Windows kill-on-close job before untrusted descendants can run, or fail launch. After leader exit, stream failure, timeout, or interruption, drain all assigned descendants, request termination, wait 10 seconds, then force the tree. Detected escape, unassignable process, or survivor is `child_failed` and never permits postflight success. Taskrail explicitly does not claim control over a deliberate privileged or undetectable Unix `setsid`/Windows breakaway escape.
- Execution in the Taskrail source checkout is unsupported in v0.5 because source-changing work makes the pinned running binary stale and native Windows cannot replace it safely. The deterministic predicate is a managed root containing both `Taskfile.yml` and `internal/toolchain/cmd/freshcheck`; dry-run reports `unsupported` before launch. Installed adopter repositories are unaffected.

Selection contract:

- Require Git, a non-bare worktree with attached non-unborn `HEAD`, equal
  Taskrail/worktree logical roots, and either a valid committed or local layout.
  Every Taskrail task/state/spec/layout/import writer uses one
  Git-common-directory mutation lock for its whole
  candidate-validation/write/rollback transaction. Loop owns it through
  postflight and passes an unguessable child-only delegation token; matching
  child writers join without release, unrelated writers/loops refuse. Delegation
  excludes loop-policy mutation and any task-creation input that could make a
  follow-up allowed. Metadata records command/PID/host/start/repository/storage
  mode/token digest, never token; stale locks use `lock status` and guarded
  `lock clear`, never automatic removal.
- Before the first child and between every iteration, run the same repository
  validation used by `taskrail validate` without writing state.
- Refuse to begin with a dirty visible working tree or an existing `in_progress` task.
  "Clean" means `git status --porcelain=v1 --untracked-files=all
  --ignore-submodules=none` reports no
  staged, unstaged, untracked, or submodule change; ignored verification artifacts
  and valid local-mode Taskrail metadata remain ignored by Git. Local preflight
  separately proves that managed local paths are ignored, untracked, unstaged,
  valid, and unchanged outside the allowed child write set. Recovery or continuation of interrupted work is
  deliberate human work, not an automatic retry hidden inside the loop.
- Select only explicit active-spec allowances through the Task-Local Loop Policy contract. Independent held tasks are bypassed, held dependencies disqualify only their dependent candidates, and eligible allowed tasks retain ordinary deterministic ranking.
- Selection finding no eligible allowed task before another child launch ends execution with successful outcome `no_work` and launches no child. This applies both to initial selection and selection after a successful iteration; absence of explicit allowances is not an error.
- Before each child, capture selected/every task bytes and parsed fields including loop-policy source/effective value/reason/disposition, active spec/config/layout digests, storage mode/root, configured/effective broad review-round limit and source, fixed reviewer ceiling/final-diff rule, full attached ref/HEAD, the complete local `refs/*` namespace, verification IDs/artifact set, prompt source/path/template SHA-256, that task's rendered SHA-256, and staged executable path/hash. Invocation-wide template bytes, review-round policy, storage mode, and executable bytes remain immutable; each task-specific rendering is immutable for its iteration. Repository policy and caller authorization remain semantic prompt/manual-evaluation context, not an implicit Taskrail policy parser or frozen machine field.
- The same snapshot captures no-follow identities and exact bytes for repository-
  owned Git configuration in the effective worktree Git directory and Git common
  directory. Missing files are recorded as absent. Postflight rejects creation,
  deletion, replacement, aliasing, or byte changes as `invalid_postflight` before
  delivery. User-global and system Git configuration remain caller-owned and
  outside this repository-integrity claim.

- The pre-child Git snapshot also enumerates direct regular files in the effective
  worktree Git directory and Git common directory whose names match
  `^[A-Z][A-Z0-9_]*$`, excluding only `COMMIT_EDITMSG`, which an ordinary commit
  rewrites. These root ref candidates, including future or repository-specific
  names such as `EVIL_REV`, are captured as exact bytes. Enumeration and reads are
  no-follow and reject aliases or special files.

Postflight contract:

- After every child termination, including non-zero or signal, run validation and collect all lifecycle, Git, loop-policy, prompt, lock, process, and mutation diagnostics. Independently derive the lifecycle candidate from valid final state: `completed_pass` for completed with a fresh bound pass; `completed_audit_fail` only when the same iteration first created a fresh bound pass for the current completion ID and then recorded a later fresh fail whose predecessor is exactly that pass; `completed_unverified` for newly completed without a fresh valid verification; `blocked_fail` for blocked with a fresh fail; `rework_fail` for in-progress with a fresh fail; otherwise `no_progress`. A completed fresh fail without the direct verified chain is inconsistent and therefore `invalid_postflight`.
- The per-child outcome uses this first-match precedence: `invalid_postflight` when repository validation, frozen control inputs, mutation allowlists, lifecycle evidence, or branch-specific Git delivery is invalid or internally inconsistent; `child_failed` for launch, stream-copy, signal, non-zero child exit, or required process-containment failure; otherwise the derived lifecycle candidate. A non-zero or signalled child therefore yields `child_failed` even when its repository writes independently form a valid lifecycle candidate; diagnostics still report that candidate and persisted lifecycle evidence. Dirty evidence allowed specifically for `child_failed` is not by itself `invalid_postflight`.
- Only per-child outcome `completed_pass` may proceed to another selection. `blocked_fail`, `rework_fail`, `completed_unverified`, `completed_audit_fail`, `child_failed`, `no_progress`, and `invalid_postflight` terminate execution and exit non-zero.
- Every delivered recognized lifecycle outcome leaves a clean visible tree, same
  full attached ref, unchanged active spec/config/layout/storage mode/review
  review-round policy/prompt, valid task-local loop metadata, and no contained process.
  The complete local ref namespace remains byte-identical except for the one
  expected attached-branch advance; tags, notes, remote-tracking refs, sibling
  branches, and other refs cannot be created, deleted, or moved by the child.
  Repository-owned Git configuration remains byte- and identity-identical to the
  pre-child snapshot.
  The same dynamic root-ref-candidate set remains byte-identical: no captured entry
  may change/disappear and no new matching entry may appear, apart from excluded
  `COMMIT_EDITMSG`.
  Committed mode requires exactly one new commit: `head_after` is the direct child
  of `head_before`, and that commit contains the complete implementation plus
  generated Taskrail outcome and no unrelated mutation. Local `completed_pass`
  with product changes likewise requires exactly one direct-child product commit
  containing no Taskrail metadata; local blocked/rework requires that commit only
  when visible product bytes changed, otherwise HEAD remains unchanged. Merge,
  intermediate, multiple, and metadata-only local commits are invalid. Remote
  delivery is always `not_checked`. Child failure may leave dirty evidence but is
  never delivered.
- Pre-existing non-selected task files remain byte-identical. Selected ID/title/priority/spec_ref/dependencies, `loop_policy`/`loop_reason`, and Description/Acceptance/Verification Notes remain unchanged; only canonical lifecycle fields, timestamps, blocker and Implementation Notes may change. Any number of new live tasks is allowed only when each was created by selected-task `verify --create-followup`, appears in a fresh report in the valid verification chain, depends on the selected task, and omits the loop-policy pair. Any other task creation, policy mutation, explicitly allowed follow-up, or ledger mutation is integrity failure.
- In parallel mode, every permitted follow-up must additionally use the creating
  worker's frozen rank-partitioned numeric key sequence. A key outside that
  sequence is an integrity failure even when its other provenance is valid.
- Fresh verification requires a new preflight-absent verification ID/path and exact task/result/time/completion-ID agreement across task, state, JSON, and report. A completed audit fail remains completed and stops for follow-up disposition; command failure after successful complete is completed-unverified and recovery reruns verify only.
- After `completed_pass`, perform one read-only selection against the frozen invocation policy. If no eligible task remains, terminate successfully as `no_work`. If an eligible task remains and completed child count equals `--max-iterations`, do not launch it and terminate successfully as `iteration_limit`, reporting that selected task as remaining work. Otherwise launch it. This ordering makes `no_work` take precedence over `iteration_limit` when completion exhausted eligible work.
- Post-child human and result-file diagnostics report the invocation-terminal outcome, validation, Git/ref/HEAD, storage mode/root, configured/effective broad review-round limit and source, fixed reviewer ceiling/final-diff rule, mutation/process violations, local commits, remote `not_checked`, remaining-work selection, and safe next action, plus the last iteration's task, child exit/signal, lifecycle and verification IDs, policy row, and prompt hashes. Initial `no_work` uses the exact diagnostic result with null iteration; preflight refusals instead use the common error-details schema and do not claim postflight fields. Successful sequential execution envelopes have exact terminal outcome `no_work` or `iteration_limit`; `completed_pass` is a per-child outcome, not an invocation-terminal result. Successful parallel execution uses `batch_pass`, exits zero, and carries the non-null parallel batch diagnostic; partial or failed batches use their registered non-zero postflight outcomes.

Safety boundary:

- With `--parallel 1`, `loop` remains one foreground process repeated
  sequentially. With `--parallel >1`, the coordinator remains one foreground
  process while only its declared isolated workers run concurrently. The
  common-directory lock coordinates linked worktrees but is not a distributed
  lease across clones.
- Taskrail does not inspect child conversations, tool calls, model output, review
  identity, token use, or provider state. Its evidence is process exit plus the
  repository contracts it already owns.
- Hook execution and free-form provenance necessity are prompt/manual-evaluation
  behavior, not mechanically attested facts. Postflight enforces inspectable ref,
  commit, tree, configuration, identity, and signature policy only where the
  frozen repository contract defines an exact mechanical oracle.
- Taskrail does not create sequential delivery commits, push, merge, open pull
  requests, wait for remote CI, or reset failed work. The sequential child creates
  the one required direct-child commit; Taskrail only validates it. Repositories
  express remote delivery policy in their prompt replacement and external
  automation.
- Every non-clean stop reports Git/preflight violations and safe next actions. When selection or launch occurred it also reports task ID, available child exit or signal, lifecycle status, verification before/after, and loop-policy disposition; preflight refusal does not fabricate child/task fields.
  Recovery is manual inspection followed by the existing `complete`, `block`,
  `unblock`, `task release`, `verify`, and Git operations as appropriate; Taskrail never resets or
  rewrites the failed child outcome automatically.

#### Operator Supervision And External Quota Exhaustion

Provider quota state remains outside Taskrail's authority. The binary does not
detect, parse, normalize, or attest quota exhaustion or reset information. A
caller-owned adapter, provider CLI, or operator may report that external
condition, and an operator-facing skill may explain it only as attributed
external evidence, separate from the authoritative Taskrail process, lifecycle,
repository, integration, and delivery result. A generic non-zero child still
follows the existing outcome precedence, ordinarily `child_failed`; no provider
condition adds a machine outcome, error code, or result-file field.

- A launched child that externally reports quota exhaustion remains one launched
  attempt and counts under the existing `iterations_completed` rules. Taskrail
  never refunds, carries forward, silently consumes, or re-labels the original
  invocation's finite budget because of an external reset claim.
- The parent supervisor does not interrupt a running coordinator merely because
  quota exhaustion was reported. The coordinator completes its existing
  containment and batch contract: no failed worker is retried, no replacement or
  new frontier launches, already-launched siblings drain to independent results,
  and independently valid candidates remain eligible for ordinary deterministic
  integration and delivery. Any later integration or adapter child still follows
  its normal process and outcome contract; quota observation grants no alternate
  delivery path or authority to skip required gates.
- Caller-owned stream capture may preserve available coordinator and worker
  diagnostics only in external or ignored transient storage. Those bytes are not
  Taskrail evidence, may contain sensitive provider output, receive no completeness
  or redaction claim, and never enter task files, `STATE.md`, committed review
  artifacts, or the loop result document. Preservation failure must be reported
  rather than hidden.
- The parent reports reset information exactly as attributed by its external
  source, including an explicit offset or timezone when supplied. It never invents
  a reset instant from absent, malformed, contradictory, timezone-free, or
  already-past text, and never presents a relative estimate as Taskrail-attested
  time.
- v0.5 permits post-reset execution only as a new foreground invocation. The
  parent reruns the exact dry-run and repository preflight, explains the newly
  selected task or frontier and current retained/unpublished work, elicits a new
  finite iteration and parallel budget, allocates a new result destination, and
  obtains fresh explicit operator confirmation before launch. It never resumes a
  worker or conversation, reuses an in-progress outcome, waits in the background,
  persists future launch intent, or automatically relaunches after a reset.

#### Parallel Isolated Clone Batches

Parallel execution is explicit optimistic concurrency over Taskrail's existing
dependency graph. It does not introduce multiple authoritative `current_task`
values, a second queue, or concurrent writes to one planning ledger. Workers
execute against independent complete committed snapshots; one foreground
coordinator serializes accepted outcomes into one authoritative Git history.

Invocation and planning requirements:

- `--parallel >1` is supported only for committed Taskrail storage in a clean,
  attached, non-bare Git worktree whose branch tip equals `HEAD`. Local ignored
  planning storage, source-checkout execution, submodules requiring recursive
  initialization, and linked-worktree workers return `unsupported` before a
  workspace or child is created. Sequential mode remains available wherever its
  inherited contract permits.
- Selection computes one deterministic ready frontier from explicit active-spec
  allowances using the same ranking and dependency semantics as sequential
  selection. Every selected task is `todo`, all its dependencies are completed in
  the frozen ledger, and no selected task depends directly or transitively on
  another selected task. Selection takes at most the effective parallel width and
  remaining iteration budget in ordinary ranking order.
- Parallel dry-run is read-only and reports the complete ordered frontier plus
  effective width, base ref/HEAD, committed storage, workspace policy, clone
  depth, retention policy, delivery mode, prompt/review/execution policy, and the
  reason every other open task was held or ineligible. It creates no directory,
  clone, ref, lock, process, or result file.
- `--workspace-root` is optional. Omission creates one private invocation
  directory beneath the operating system's temporary root. An explicit root is
  resolved from the caller's original working directory and must be an existing
  private directory outside the repository worktree, Git directory/common
  directory, managed storage, result destination, and every configured semantic
  input. Traversal, aliases, links, reparse points, and unsafe ownership or
  permissions fail closed. Taskrail creates no workspace before repository and
  destination preflight succeeds.
- `--clone-depth` defaults to integer `1`, accepts a positive integer or `full`,
  and is frozen for the invocation. A finite local-source clone uses transport
  semantics equivalent to `--no-local --single-branch --no-tags --depth <n>` so
  Git cannot silently replace the shallow boundary with a local hard-linked
  full-history clone. `full` omits the depth boundary. Taskrail does not alter Git
  LFS smudging, initialize submodules recursively, add sparse checkout, or claim
  that a shallow checkout satisfies repository-specific history requirements.
- `--keep-workspaces` defaults to `failure`. During final postflight and before
  durable result publication, `never` removes every coordinator-owned workspace,
  `failure` retains only failed worker or integration workspaces, and `always`
  retains all of them. The immutable result therefore reports null for each
  successfully removed workspace and an absolute path only for retained work;
  publication failure does not recreate already-cleaned workspaces.
  Cleanup removes only directories whose invocation identity and no-follow root
  binding still match. Retained absolute paths are transient diagnostics and
  never enter committed Taskrail state.

Worker requirements:

- The coordinator freezes the exact base ref/HEAD, complete task/spec/state/
  config/prompt inputs, selected frontier, child argv, executable identity,
  review policy, timeout, clone policy, and delivery policy before cloning. It
  creates one independently locked clone per selected task at exactly that base
  and launches the same caller-supplied argv once in each clone with a fresh
  selected-task implementation prompt. Workers never run `next` or select work.
- Each clone has its own Git common directory and Taskrail mutation lock. Worker
  lifecycle writes remain bounded to its selected task and verification-created
  implicit-hold follow-ups under the inherited delegation contract. No worker
  receives authority over the source checkout, another clone, the integration
  clone, workspace policy, or delivery adapter.
- Let `M` be the greatest numeric task-key value in the complete frozen ledger,
  `W` the selected frontier width, and `R` a worker's one-based deterministic
  rank. That worker's zero-based `K`th delegated follow-up receives numeric key
  `M + R + K*W`; normal slug derivation then forms its full ID. The coordinator
  freezes `M`, `W`, and `R` into the worker grant, and delegated task creation
  rejects any other key. These disjoint unbounded sequences preserve the no-cap
  semantic follow-up rule while preventing cross-clone identity collisions.
  Sequential and direct-operator allocation remains unchanged.
- A successful worker exits zero with one valid `completed_pass`, one direct-child
  candidate commit from the frozen base, a clean clone, no unexpected refs or
  surviving process, and the complete inherited verification and postflight
  evidence. Every other inherited lifecycle/process/integrity result is a failed
  worker. A failed worker is never retried and its task remains unchanged in the
  authoritative repository.
- Once any worker fails, the coordinator launches no replacement task and no new
  frontier. Workers already launched are contained and allowed to finish so their
  independent results are not discarded merely because a sibling failed.

Serial local delivery requirements:

- `--delivery local` is the default parallel delivery. After workers terminate,
  Taskrail creates one separate integration clone at the frozen base and
  considers successful candidates in original deterministic frontier order,
  never completion-time order. The operator worktree remains byte/ref-identical
  until the complete integrated candidate passes final publication preflight.
- For each successful worker, deterministic one-commit replay is attempted onto
  the evolving integration head. `planning/STATE.md` is an aggregate projection:
  the integration flow never asks an agent to hand-resolve it, and reprojects it
  through `taskrail repair --apply` after applying the selected task and product
  bytes without committing. The coordinator validates that candidate and creates
  exactly one integration commit whose parent is the prior evolving integration
  head. The resulting per-task commit contains that task's implementation,
  tests, documentation, terminal task bytes, and current reprojected state.
- A semantic replay conflict permits exactly one fresh integration child using
  the same caller-supplied argv and the built-in `loop-integration` prompt bound to the
  candidate, evolving head, both relevant task/spec contracts, worker evidence,
  and exact conflict. It may resolve current-scope product/test/documentation
  conflicts and rerun evidence, but cannot drop acceptance, remove a detecting
  test merely to pass, change task relationships or policy, hand-edit generated
  state, retry, or integrate another candidate. Failure leaves that candidate
  unpublished and does not prevent later dependency-independent successes from
  being considered.
- Every accepted candidate is repository-valid and passes its affected checks.
  After all candidates, one fresh integration child runs the repository's full
  aggregate gate over the exact integration head; it may report but not silently
  repair unrelated work. Aggregate validation is read-only: the coordinator
  compares the integration inputs, Git tree/index/ref/worktree snapshot, and
  repository-owned Git configuration before and after validation. Only a passing
  aggregate child whose bound head still exactly matches those observations
  attests a publishable integration head. Aggregate failure publishes no final
  fast-forward and retains the integration workspace under `failure` or `always`
  policy.
- Every conflict-resolution and aggregate integration child records its role,
  nullable selected task, exact prompt source/template/rendered digests, process
  outcome, and ordered affected-check names in the parallel result. Conflict
  children bind the worker evidence and candidate/evolving-head identities;
  aggregate children bind the exact final integration head. Missing or stale
  bindings make integration fail rather than degrading to prose diagnostics.
- Final publication reacquires the source repository lock and compare-and-swaps
  exact original worktree cleanliness, attached ref, base HEAD, index, relevant
  refs, configuration, and planning inputs. It then performs one non-force
  fast-forward of that attached branch and worktree to the aggregate-attested
  integration head. Source evidence is rechecked after fetch and before that
  fast-forward. Drift refuses without reset, checkout overwrite, rebase, stash,
  or partial publication. This final Git operation is not claimed to be an
  all-or-none durable transaction: an interruption can leave the branch advanced
  while the index or worktree requires operator repair, and a host death can
  prevent a terminal diagnostic. An observed uncertain/advanced publication
  reports interruption evidence and never retries. Operators preserve all source
  drift, inspect the branch, index, and worktree, restore a clean intended Git
  state with deliberate Git operations, and only then begin a new invocation;
  normal loop preflight refuses the dirty or drifted retry.
- Independently valid candidates are published even when a sibling worker or
  candidate integration failed. Such an invocation returns the exact partial
  batch failure with passing/integrated and failed/unpublished rows, launches no
  replacement work, and names safe operator actions. Zero accepted candidates is
  a failed batch; all selected candidates accepted is a passing batch.

Review-adapter delivery requirements:

- `--delivery review` requires one explicit `--review-adapter <path>` and is a
  separately staged capability after local delivery. The adapter path resolves
  like the child executable and names one caller-owned executable, not a shell
  string or named provider. Supplying an adapter in local mode or review mode
  without one is `invalid_arguments`.
- Taskrail sends the adapter one strict versioned JSON request on finite stdin for
  each `publish_branch`, `open_change`, `inspect_change`, `update_change`, or
  `merge_change` operation and accepts exactly one strict JSON result on stdout;
  stderr streams as diagnostics. The adapter owns provider credentials and may
  wrap `gh`, `glab`, or another service. Taskrail contains no provider names,
  tokens, API clients, session persistence, or provider-specific result fields.
- Passing worker changes may be open concurrently, but merges are serialized in
  deterministic frontier order. After each merge, every remaining change is
  refreshed against the new target through one bounded integration-child pass,
  reprojects `STATE.md`, reruns required checks, and updates the existing change.
  Adapter refusal, failed required checks/review, target drift, or unresolved
  conflict leaves that change open/unmerged, launches no replacement task, and
  does not prevent an independent passing change from later consideration.
- Review delivery is foreground, explicitly authorized, timeout-bounded, and
  result-file reported. It never force-pushes, bypasses hosted checks, invents
  approval, retries an operation, or claims remote state not returned by the
  adapter. Exact adapter requests/results, merge identities, required-check
  evidence, and partial outcomes are defined by the machine API companion.

The machine API companion defines the exact parallel dry-run plan, worker,
integration, workspace, delivery, adapter, and terminal batch shapes. The loop
result contract gains an explicit nullable parallel member so default sequential
execution remains unambiguous; parallel execution uses the parallel batch
diagnostic and never overloads one sequential `last_iteration` as if it
represented concurrent work.

#### Source-Checkout Bootstrap Loop Retirement

Taskrail's own v0.5 development briefly used a temporary,
source-checkout-only shell loop while the product command was unavailable. It
was bootstrap tooling, never shipped Taskrail behavior or an adopter workflow,
and has been retired with all runner, queue, prompt, test, and local-guidance
bytes. The completed product loop and local Git delivery evidence remain
independently required. Source-checkout execution remains unsupported in v0.5,
so this repository returns to human-invoked task execution rather than claiming
the product command replaces the retired bootstrap here.

#### Maintainer Skill Release Evaluations

- Keep provider-neutral behavioral eval definitions under maintainer testdata, outside the embedded skill package, so `init --with-skills` installs no eval fixtures, runner, credentials, transcripts, or benchmark output.
- Every shipped skill has realistic positive, negative, recovery, and boundary cases with stable prompts/fixture digests, deterministic repository assertions, expected outcome, and human-review questions. Changed skills compare the candidate against the prior released bytes; new skills compare against no skill.
- A maintainer manually runs the complete registered suite before a skill-heavy release through a caller-owned agent adapter. The report records adapter/model identity, skill and fixture digests, paired raw outcomes or missing arms, deterministic grades, and human review, including local provenance and decoy-path observations that deterministic tests cannot attribute to an opaque agent. Timing and usage remain optional transient adapter evidence rather than fields in the committed report. Model-backed evidence is stochastic and never substitutes for required credential-free CI.
- An agent may analyze failures and produce candidate patch proposals in an isolated workspace, rerun the same cases, and report paired evidence. It never edits shipped skill sources, fixtures, assertions, packaged mirrors, tracked state, or Git history automatically. A human chooses and applies any patch, then required contract checks and an untouched final case set rerun.
- The v0.5 release gate requires a committed safe summary at `<planning-dir>/reviews/skill-evals/v0.5.0/<session-id>/report.json`. Raw provider transcripts remain beneath ignored artifacts and are represented only by safe summaries and paired run digests. The exact report records outcome `pass|fail|incomplete|waived`, tested snapshot/executable, candidate/baseline/fixture digests, observed or unavailable adapter/model identity, deterministic grades, missing arms, and human review.
- The report is canonical two-space-indented UTF-8 JSON with one final LF and
  exactly ordered fields `schema_version`, `session_id`, `generated_at`,
  `tested_head`, `candidate_executable_sha256`, `baseline_executable_sha256`,
  `product_sha256`, `outcome`, `candidate`, `baseline`, `fixtures_sha256`,
  `adapter`, `model`, non-null `cases`, `deterministic_checks`,
  `human_review`, and nullable `waiver`.
  `schema_version` is `1`; the session ID is a portable review key; timestamps are
  canonical UTC; object IDs and digests are lower-case. Candidate and baseline
  each have exactly `taskrail_version` and `skills_sha256`, with exact versions
  `v0.5.0` and `v0.4.0`. Adapter/model each have exactly non-empty `name`, non-empty
  `version`, and boolean `observed`; both name the intended target and use
  `observed:false` only when no arm ran, otherwise both are true and describe the
  observed runner. Deterministic checks have exactly
  `outcome` (`pass|fail`) and non-null sorted `evidence` strings. Human review is a
  non-empty safe summary.
- A case has exactly `case_id`, `skill`, `storage_mode` (`committed|local`),
  `fixture_sha256`, boolean
  `baseline_required`, nullable `candidate`, nullable `baseline`, `comparison`
  (`better|same|worse|inconclusive`), and `human_review`. A non-null run has exactly
  `outcome` (`pass|fail|incomplete`), `skill_sha256`, `executable_sha256`,
  `deterministic_grade` (`pass|fail`), and `raw_sha256`. Case IDs are globally unique, every registered
  case appears exactly once, and cases sort by `(skill,case_id)`. Candidate null

#### Verify Lifecycle Advisory

`verify --result pass` emits a non-gating advisory warning when the target task is
not `completed`.

Requirements:

- The warning names the task, its current status, and the expected order. It is
  advisory: `verify` still writes artifacts, records the result, and exits zero.
- Human mode writes stderr. JSON emits non-null `warnings` (empty when none); the exact object is `{"code":"verify_pass_before_complete","message":<string>,"task_id":<string>,"status":<todo|in_progress|blocked|cancelled>,"expected_status":"completed"}`.
- It covers every non-`completed` status, not only `in_progress`.
- It never makes `validate` fail and never changes task status.
- `verify --result fail` emits no corresponding warning: `in_progress`, `blocked`, and completed audit are valid failing records. It carries a verification ID but binds no passing completion.

## Caution

Do not turn `v0.5.0` into a general agent framework.

The loop is intentionally one foreground coordinator. Sequential execution stays
the default; explicit parallel execution is bounded to one frozen dependency-ready
frontier in isolated clones followed by serial integration. It is not permission
for shared-worktree writers, background scheduling, retries, distributed leases,
or unconstrained multi-agent coordination. The prompt system is intentionally a
versioned lookup, strict substitution, and local whole-file replacement. The
review lenses are intentionally advisory. Resist adding provider configuration,
prompt graph execution, retries, background operation, model-output parsing,
automatic planning writes, or semantic validation under these names.

Task-local loop policy must not become a second task database or an ordering
system. It contains only an optional paired allowance/hold decision and reason.
Status, dependencies, priority, spec linkage, title, acceptance, and verification
stay in the existing task and state contracts; deterministic ranking remains the
ordinary ranking.

Workflow-adversarial memory likewise stays an optional review index, not task
state or permanent assurance. Partition detailed runs by spec, keep the current
index compact, and treat old clean claims as snapshot-bound evidence.

Local replacement can remove supported guidance. That explicit repository choice
does not justify implicit merging, and Taskrail does not judge replacement quality.
Universal loop safety remains in mechanical preflight/postflight; semantic and
delivery policy remains in prompt text.

A review artifact's prompt-resolution binding records only the role-mandated
template bytes and source that Taskrail resolved at publication. It does not prove
that an external reviewer received or followed those bytes, authenticate a
reviewer, establish context independence, or certify a replacement's safety or
quality.

Local mode is inspectable ignored Markdown, not a hidden database or an excuse to
weaken validation. It deliberately lacks clone, CI, and teammate portability until
promotion. Never broaden ignore patterns to hide adopter-owned directories or
treat ignored state as protected from destructive Git cleanup.
Ignored local skill files share that cleanup risk even though they live at normal
assistant discovery paths; `git clean -x`/`-X` can remove them before promotion.

## Recommendation About LLM Support

Do not add direct LLM calls to Taskrail core.

`taskrail loop` starts a caller-supplied executable; it does not know whether that
process is a coding agent, a deterministic test double, or another local tool.
`taskrail prompt` emits text; it does not send that text to a provider. The
judgement-heavy parts of spec review and decomposition remain in prompts and
skills, while the binary provides deterministic inputs, validation, and reviewed
write paths.

This preserves the established order: repo-native CLI and file model first,
prompts and skills for external agents second, and provider-neutral caller-owned
process adapters only where an explicit delivery mode requires one. Taskrail
still does not embed a provider API adapter.

## Explicitly Excluded

Continue to exclude:

- direct model or provider API calls from the Taskrail binary;
- named or built-in provider adapters, provider configuration, model selection,
  token or cost management, and conversation/session persistence; the explicit
  review-delivery executable remains caller-owned and provider-neutral;
- shell-string evaluation or a shell-script runtime inside `loop`;
- background daemons, schedules, automatic post-reset waiting or relaunch,
  persisted future execution intent, retries, unbounded or persistent worker pools,
  shared-worktree parallel writers, distributed leases, and multi-agent
  coordination outside one explicit isolated-clone batch and its serial
  integration;
- skill interpretation, skill graphs, conditional workflow execution, or a
  general prompt-composition language;
- automatic continuation of an existing `in_progress` task, worker or provider
  session resume, or carry-forward/refund of an earlier loop invocation's finite
  budget;
- bootstrap caused by a read-only command, implicit committed adoption, mixed
  committed/local Taskrail state, or local storage outside the managed overlay;
- Git force operations, destructive rollback, or implicit remote delivery;
  sequential mode retains Taskrail's inherited no-commit/no-push/no-merge
  boundary while its caller-owned child creates the required direct-child commit,
  while explicit parallel delivery is limited to candidate commits made by
  caller processes, one guarded local fast-forward, or strict caller-owned
  review-adapter operations;
- semantic enforcement of independent reviewer identity or different model use;
- one generic review-count setting shared by implementation, task review, spec
  lenses, decomposition, manual testing, and post-delivery audits;
- automatic spec edits, spec activation, task creation, or `import --apply` from a
  review or decomposition prompt;
- turning semantic spec findings into `validate` errors or conflating
  `spec-gaps` with mechanical `coverage --gaps`;
- semantic task-size validation, provider/model effort estimates, or numeric
  proof based on time, tokens, points, files, lines, criteria, or task counts;
- a second lifecycle, dependency, queue, or policy-storage schema for loop selection;
- automatic promotion of workflow-review findings or treating review memory as Taskrail state;
- automatic editing, selection, regeneration, or commit of packaged skills from behavioral eval or model-judge output;
- physical task archival, automatic terminal-task moves, or an archive storage class in the task ledger;
- `verify` performing a lifecycle transition or hard-rejecting a misordered run;
- `reopen` / `uncomplete` recovery semantics; and
- Taskrail-owned autonomous-run databases, committed conversation logs, required persistent execution receipts, SDD provider adapters, provenance claims, or upstream-artifact synchronization.

The narrow exception to prior automatic-loop and orchestration exclusions is the
explicit foreground `taskrail loop -- <command> <args...>` boundary specified
above. It selects deterministically, renders one supported prompt, launches one
opaque external process, verifies repository postconditions, and repeats only up
to a finite caller-visible limit. Nothing broader is implied.
