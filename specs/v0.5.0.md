# Taskrail v0.5.0

## Summary

Taskrail `v0.5.0` adds **autonomous workflow integrity and reviewable planning**.

Through `v0.4.0`, Taskrail established deterministic task state, active-spec
selection, reviewable import drafts, structural coverage and gap reports, and a
packaged skill set. Adopters can drive those primitives with an external coding
agent, but Taskrail does not yet provide a portable outer loop or a reusable
workflow-prompt surface. Repositories therefore assemble their own shell runner,
queue policy, prompts, and post-run checks. Those copies are useful, but they
drift and are commonly platform- or provider-specific.

The existing skill contract also has a concrete lifecycle defect. The packaged
`autonomous-backlog` and `autonomous-task` skills run `verify` and then say, in
prose, to finish as `completed` or `blocked`; neither invokes `complete` or
`block`. Because `verify` is not a lifecycle transition, a nominally successful
run can remain `in_progress`, and a run that cannot proceed can leave no recorded
blocker.

This version fixes that lifecycle contract and then builds on it in three bounded
ways:

- a cross-platform, foreground `taskrail loop` command that starts one fresh,
  caller-supplied external process per task and fails closed between iterations;
- a versioned catalog of built-in workflow prompts with deterministic rendering
  and repository-local replacement; and
- stronger prompt and skill workflows for post-spec review and adversarial
  spec-to-task decomposition before any draft is applied.

Taskrail still does not call a model, know about model providers, interpret a
skill, or silently write judgement-derived planning state. The binary owns the
mechanical boundary: selection, policy validation, prompt resolution, process
execution, and postconditions. The external agent owns semantic implementation
and review. Humans still decide which spec findings and task drafts become
committed state.

## Goals

- Settle one normative lifecycle order and make every full-task skill and built-in
  task prompt lifecycle-complete against it.
- Provide a portable autonomous loop without shipping parallel Bash and
  PowerShell implementations or adding provider-specific adapters.
- Keep unattended execution fail-closed: one bad, blocked, stale, or incomplete
  iteration stops before another task starts.
- Separate task lifecycle status from optional unattended-execution policy through
  a small, inspectable `run` / `hold` / `skip` queue.
- Make workflow prompts a versioned product surface that can be listed, inspected,
  rendered deterministically, and replaced locally.
- Improve spec-to-task decomposition with requirement traceability, explicit
  verification planning, and a fresh adversarial review before `import --apply`.
- Productize the consistency, gaps, additions, and adversarial review lenses used
  after authoring a spec and before decomposing it.
- Extend behavioral contract checks across both shipped skills and built-in
  prompts so their command and lifecycle instructions cannot silently drift from
  the CLI.
- Keep all semantic review advisory and draft-only until a human explicitly
  adopts a finding or applies a task draft.

## Potential Features

### Canonical Transition Order

Define one normative order for a tracked-work run in
`docs/workflow/autonomous-contract.md`, and cite that contract from the skills,
built-in prompts, `AGENTS.md`, and tests rather than inventing a different order in
each surface.

Success branch:

```text
validate -> start -> implement -> local checks -> complete -> verify --result pass
```

Cannot-proceed branch:

```text
validate -> start -> block --reason -> verify --result fail -> stop
```

Rework branch (findings exist but the task stays runnable):

```text
validate -> start -> verify --result fail -> stop (task remains in_progress)
```

Requirements:

- `complete` precedes `verify --result pass`. Verification records the outcome of
  an already-finished implementation; it does not decide or perform the lifecycle
  transition.
- `complete` is never called when the verification result will be `fail`. A
  failing run ends `blocked` with a reason or stays `in_progress` for deliberate
  rework, never `completed`.
- A blocked run never calls `complete`, and `verify --result fail` is never
  described as the operation that blocks a task.
- Here "terminal branch" means that the current autonomous run ends. `blocked`
  remains a reversible Taskrail status through `unblock`; this version does not
  redefine it as immutable delivered history.
- Follow-up tasks may be created before `complete` with `task new` or during
  verification with `verify --create-followup`. Both paths re-project the state
  counts through an existing CLI writer.
- A full-task skill or built-in task prompt must name both the success and
  cannot-proceed branches. Prose such as "finish as completed or blocked" does
  not satisfy the contract.

### Lifecycle-Complete Skill Flows

Rewrite `autonomous-backlog` and `autonomous-task` to use explicit commands for
both terminal branches.

Requirements:

- The success branch invokes
  `${TASKRAIL:-taskrail} complete <task-id> --note "..."` before
  `${TASKRAIL:-taskrail} verify <task-id> --result pass --summary "..."`.
- The cannot-proceed branch invokes
  `${TASKRAIL:-taskrail} block <task-id> --reason "..."` before
  `${TASKRAIL:-taskrail} verify <task-id> --result fail --summary "..."`, then
  stops.
- The cannot-proceed branch never invokes `complete`.
- Both branches preserve the Taskrail source-checkout freshness guard immediately
  before every state writer.
- `autonomous-verify` remains a separate verification workflow and may verify a
  task whose lifecycle transition already happened.
- Committed `.agents/` and `.claude/` copies are regenerated from
  `internal/taskrail/skills/` so package parity remains byte-exact.

### Workflow Prompt Catalog And Overrides

Add a read-only `taskrail prompt` command family backed by prompts embedded in the
binary separately from the packaged skill tree.

Command surface:

```text
taskrail prompt list [--json]
taskrail prompt show <prompt-id> [--builtin] [--json]
taskrail prompt render <prompt-id> [--task <id>] [--spec <version-or-path>] [--draft <path>] [--trace <path>] [--review <path>] [--json]
```

The initial prompt contract is version `v1` and contains these stable IDs:

- `task-implementation`
- `spec-consistency`
- `spec-gaps`
- `spec-additions`
- `spec-adversarial`
- `task-decomposition`
- `task-decomposition-adversarial`

Resolution requirements:

- Built-ins have a deterministic registry order. `prompt list` returns every ID,
  its prompt-contract version, and whether a local replacement exists.
- A repository may replace a built-in at exactly
  `.taskrail/prompts/v1/<prompt-id>.md`. The local file replaces the complete
  built-in; this version does not define fragment merging, inheritance, or a
  prompt-composition language.
- `prompt show` resolves the local replacement by default. `--builtin` always
  returns the embedded copy so an adopter can inspect or compare the supported
  default.
- An unknown ID, unreadable replacement, or whitespace-only replacement fails
  loudly. Taskrail never silently falls back from a broken local replacement to
  the built-in.
- `prompt render` resolves the prompt, loads the requested repository context,
  substitutes only the placeholders declared for that prompt, and rejects unknown
  or unresolved placeholders.
- A placeholder is exactly `{{NAME}}`, where `NAME` matches
  `[A-Z][A-Z0-9_]*`. Tokens are discovered and validated before substitution,
  then replaced in one non-recursive pass. Other brace text is literal. Prompt
  authors avoid a literal string matching that token grammar; `v1` defines no
  escape or template action syntax.
- `task-implementation` declares `TASK_ID`, `TASK_PATH`, `ACTIVE_SPEC_VERSION`,
  `ACTIVE_SPEC_PATH`, and `AUTONOMY_POLICY_PATH`. The four spec-review prompts
  declare `SPEC_VERSION` and `SPEC_PATH`. `task-decomposition` declares those two
  plus `TRACE_PATH`. `task-decomposition-adversarial` additionally declares
  `DRAFT_PATH` and `REVIEW_PATH`. A template may use a subset of its declared
  names; any other token fails.
- Placeholder values are UTF-8 text values and repository-relative paths, never
  embedded file contents or shell-escaped command fragments. There are no
  conditions, loops, includes, shell interpolation, or arbitrary environment
  expansion in prompt templates.
- Task prompts require `--task`; spec-review prompts require `--spec`;
  decomposition authoring requires `--spec` and `--trace`; the
  decomposition-adversarial prompt additionally requires `--draft` and `--review`.
  Requiring the subject prevents a review of the active spec when the caller meant
  to review a not-yet-active next spec.
- `--spec` accepts a version such as `v0.5.0` or its matching versioned Markdown
  file under the configured specs directory. `SPEC_VERSION` is derived from that
  filename and `SPEC_PATH` is its repository-relative path; arbitrary Markdown
  paths are rejected.
- Text `show` and `render` output the exact prompt content without decorative
  framing. JSON reports ID, prompt-contract version, source (`builtin` or
  `override`), replacement path when present, and content.
- Prompt commands are read-only and never create `.taskrail/prompts/`. Default
  `init` and `init --with-skills` do not materialize built-in prompts or local
  replacement placeholders.
- Override, spec, draft, trace, and review paths are canonicalized against the
  repository root. They must remain inside that root, resolve through no symlink,
  and name regular files when they are inputs. A draft is parsed as an
  `ImportDraft` before its path is supplied to a review prompt.
- An incompatible placeholder set, required context, or output meaning creates a
  new prompt-contract directory such as `v2`; ordinary wording improvements may
  update built-in `v1` content. A local `v1` replacement continues to replace the
  `v1` built-in after a binary upgrade until the repository changes or removes it.

Boundary: local replacement is intentionally powerful. Taskrail mechanically
enforces loop postconditions even when a replacement omits lifecycle guidance,
but it does not judge the semantic quality of adopter-authored prompt text.

### Task Implementation Prompt

The built-in `task-implementation` prompt generalizes the useful, portable parts
of the EpochFC unattended workflow without importing repository-specific test,
branch, remote, or provider policy.

Required workflow:

1. Understand the task, domain purpose, user-visible behavior, and affected
   invariants.
2. Implement the smallest safe change with a failing test first whenever
   practical.
3. Run relevant local tests and checks.
4. Run a dedicated simplification pass that preserves behavior.
5. Run a separate review pass for correctness, testing, security, error handling,
   edge cases, unnecessary complexity, and domain fit.
6. Fix concrete high- and medium-severity findings. For a test-strength finding,
   demonstrate that the strengthened test detects a deliberate regression before
   restoring the implementation.
7. Re-run relevant checks.
8. Record follow-ups, perform the canonical lifecycle branch, and report auditable
   evidence.

Additional requirements:

- Self-review and the simplification pass do not satisfy the separate review step.
  The prompt asks the external agent to use a distinct subagent or fresh review
  context when its runtime supports one; Taskrail does not inspect or certify
  reviewer identity.
- Review and re-check happen before `complete` and `verify --result pass`.
- The built-in prompt applies the same Taskrail source-checkout freshness guard as
  the packaged skills immediately before every state writer. Pinning the child to
  the loop executable does not prove that executable matches a source checkout.
- Headless execution never guesses around operator decisions, credentials,
  production data, billed resources, or live consoles. It uses the canonical
  blocked branch and stops.
- The built-in prompt asks for one logical commit that leaves the tree clean.
  Push destination, branch choice, remote CI, and release policy are repository
  concerns supplied by a local replacement when needed.
- High- and medium-priority findings may become follow-up tasks through the CLI.
  Low-priority observations remain in the report unless repository policy says
  otherwise.
- When the resolved `AUTONOMY_POLICY_PATH` exists, one iteration may create and
  add at most two follow-up tasks in total, as `run` or `hold`. Further findings
  remain in the report for human promotion after the loop. This bounds durable
  per-iteration expansion; `--max-iterations` bounds child count, not wall-clock
  duration or the eventual size of work created by separate loop invocations.

### Post-Spec Review Lenses

Ship four built-in prompt lenses and a packaged `taskrail-spec-review` skill for
the review performed after a spec draft is coherent and before task
decomposition begins.

The lenses are:

- **Consistency (`spec-consistency`)**: find contradictions among summary, goals,
  requirements, acceptance criteria, exclusions, terminology, lifecycle
  assumptions, prior-version contracts, and relevant repository documentation.
- **Gaps (`spec-gaps`)**: find missing actors, states, failure paths, negative
  cases, compatibility, migration, rollout, rollback, cleanup, observability,
  documentation, testing, operator evidence, and release acceptance.
- **Additions (`spec-additions`)**: identify high-leverage adjacent behavior or
  workflow improvements, while distinguishing a required current-version closure
  from an attractive future feature or an idea that conflicts with a non-goal.
- **Adversarial (`spec-adversarial`)**: attack assumptions, unsafe defaults,
  ambiguous acceptance boundaries, security and data-integrity risks, operational
  failure modes, and ways an implementation could technically satisfy the words
  while missing the product intent.

Workflow requirements:

- Each lens reads the exact selected spec and relevant current repository
  contracts. A not-yet-active spec is selected explicitly with `--spec`.
- Each finding includes a severity, concrete evidence (preferably file and
  heading), impact, recommended disposition, and scope target: current version,
  future version, or reject.
- Each lens report records the selected repository-relative spec path and its
  SHA-256 digest. If the spec changes between lenses, later results are not
  represented as one review of a single snapshot; the affected lenses are rerun
  against the final digest or explicitly listed as stale.
- The additions lens is not a license for silent scope growth. Every accepted
  addition requires an explicit spec edit and version decision.
- The skill runs lenses as separate review contexts when the agent runtime
  supports that operation. One lens's conclusions are not supplied as facts to
  the next lens before it performs its own read.
- The lenses produce advisory findings only. They never edit a spec, activate a
  version, create a task, or make `validate` fail.
- A human resolves or rejects the findings and edits the spec deliberately before
  decomposition. The final disposition records accepted, rejected, deferred, and
  still-open findings; decomposition does not begin with unresolved high- or
  medium-severity findings.

The semantic `spec-gaps` lens is distinct from `coverage --gaps`. The prompt
reviews a spec's meaning before or during planning; `coverage --gaps` remains the
mechanical count-and-graph report over an existing active-spec task graph.

### Adversarial Spec-To-Task Decomposition

Strengthen `taskrail-decompose` from a single authoring pass into a reviewed draft
workflow while retaining the existing `ImportDraft` schema and `import --apply`
writer.

Author pass:

1. Select the intended spec explicitly and read it in full, including goals,
   acceptance, cautions, and exclusions.
2. For the active spec, use `coverage --json` to identify uncovered areas. For a
   not-yet-active spec, enumerate its live anchors with `spec show --anchors` and
   inspect existing tasks before drafting to prevent duplication.
3. Write a caller-chosen trace sidecar passed through `--trace`. It is one JSON
   object with `schema_version: 1`, repository-relative `spec_path`, `spec_sha256`,
   and a `requirements` array. Each requirement records a stable heading plus
   quoted requirement or line range, the covering draft task keys, and either
   disposition `task` or `no-task` with a non-empty rationale.
4. Produce one `ImportDraft` schema version 1 with focused outcomes, real
   `spec_ref` anchors, clear acceptance criteria, verification notes, and only true
   dependency edges. Do not apply it. Every normative requirement appears in the
   trace; an untraced requirement is a failed author pass, not an implicit choice.

The trace-sidecar fields are exact: `schema_version` is integer `1`; `spec_path`
is a string; `spec_sha256` is a lower-case 64-hex string; and `requirements` is a
non-null array of objects with string `ref`, non-null string array `task_keys`,
`disposition` (`task` or `no-task`), and non-empty string `rationale`.

The author prompt checks for:

- user-visible and end-to-end outcomes rather than a layer-by-layer ticket dump;
- error, boundary, and negative cases;
- testing depth, manual or operator evidence, documentation, migration, rollout,
  rollback, cleanup, security, privacy, and observability where relevant;
- tasks that are too broad, too small to be independently meaningful, or duplicate
  existing work;
- implementation tasks that violate cautions or explicit non-goals; and
- operator-only or credential-gated work that should later receive `hold` policy.

`ImportDraft` body contract:

- `TaskDraft.body`, already present in schema version 1, becomes the complete
  reviewed Markdown body written beneath the generated task heading. A
  decomposition task uses it for description, acceptance, verification notes,
  and implementation notes rather than emitting detail the writer discards.
- `import --apply` preserves every non-empty reviewed body through task creation.
  It rejects a body that contains frontmatter or a top-level task heading, or
  omits the standard `## Description`, `## Acceptance`, and
  `## Verification Notes` sections. An absent body keeps the existing scaffold
  behavior for generic imports.
- This activates a dormant schema-v1 field; it does not add an unknown field or
  require an `ImportDraft` version bump. Tests prove the exact reviewed body
  reaches the created task rather than being replaced by TODO sections.

Adversarial pass:

1. Render `task-decomposition-adversarial` with the same selected spec and the
   exact draft and trace paths plus a caller-chosen `--review` output path.
2. Give it to a fresh review process or fresh agent context that has not received
   the author's chain of reasoning.
3. Challenge omissions, overlap, false sequencing, cycles, broad tasks, shallow
   acceptance, unverifiable outcomes, hidden operator dependencies, non-goal
   violations, and technically complete task sets that fail to deliver the spec's
   end-to-end intent.
4. Write one JSON review sidecar with `schema_version: 1`, selected spec, draft,
   and trace paths and SHA-256 digests, review-context mode, and `findings`. Each
   finding records severity, evidence, impact, disposition, and rationale. The
   adversary never applies the draft or creates tasks.
5. The author or human resolves every high- and medium-severity finding and
   updates the draft, trace, and review disposition. Material task-graph changes
   receive a second adversarial pass; two adversarial passes are the maximum for
   one decomposition session. If high- or medium-severity findings remain after
   that, do not apply the draft.
6. A human reviews the final JSON draft, trace, and disposition report. The final
   review records the final draft and spec SHA-256 digests.
7. Apply with `taskrail import --apply <draft.json> --expect-sha256 <digest>`.
   `--expect-sha256` compares the exact draft bytes before any write and refuses a
   mismatch, mechanically binding the reviewed draft to the existing single
   writer. Then run `validate` and the relevant coverage report.

The review-sidecar fields are exact: integer `schema_version: 1`; string
`spec_path`, `draft_path`, and `trace_path`; lower-case 64-hex `spec_sha256`,
`draft_sha256`, and `trace_sha256`; `context_mode`
(`fresh-process`, `fresh-context`, or `same-context`); and non-null `findings`.
Each finding has `severity` (`high`, `medium`, or `low`), string `finding`,
non-null string array `evidence`, string `impact`, `disposition` (`open`,
`resolved`, `rejected`, or `deferred`), and non-empty string `rationale`. The
human disposition adds `final_spec_sha256` and `final_draft_sha256`.

These sidecars are prompt/skill handoff contracts, not new Taskrail state schemas.
The `taskrail-decompose` skill refuses to recommend apply while trace entries or
high/medium findings remain open; the binary mechanically enforces only the exact
draft digest supplied to `--expect-sha256`.

"Fresh" is intentionally bounded to a new local process or agent context. The
review sidecar states whether that condition was met. Taskrail does not claim that
two invocations use different models, providers, accounts, or independent
server-side reasoning; a same-context fallback is labeled as such and requires
explicit human acceptance rather than being reported as independent review.

### Optional Autonomous Run Policy

When present, `<planning-dir>/AUTONOMY.tsv` separates curated unattended policy
from lifecycle status. In the default layout this is `planning/AUTONOMY.tsv`.

Format:

```text
# comments are allowed
run<TAB>T-123<TAB>safe unattended implementation
hold<TAB>T-124<TAB>requires an operator credential
skip<TAB>T-125<TAB>parked for provenance
```

Parsing requirements:

- The file is UTF-8 without a byte-order mark and at most 1 MiB. LF and CRLF line
  endings are accepted and normalized for parsing.
- Blank lines are ignored. A comment begins when the first non-space character is
  `#` and occupies the rest of that line.
- Every data line has exactly three tab-separated fields. Policy and task ID are
  trimmed of surrounding ASCII space; the rationale is trimmed, non-empty, and
  contains no tab or control character. Policy values are lower-case and
  case-sensitive.
- Parse and validation errors name the repository-relative path and line number.
  Postflight compares parsed rows and their relative order, so an LF/CRLF-only
  rewrite does not masquerade as a policy change.

Static validation requirements:

- Allowed policies are exactly `run`, `hold`, and `skip`. Task IDs are unique and
  reasons are non-empty. Every referenced task exists.
- Open `run` and `hold` rows belong to the active spec. Completed and cancelled
  rows are retired history and may remain after activation; a `skip` row may also
  point elsewhere so a repository can retain explicit parked-work provenance.
- The file owns only curated order and unattended policy. Task files remain the
  source of lifecycle status, priority, dependencies, and spec linkage. The runner
  never writes lifecycle status into the policy file.
- For an open `run` task, every unresolved dependency appears earlier as `run` or
  `hold`; an unresolved dependency that is absent, later, or `skip` is invalid.
  A cancelled dependency is also invalid because only `completed` resolves an
  eligibility edge; bypassing its retired policy row must not strand later work.
- While the file exists, active-spec tasks absent from it are outside unattended
  selection. This makes the policy an allowlist, not merely a sorting hint.
- `taskrail validate` validates the optional file when present. `taskrail loop
  --dry-run` also reports the resolved queue, task statuses, first action, and any
  policy violation without launching a child or writing state.
- Taskrail never creates `AUTONOMY.tsv` during default `init`. Repositories that do
  not need curated policy continue to use normal active-spec selection.

Runtime row semantics:

| Policy | `todo` | `in_progress` | `blocked` | `completed` / `cancelled` |
|--------|--------|---------------|-----------|---------------------------|
| `run` | launch only when dependency-eligible | stop non-zero for deliberate recovery | stop cleanly with blocker handoff | bypass |
| `hold` | stop cleanly with operator handoff | stop non-zero for deliberate recovery | stop cleanly with blocker handoff | bypass |
| `skip` | bypass | global active-task preflight still stops non-zero | bypass | bypass |

The scanner evaluates rows in order after bypassing retired and `skip` rows. It
never jumps past the first `hold`, blocked row, or recovery condition. A selected
`run` task may legitimately become blocked during its child process: the policy
remains structurally valid, postflight recognizes a fresh blocked/fail tuple, and
the row becomes a blocker handoff on the next dry run.

Writer integration:

- `task rename` atomically rewrites a matching policy task ID with its dependency
  and `STATE.md` references, preserving policy, rationale, and position.
- `spec activate` refuses before writing when unfinished `run` or `hold` rows
  would point away from the target spec. Its error directs the operator to finish,
  remove, or deliberately park those rows first. Terminal historical and `skip`
  rows do not block activation.
- `task repoint` refuses an open repoint that would leave a `run` or `hold` row
  off the active spec. Policy remains human-authored; these commands preserve
  validate-clean state rather than silently changing policy intent.

### Layout Compatibility And Upgrade

The recognized autonomy policy changes how work is selected, so an older binary
must not silently ignore it.

Requirements:

- `v0.5.0` raises the supported layout version to `2`. The existing version-aware
  `init` flow previews and applies the `1 -> 2` marker migration without creating
  an autonomy policy or prompt override.
- `AUTONOMY.tsv` is accepted only in a layout-2 repository. The v0.5 binary tells a
  layout-1 repository to run the normal `init --apply` upgrade before using it.
- Once upgraded, older Taskrail binaries refuse the newer layout through the
  existing command-wide compatibility guard instead of ignoring its selection
  policy.
- Upgrade documentation requires refreshing installed skills explicitly with
  `taskrail init --with-skills --force`; default init remains non-destructive.
- Automated and manual upgrade acceptance covers a v0.4 layout and skills moving
  to v0.5, an older binary refusing layout 2, and a v0.5 binary honoring the same
  policy before and after skill refresh.

### Cross-Platform Autonomous Loop

Add a foreground generic process runner:

```text
taskrail loop [--max-iterations <n>] [--dry-run] -- <command> <args...>
```

Execution contract:

- The child command is required for execution and is passed as an argument vector
  directly to the operating system. Taskrail never joins it into a shell string,
  evaluates shell syntax, or names a supported provider.
- A bare executable name resolves through the inherited `PATH`. A path containing
  a separator resolves against the caller's original working directory before the
  child cwd changes to the repository root, then is passed as an absolute path.
- `--max-iterations` is a positive integer and defaults to `1`. There is no
  unlimited value. A caller opts into a longer run explicitly.
- `--dry-run` rejects a child command, performs all read-only repository and policy
  checks, and supports `--json`. Its result has action `run`, `hold`, or `none`,
  plus reason, policy summary, violations, and selected task. It includes prompt
  source, SHA-256, and rendered content only for `run`; hold and no-work results
  do not fabricate a selected task or prompt. Valid hold and no-work results exit
  zero; invalid repository or policy results exit non-zero.
- The loop runs from the repository root and launches one fresh child process per
  selected task. It writes the exact UTF-8 rendered prompt bytes to child stdin,
  adds no framing or newline, closes stdin immediately, and streams child stdout
  and stderr to the corresponding Taskrail streams. Stream-copy failure fails the
  iteration. A provider CLI that cannot consume a finite stdin prompt requires a
  caller-supplied adapter process.
- The child inherits the environment because provider authentication and toolchain
  setup are caller-owned trusted-process concerns. The loop unconditionally sets
  child `TASKRAIL` to the canonical absolute path of the currently running
  executable; an inherited conflicting override is reported in dry-run output but
  cannot redirect child state writers. The built-in prompt describes this as the
  platform-neutral executable in `TASKRAIL`, not as POSIX shell syntax.
- `loop` has no `--json` execution mode because streamed child output cannot form
  one valid Taskrail JSON document.
- `--max-iterations` bounds child count only. This version has no wall-clock
  timeout. On interruption, Taskrail closes stdin, forwards the platform's normal
  termination request to an isolated Unix process group or sends a best-effort
  `CTRL_BREAK_EVENT` to a Windows process group, waits a 10-second grace period,
  then terminates the remaining tree through that process group or a Windows job
  object. It waits for exit, reports non-zero, and never selects another task.

Selection contract:

- Require the Git CLI, a non-bare worktree with `HEAD`, and a Taskrail repository
  root equal to that worktree root. Acquire an exclusive local loop lock in the
  Git common directory before preflight and hold it through final postflight. A
  second loop refuses before selecting work. A lock left by an abruptly killed
  process is never cleared automatically; the error names its metadata and the
  manual inspect-and-remove recovery.
- Before the first child and between every iteration, run the same repository
  validation used by `taskrail validate` without writing state.
- Refuse to begin with a dirty working tree or an existing `in_progress` task.
  "Clean" means `git status --porcelain=v1 --untracked-files=all
  --ignore-submodules=none` reports no
  staged, unstaged, untracked, or submodule change; ignored verification artifacts
  remain ignored by Git. Recovery or continuation of interrupted work is
  deliberate human work, not an automatic retry hidden inside the loop.
- If `AUTONOMY.tsv` exists, select through its policy and barrier rules. Otherwise
  use the same read-only active-spec eligibility and ranking as `status`.
- No eligible task or a `hold` barrier is a clean stop and launches no child.
- Capture the selected task ID, task ledger, active spec, canonical verification
  summary, current branch, `HEAD`, policy rows, and resolved prompt source/content
  SHA-256 before launch. The same resolved template bytes are used for every
  iteration in one invocation and rendered with each selected task's context; a
  child may commit a replacement, but it cannot affect a later task until a human
  starts a new loop.

Postflight contract:

- A non-zero child exit stops immediately and makes `loop` exit non-zero after
  collecting the same repository diagnostics used for any failed postflight.
- A fresh verification consists of both a changed canonical state summary with
  exact grammar `<pass|fail> for <task-id> at <RFC3339-UTC>` and a verification
  `report.json` created after child launch whose task, result, and generated time
  match. An old same-task pass or fail never satisfies postflight.
- After a zero child exit, re-run validation and require the selected task to be
  `completed` with a fresh matching pass.
- A selected task that became `blocked` with a new non-empty blocker and fresh
  matching fail is an honest outcome, but not a successful iteration: report the
  blocker, exit non-zero, and do not select another task. An `in_progress` task
  with a fresh fail is reported as deliberate rework and likewise stops non-zero.
- Blocked and rework classifications still require a valid policy and clean tree;
  otherwise the report names both the lifecycle outcome and the unresolved
  repository failure.
- A task left `todo` or `in_progress`, a stale or mismatched verification result,
  an invalid policy edit, or any other no-progress result stops non-zero rather
  than launching the same work again.
- Require a clean working tree after a successful iteration. The built-in prompt
  asks the agent to commit the logical task outcome; Taskrail does not require a
  particular branch, remote, push, commit message, or exact commit count.
- A successful iteration remains on the captured branch, advances `HEAD` by at
  least one commit with the captured `HEAD` as an ancestor, and keeps the active
  spec unchanged. Existing tasks other than the selected task retain their IDs,
  statuses, spec refs, and dependencies; newly created follow-ups are the allowed
  ledger expansion.
- When a policy file exists, every pre-existing row retains its ID, policy,
  rationale, and relative order. Additions are limited to at most two tasks
  created during this iteration and linked as follow-ups of the selected task.
  A new row is inserted immediately before the first existing row it blocks; if
  it blocks none, `run` is inserted after the last existing `run` before the first
  `hold`, while `hold` is inserted after existing runnable work. Any other policy
  mutation stops before another child.
- The resolved prompt hash is unchanged for the invocation. If the committed
  replacement changed, report that it will take effect only after a new
  human-started loop and stop before another iteration.
- Only after every postcondition passes may the loop select another task. It stops
  successfully after the configured iteration cap even when runnable work remains
  and reports that remaining work.

Safety boundary:

- `loop` is foreground-only and sequential. The local Git-common-directory lock
  prevents two loops, including linked worktrees, from launching concurrently.
  This is not a distributed lease and does not coordinate separate clones.
- Taskrail does not inspect child conversations, tool calls, model output, review
  identity, token use, or provider state. Its evidence is process exit plus the
  repository contracts it already owns.
- Taskrail does not commit, push, merge, open pull requests, wait for remote CI, or
  reset failed work. Repositories express delivery policy in their prompt
  replacement and external automation.
- Every non-clean stop reports task ID, child exit or signal, lifecycle status,
  verification before/after, Git status, policy result, and safe next actions.
  Recovery is manual inspection followed by the existing `complete`, `block`,
  `unblock`, `verify`, and Git operations as appropriate; Taskrail never resets or
  rewrites the failed child outcome automatically.

### Skill And Prompt Behavioral Contract Tests

Extend the existing shippable-skill checks into one behavioral contract over the
shipped skills and built-in prompts, while retaining byte parity as a separate
packaging guarantee.

Requirements:

- **Command existence**: every backticked `${TASKRAIL:-taskrail} <subcommand>`
  invocation in a shippable skill, and every platform-neutral Taskrail command
  invocation in a built-in prompt, resolves to a real CLI command path.
- **Lifecycle branches**: every full-task skill and the built-in task prompt place
  `complete` before `verify --result pass`, place `block --reason` before
  `verify --result fail`, and contain no `complete` in the cannot-proceed branch.
  The lifecycle instructions live in delineated canonical blocks with golden and
  negative fixtures; unrelated examples elsewhere in a document cannot satisfy a
  global substring check.
- **Terminal reachability**: a skill or prompt that starts a task names at least
  one real terminal transition and describes both unattended outcomes.
- **Review ordering**: the task prompt requires review and re-check before
  completion; the decomposition skill and prompts require the adversarial pass
  before `import --apply`.
- **Read-only lenses**: post-spec prompts contain no instruction to activate a
  spec, create a task, apply a draft, or hand-edit machine-managed state.
- **Provider independence**: built-in prompts and packaged skills invoke no named
  model API or provider CLI. Provider commands appear only as user-supplied
  `taskrail loop -- ...` examples in orientation documentation.
- **Registry coverage**: every embedded skill and prompt is declared and tested by
  construction; an undeclared embedded directory fails the package check.
- **Override boundary**: behavioral checks cover supported built-ins, not arbitrary
  repository replacements. Prompt resolution tests still reject unknown, empty,
  unreadable, symlinked, outside-repository, or path-traversing replacements and
  subjects. Tests cover token grammar, one-pass substitution, required context,
  contract-version reporting, and replacement precedence.
- **Portable process tests**: loop tests use a Go helper process, not Bash, and
  cover argv preservation, stdin prompt delivery, repository-root cwd,
  environment and executable resolution, EOF, stream errors, interruption and
  child-tree cleanup, child failure, blocked work, fresh versus stale verification,
  no progress, iteration caps, lock contention, dirty-tree refusal, policy
  barriers and mutations, branch/HEAD continuity, and postflight validation on
  all supported operating systems.
- **Policy tests**: parser and selection coverage includes LF/CRLF, comments,
  malformed fields, line-numbered diagnostics, every policy/status combination,
  dependency ordering, terminal historical rows, rename rewriting, repoint and
  activation refusal, and layout-1 downgrade protection.
- **Decomposition tests**: a non-empty schema-v1 `TaskDraft.body` round-trips into
  the created task, prompt/skill fixtures require exact sidecar fields and refuse
  to recommend apply with open high/medium findings, and `--expect-sha256` refuses
  before writing when draft bytes changed.
- Existing skill-package parity remains unchanged: committed `.agents` and
  `.claude` copies equal the package source, and installed copies differ only by
  the supported version marker.
- `README.md`, `AGENTS.md`, `docs/workflow/autonomous-contract.md`,
  `human-workflow.md`, `agent-steering.md`, `skills-overview.md`, and
  `skills-productization.md` cite the canonical order and document loop, prompt,
  policy, upgrade, recovery, and skill behavior without contradictory copies.
  `CHANGELOG.md` records the user-visible commands and files when implemented.
- Manual sandbox evidence covers a multi-iteration success, operator hold,
  blocked/fail outcome, stale verification refusal, interrupted child recovery,
  local prompt replacement, adversarial decomposition handoff, and v0.4-to-v0.5
  upgrade. Packaged binary smoke checks exercise Linux, macOS, and native Windows
  cwd, argv, environment, and interruption behavior.

### Verify Lifecycle Advisory

`verify --result pass` emits a non-gating advisory warning when the target task is
not `completed`.

Requirements:

- The warning names the task, its current status, and the expected order. It is
  advisory: `verify` still writes artifacts, records the result, and exits zero.
- Human-readable mode writes the warning to stderr. `--json` keeps stdout valid and
  includes the same signal in a structured, non-null `warnings` array.
- It covers every non-`completed` status, not only `in_progress`.
- It never makes `validate` fail and never changes task status.
- `verify --result fail` emits no corresponding warning: `blocked` and
  `in_progress` are both valid targets for a failing result.

## Caution

Do not turn `v0.5.0` into a general agent framework.

The loop is intentionally one foreground process repeated sequentially over
deterministic Taskrail state. The prompt system is intentionally a versioned
lookup, strict substitution, and local whole-file replacement. The review lenses
are intentionally advisory. Resist adding provider configuration, prompt graph
execution, retries, background operation, model-output parsing, automatic
planning writes, or semantic validation under these names.

The optional autonomy policy also must not become a second task database. It
contains only order, `run` / `hold` / `skip`, and a rationale. Status,
dependencies, priority, spec linkage, title, acceptance, and verification stay in
the existing task and state files.

Local prompt replacement can remove supported guidance. That is an explicit
repository choice, not a reason to merge prompt fragments implicitly. Universal
loop safety belongs in mechanical preflight and postflight checks; semantic and
delivery policy belongs in prompt text.

## Recommendation About LLM Support

Do not add direct LLM calls to Taskrail core.

`taskrail loop` starts a caller-supplied executable; it does not know whether that
process is a coding agent, a deterministic test double, or another local tool.
`taskrail prompt` emits text; it does not send that text to a provider. The
judgement-heavy parts of spec review and decomposition remain in prompts and
skills, while the binary provides deterministic inputs, validation, and reviewed
write paths.

This preserves the established order: repo-native CLI and file model first,
prompts and skills for external agents second, and no provider adapter until a
separate future spec demonstrates that one is necessary.

## Explicitly Excluded

Continue to exclude:

- direct model or provider API calls from the Taskrail binary;
- named provider adapters, provider configuration, model selection, token or cost
  management, and conversation/session persistence;
- shell-string evaluation or a shell-script runtime inside `loop`;
- background daemons, schedules, retries, worker pools, parallel task execution,
  distributed leases, and multi-agent coordination;
- skill interpretation, skill graphs, conditional workflow execution, or a
  general prompt-composition language;
- automatic continuation of an existing `in_progress` task;
- Git commits, pushes, merges, pull requests, remote-CI waiting, force operations,
  or rollback performed by Taskrail;
- semantic enforcement of independent reviewer identity or different model use;
- automatic spec edits, spec activation, task creation, or `import --apply` from a
  review or decomposition prompt;
- turning semantic spec findings into `validate` errors or conflating
  `spec-gaps` with mechanical `coverage --gaps`;
- a second lifecycle or dependency schema in `AUTONOMY.tsv`;
- `verify` performing a lifecycle transition or hard-rejecting a misordered run;
- `reopen` / `uncomplete` recovery semantics; and
- historical run databases, committed conversation logs, or required persistent
  execution receipts.

The narrow exception to prior automatic-loop and orchestration exclusions is the
explicit foreground `taskrail loop -- <command> <args...>` boundary specified
above. It selects deterministically, renders one supported prompt, launches one
opaque external process, verifies repository postconditions, and repeats only up
to a finite caller-visible limit. Nothing broader is implied.
