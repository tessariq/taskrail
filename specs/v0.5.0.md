# Taskrail v0.5.0

## Summary

Taskrail `v0.5.0` adds **autonomous workflow integrity and reviewable planning**.

Through `v0.4.0`, Taskrail established deterministic task state, active-spec
selection, reviewable import drafts, structural coverage and gap reports, and a
packaged skill set. Adopters can drive those primitives with an external coding
agent, but Taskrail does not yet provide a portable outer loop or a reusable
workflow-prompt surface. Repositories therefore assemble their own shell runner,
queue policy, prompts, and post-run checks. Those copies are useful, but they
drift and are commonly platform- or provider-specific.

The existing skill contract also has a concrete lifecycle defect. The packaged
`autonomous-backlog` and `autonomous-task` skills run `verify` and then say, in
prose, to finish as `completed` or `blocked`; neither invokes `complete` or
`block`. Because `verify` is not a lifecycle transition, a nominally successful
run can remain `in_progress`, and a run that cannot proceed can leave no recorded
blocker.

This version fixes that lifecycle contract and builds on it in four bounded ways:

- a cross-platform, foreground `taskrail loop` command that starts one fresh,
  caller-supplied external process per task and fails closed between iterations;
- a versioned catalog of built-in workflow prompts with deterministic rendering,
  repository-local replacement, and outcome-focused task authoring;
- stronger prompt and skill workflows for post-spec review and adversarial
  spec-to-task decomposition before any draft is applied; and
- report-only adversarial workflow testing with compact cross-run memory of
  findings and tested surfaces.

Taskrail still does not call a model, know about model providers, interpret a
skill, or silently write judgement-derived planning state. The binary owns the
mechanical boundary: selection, policy validation, prompt resolution, process
execution, and postconditions. The external agent owns semantic implementation
and review. Humans still decide which spec findings and task drafts become
committed state.

## Goals

- Settle one normative lifecycle order and make every full-task skill and built-in task prompt lifecycle-complete against it.
- Provide a portable autonomous loop without parallel shell implementations or provider-specific adapters, and stop before another task after any bad, blocked, stale, or incomplete iteration.
- Separate lifecycle status from optional unattended policy through a small, inspectable `run` / `hold` / `skip` queue.
- Make workflow prompts versioned, deterministic, inspectable, and locally replaceable.
- Make task bodies outcome-focused and give acceptance criteria concrete but implementation-neutral verification designs.
- Improve decomposition with requirement traceability, explicit verification planning, and a fresh adversarial review before `import --apply`.
- Productize post-spec consistency, gaps, additions, and adversarial lenses plus post-implementation workflow-adversarial review.
- Add opt-in active-spec statistics without hiding repository-wide history by default.
- Test shipped skills and built-in prompts behaviorally so their commands, lifecycle, authoring, and review instructions cannot drift from the CLI.
- Keep semantic findings advisory and reviewable until a human adopts one or applies a task draft.

## Potential Features

### Canonical Transition Order

Define one normative order for a tracked-work run in
`docs/workflow/autonomous-contract.md`, and cite that contract from the skills,
built-in prompts, `AGENTS.md`, and tests rather than inventing a different order in
each surface.

Recognized branches:

```text
completed-pass: validate -> start -> implement -> checks -> complete -> verify pass
blocked-fail: validate -> start -> block --reason -> verify fail -> stop
rework-fail: validate -> start -> verify fail -> stop (remains in_progress)
```

Requirements:

- `complete` precedes `verify --result pass`; verification records an already-finished implementation and neither decides nor performs its lifecycle transition.
- `complete` is never called for a failing or blocked run. Failure leaves the task `blocked` with a reason or `in_progress` for deliberate rework; `verify --result fail` is never described as blocking it.
- "Terminal branch" means the current autonomous run ends. `blocked` remains reversible through `unblock`, not immutable delivered history.
- Follow-ups may be created before `complete` with `task new` or during verification with `verify --create-followup`; both existing writers re-project state counts.
- A full-task skill or built-in task prompt names both success and cannot-proceed branches; "finish as completed or blocked" is insufficient.
- Every writer's exit is checked before the next command. If `complete` succeeds but passing `verify` fails to execute, stop as `completed-unverified` and rerun only passing verification after inspection; never repeat `complete` or compensate with `block`. If a later independent audit records fail on completed work, keep delivered history completed, create a follow-up when action is required, and report `completed-audit-fail` rather than rework/block.
- `complete` records non-empty random lower-case 32-hex task `completion_id`. Verification records task `last_verification_id`, `last_verification_result`, and optional `last_verified_completion_id`; state adds `last_verification_id` and optional `last_verified_completion_id`; verify JSON/report use `verification_id`, `result`, and optional `observed_completion_id`. The task note is `- <time>: verification <result> id <verification-id> completion <id|none>`, and artifacts use `<timestamp>-<verification-id>`. A current pass requires completed status, non-empty completion ID, and equal non-empty observed ID across all surfaces.
- A first post-upgrade pass over legacy completed history atomically adopts a new completion ID and binds it; a fail records no observed completion and does not adopt. Passing/failing verification before completion uses `none`. Legacy completed work remains delivered for compatibility but is not a current bound pass until adoption.
- The canonical state summary is `<pass|fail> for <task-id> at <RFC3339-UTC> id <verification-id>`. Freshness requires an ID absent from the preflight artifact/summary snapshot and exact agreement across state, task note, and `report.json`; wall-clock order alone is insufficient.

### Lifecycle-Complete Skill Flows

Rewrite `autonomous-backlog` and `autonomous-task` to use explicit commands for
both terminal branches.

Requirements:

- The success branch invokes `${TASKRAIL:-taskrail} complete <task-id> --note "..."` before `${TASKRAIL:-taskrail} verify <task-id> --result pass --summary "..."`.
- The cannot-proceed branch invokes `${TASKRAIL:-taskrail} block <task-id> --reason "..."` before `${TASKRAIL:-taskrail} verify <task-id> --result fail --summary "..."`, never invokes `complete`, and then stops.
- Both branches preserve the Taskrail source-checkout freshness guard immediately
  before every state writer.
- `autonomous-verify` remains a separate verification workflow and may verify a
  task whose lifecycle transition already happened.
- Regenerate committed `.agents/` and `.claude/` copies from `internal/taskrail/skills/` so package parity remains byte-exact.

### Workflow Prompt Catalog And Overrides

Add a read-only `taskrail prompt` command family backed by prompts embedded in the
binary separately from the packaged skill tree.

Command surface:

```text
taskrail prompt list [--json]
taskrail prompt show <prompt-id> [--contract <version>] [--builtin] [--json]
taskrail prompt render <prompt-id> [--contract <version>] [--task <id>] [--spec <version-or-path>] [--spec-review <path>] [--draft <path>] [--trace <path>] [--memory <path>] [--review <path>] [--json]
```

The initial prompt contract is version `v1` and contains these stable IDs:

- `task-implementation`
- `task-authoring`
- `spec-consistency`
- `spec-gaps`
- `spec-additions`
- `spec-adversarial`
- `task-decomposition`
- `task-decomposition-adversarial`
- `workflow-adversarial`

Resolution requirements:

- Built-ins have deterministic registry order; `prompt list` returns every ID, contract version, and whether a local replacement exists.
- `show`/`render` default to the newest contract supported for that ID; `--contract v1` selects exactly one retained version and its `.taskrail/prompts/v1/` override. Unknown ID/version pairs fail. Adding v2 never changes, migrates, or shadows explicit v1 resolution; list reports every supported pair.
- A repository may replace a complete built-in only at `.taskrail/prompts/v1/<prompt-id>.md`; there is no merging or composition language. Replacements are UTF-8 without BOM, non-empty, and at most 256 KiB. `prompt show` resolves one by default, `--builtin` returns embedded bytes, and any invalid replacement fails without fallback.
- `prompt render` loads requested context, substitutes only declared placeholders, and rejects unknown or unresolved tokens. A token is exactly `{{NAME}}` with `NAME` matching `[A-Z][A-Z0-9_]*`; validation precedes one non-recursive substitution pass. Other braces are literal, authors avoid literal token-shaped text, and `v1` has no escape or action syntax.
- Exact declarations are: `task-implementation`: `TASK_ID`, `TASK_PATH`, `ACTIVE_SPEC_VERSION`, `ACTIVE_SPEC_PATH`, `AUTONOMY_POLICY_PATH`; `task-authoring`: `TASK_ID`, `TASK_PATH`, `SPEC_VERSION`, `SPEC_PATH`; each spec lens: `SPEC_VERSION`, `SPEC_PATH`, `REVIEW_PATH`; `task-decomposition`: `SPEC_VERSION`, `SPEC_PATH`, `SPEC_REVIEW_PATH`, `TRACE_PATH`, `DRAFT_PATH`; `task-decomposition-adversarial`: those five plus `REVIEW_PATH`; `workflow-adversarial`: `SPEC_VERSION`, `SPEC_PATH`, `MEMORY_PATH`, `REVIEW_PATH`. Templates may use a subset; any other token fails.
- Placeholder values are UTF-8 text and repository-relative paths, never embedded file contents or shell-escaped fragments. Templates provide no conditions, loops, includes, shell interpolation, or environment expansion.
- `task-implementation`/`task-authoring` require `--task`; each spec lens requires `--spec --review`; decomposition requires `--spec --spec-review --trace --draft`; decomposition-adversarial adds `--review`; workflow-adversarial requires `--spec --memory --review`. Undeclared context flags fail; task-authoring derives spec from the task's `spec_ref`.
- `--spec` accepts a version such as `v0.5.0` or its matching versioned Markdown file under the configured specs directory; arbitrary Markdown paths are rejected. `SPEC_VERSION` derives from that filename and `SPEC_PATH` is repository-relative. Task-derived spec context rejects a missing or invalid reference.
- Text output is exact content. `list --json` emits ordered `{id,contract_version,source,replacement_path}` entries without bodies; `show/render --json` emit that metadata plus `content` and SHA-256. Empty lists are `[]`; absent replacement paths are omitted.
- Prompt commands are read-only and never create prompt, memory, or review files. Neither init mode materializes built-ins or placeholders.
- Durable outputs are confined under `<planning-dir>/reviews/spec/<version>/<session-id>/`, `reviews/decomposition/<version>/<session-id>/`, or `reviews/workflow-adversarial/`; managed state, task, spec, source, prompt, artifact, and Git paths are rejected. Canonical paths traverse no symlink/reparse point and siblings cannot alias. Prompt rendering validates only; immediately before each external publication the skill rechecks every ancestor no-follow, atomically creates without replacement in the same directory, and fails on path substitution. Adversarial decomposition consumes regular existing draft/trace inputs.
- Incompatible placeholders, required context, or output meaning require a new contract directory such as `v2`; wording may update `v1`, and a local `v1` file continues replacing it until changed or removed.

### Task Implementation Prompt

The built-in `task-implementation` prompt generalizes the useful, portable parts
of the EpochFC unattended workflow without importing repository-specific test,
branch, remote, or provider policy.

Required workflow:

1. Understand the task, domain purpose, user-visible behavior, and affected
   invariants.
2. Implement the smallest safe change with a failing test first whenever
   practical.
3. Run relevant local tests and checks.
4. Run a dedicated simplification pass that preserves behavior.
5. Run a separate review pass for correctness, testing, security, error handling,
   edge cases, unnecessary complexity, and domain fit.
6. Fix concrete high- and medium-severity findings. For a test-strength finding,
   demonstrate that the strengthened test detects a deliberate regression before
   restoring the implementation.
7. Re-run relevant checks.
8. Record follow-ups, perform the canonical lifecycle branch, and report auditable
   evidence.

Additional requirements:

- Self-review and simplification do not satisfy the separate review, which precedes `complete` and passing verification. Use a distinct subagent or fresh context when supported; Taskrail does not certify reviewer identity.
- The built-in prompt applies the same Taskrail source-checkout freshness guard as
  the packaged skills immediately before every state writer. Pinning the child to
  the loop executable does not prove that executable matches a source checkout.
- Headless execution never guesses around operator decisions, credentials, production data, billed resources, or live consoles; it blocks and stops.
- In loop delivery, perform the selected lifecycle branch first, then commit the complete implementation plus generated task/state/policy outcome, then return to postflight. Success, blocked, and rework branches all persist one reviewable local outcome; Taskrail never commits, pushes, or claims remote delivery itself.
- High- and medium-priority findings may become CLI-created follow-ups; low-priority observations remain in the report unless repository policy says otherwise.
- One iteration may create at most two follow-up tasks whether policy exists or not. With policy, add them as `run` or `hold`; otherwise leave further findings in the report. This bounds durable expansion while `--max-iterations` bounds child count, not wall-clock duration or separate invocations.

### Outcome-Focused Task Authoring

Ship a built-in `task-authoring` prompt and use this shared body contract for
scaffolded, imported, follow-up, and decomposition-generated tasks. The prompt
command remains read-only; an external agent writes a body proposal, then the
reviewed writer applies it safely:

```text
taskrail task author <task-id> --body <proposal> --expect-sha256 <task-digest> [--dry-run] [--json]
```

Requirements:

- A task states one independently meaningful user, operator, or system outcome and the invariant established, rather than a repository layer or list of files to edit.
- Authoring is pre-execution work: the prompt rejects a selected task unless its status is `todo`, so completed and cancelled history cannot be rewritten through this flow.
- Acceptance criteria are observable and name relevant actors, preconditions, state, success, failure, and boundary outcomes where they materially differ.
- `## Verification Notes` maps each criterion to setup, input or action, expected observation, and the cheapest sufficient evidence layer: unit, boundary integration, CLI/workflow, manual, or operator evidence.
- Use a public or durable boundary as the oracle. Mocks, call counts, file existence, process exit, or “the suite passes” are insufficient when the criterion concerns persisted or user-visible meaning.
- Bug fixes and high-risk behavior identify regression-sensitive evidence; when practical, a new or strengthened test is shown to fail against the prior defect or a deliberate relevant perturbation before the implementation is restored.
- Manual probes are reproducible and sandbox-first, name prerequisites and cleanup, and distinguish expected behavior from observed evidence. Non-code tasks name an equivalent inspectable check or explain why a test category is not applicable.
- Address recovery, idempotency, concurrency, security, migration, compatibility, and cleanup only when the outcome or spec makes them relevant; do not add checklist-driven scope.
- Avoid vague instructions such as “add tests” or “verify it works,” but also avoid exact functions, test filenames, mocks, or internal structure unless the public contract or known regression requires them.
- Cross-task workflows place an end-to-end criterion on a task capable of proving integrated delivery; dependency edges alone are not verification.
- `task new` scaffolding asks for planned criterion-to-evidence mapping plus later evidence paths. Task-producing built-ins and skills cite this contract, and the decomposition adversary rejects both shallow and unnecessarily implementation-bound verification notes.
- `task author` acquires the repository writer lock, rechecks exact task bytes/digest and `todo`, validates the proposal, and atomically changes only Description, Acceptance, and Verification Notes while preserving frontmatter, H1, and Implementation Notes. It re-validates and reports a selected-task-only diff; conflict or failure writes nothing.

### Post-Spec Review Lenses

Ship four built-in prompt lenses and a packaged `taskrail-spec-review` skill for
the review performed after a spec draft is coherent and before task
decomposition begins.

The lenses are:

- **Consistency (`spec-consistency`)**: find contradictions among summary, goals,
  requirements, acceptance criteria, exclusions, terminology, lifecycle
  assumptions, prior-version contracts, and relevant repository documentation.
- **Gaps (`spec-gaps`)**: find missing actors, states, failure paths, negative
  cases, compatibility, migration, rollout, rollback, cleanup, observability,
  documentation, testing, operator evidence, and release acceptance.
- **Additions (`spec-additions`)**: identify high-leverage adjacent behavior or
  workflow improvements, while distinguishing a required current-version closure
  from an attractive future feature or an idea that conflicts with a non-goal.
- **Adversarial (`spec-adversarial`)**: attack assumptions, unsafe defaults,
  ambiguous acceptance boundaries, security and data-integrity risks, operational
  failure modes, and ways an implementation could technically satisfy the words
  while missing the product intent.

Workflow requirements:

- Each lens independently reads the explicit selected spec and repository contracts and writes schema-v1 JSON to its caller-bound path. Exact fields are `schema_version`, `session_id`, `lens`, `spec_path`, lower-case `spec_sha256`, `context_mode`, `generated_at`, and non-null `findings`.
- Each finding has session-unique `finding_id`, severity (`high|medium|low`), non-empty evidence, impact, recommendation, scope (`current|future|reject`), disposition (`open|accepted|rejected|deferred`), rationale, and optional `target_version`; deferred requires a target version. High means plausible data/security/lifecycle loss, medium means material contract failure, and low means bounded quality risk.
- Fixed session outputs are `consistency.json`, `gaps.json`, `additions.json`, `adversarial.json`, and `manifest.json`. The manifest binds final spec path/digest, every lens path/digest/spec digest, generated time, and exactly one final disposition per finding ID.
- If accepted findings edit the spec, stale lenses rerun; every final lens binds one final spec digest. Accepted findings name the resulting heading, rejected findings explain why, and deferred findings name a future version. Missing lenses, digest mismatch, duplicate/missing disposition, or open high/medium findings forbids decomposition.
- Additions never silently grow scope. Lenses stay advisory and never edit/activate specs, create tasks, or gate `validate`; a human edits and approves the manifest. Separate contexts are used when supported, without supplying one lens's conclusions as facts to another.

The semantic `spec-gaps` lens is distinct from `coverage --gaps`. The prompt
reviews a spec's meaning before or during planning; `coverage --gaps` remains the
mechanical count-and-graph report over an existing active-spec task graph.

### Adversarial Spec-To-Task Decomposition

Strengthen `taskrail-decompose` into a digest-bound reviewed draft workflow. Existing `ImportDraft` schema version 1 keeps its v0.4 meaning; reviewed decomposition emits schema version 2 so older consumers cannot silently discard reviewed bodies.

Author pass:

1. Select the intended spec and final post-spec `manifest.json`; verify its digest, final spec digest, all four lens entries, dispositions, and no open high/medium finding before authoring.
2. For the active spec, use `coverage --json` to identify uncovered areas. For a
   not-yet-active spec, enumerate its live anchors with `spec show --anchors` and
   inspect existing tasks before drafting to prevent duplication.
3. Write `trace.json`: exact fields `schema_version:1`, `session_id`, canonical `spec_path`, lower-case `spec_sha256`, and non-null `requirements`. Each unique `requirement_id` has normalized `spec_ref`, exactly one source (`{"kind":"quote","text":...}` or `{"kind":"lines","start":n,"end":m}`), unique `task_keys`, disposition (`task|no-task`), and non-empty rationale. `task` requires keys; `no-task` forbids them.
4. Write `draft.json` as `ImportDraft` v2 with matching `review_session_id`. Every task has a unique key, real anchor, true dependencies, and a non-empty reviewed body following the outcome-focused contract. Every normative requirement is traced, every trace key exists, and every draft key appears in trace. Do not apply.

The author prompt checks for:

- user-visible and end-to-end outcomes rather than a layer-by-layer ticket dump;
- error, boundary, and negative cases;
- testing depth, manual or operator evidence, documentation, migration, rollout,
  rollback, cleanup, security, privacy, and observability where relevant;
- tasks that are too broad, too small to be independently meaningful, or duplicate
  existing work;
- implementation tasks that violate cautions or explicit non-goals; and
- operator-only or credential-gated work that should later receive `hold` policy.

V2 body/apply contract:

- Each body is complete Markdown beneath the generated H1 and contains exactly one `## Description`, `## Acceptance`, and `## Verification Notes`; `## Implementation Notes` is optional and lifecycle writers may add it. Frontmatter and a top-level heading are rejected. Apply preserves exact non-empty reviewed body bytes.
- V1 remains accepted with existing scaffold/body behavior. V2 apply validates and stages all task/spec/policy/state outputs under the repository writer lock and publishes all or none; partial-success semantics remain only for legacy v1.

Adversarial pass:

1. Render `task-decomposition-adversarial` with the same spec and exact draft/trace paths plus immutable `review-1.json` output.
2. Give it to a fresh review process or fresh agent context that has not received
   the author's chain of reasoning.
3. Challenge omissions, overlap, false sequencing, cycles, broad tasks, shallow
   acceptance, unverifiable outcomes, hidden operator dependencies, non-goal
   violations, and technically complete task sets that fail to deliver the spec's
   end-to-end intent.
4. Each review has exact selected spec/draft/trace paths and SHA-256s, `session_id`, `pass_number`, context mode, and non-null findings with stable ID, severity, evidence, impact, disposition, and rationale. It never applies or creates tasks.
5. Resolve findings in draft/trace. Material task, dependency, acceptance, verification, or trace change requires immutable `review-2.json` over final bytes. Two passes are the session maximum; a material change after pass 2 starts a new session rather than applying unreviewed bytes.
6. A human writes exact `manifest.json`: `schema_version:1`, `session_id`, `spec_review_manifest_path`, `spec_review_manifest_sha256`, final `spec_path/spec_sha256`, `draft_path/draft_sha256`, `trace_path/trace_sha256`, `generated_at`, `approved_at`, non-null ordered `reviews`, and non-null `dispositions`. Each review has `pass_number`, path/SHA-256, context mode, and its spec/draft/trace SHA-256s; each disposition has finding ID, severity, `resolved|rejected|deferred`, and rationale. High/medium cannot defer.
7. Apply with `taskrail import --apply <draft> --expect-sha256 <draft-digest> --review-manifest <manifest> --expect-review-sha256 <manifest-digest>`. Before any write, the binary validates v2/session identity, all exact digests, trace/draft referential integrity, final review inputs, and dispositions. Then validate and report coverage.

V2, trace, review, and manifest decoders reject unknown/missing fields, null where non-null is required, non-lowercase/non-64-hex digests, duplicate IDs/keys/passes, and unordered pass numbers. These tracked session files are review handoffs, not lifecycle state. Commit the final spec-review and decomposition session directories with imported tasks; abandoned proposals are removed before another clean workflow.

"Fresh" means a new local process/context when supported; same-context fallback is labeled and requires human acceptance. Taskrail never claims different models/providers or independent server reasoning.

### Workflow-Adversarial Review Memory

Ship a built-in `workflow-adversarial` prompt and packaged
`taskrail-workflow-adversarial` skill for serial, post-implementation testing
against an explicitly selected spec. They produce review files only: no product
code, spec, task, status, autonomy-policy, or verification-result edits, no
semantic validation gate, and no alternate `taskrail loop` mode.

Workflow requirements:

- Read the selected spec, completed tasks, implementation, tests, and prior memory before choosing one bounded surface and a fresh angle. Attack end-to-end intent, lifecycle transitions, trust boundaries, failure recovery, stale evidence, cleanup, and ways tests can pass while users fail.
- Prefer a fresh review context when supported. Rotate among untested, stale, and previously shallow surfaces rather than repeatedly inspecting the easiest area and implying broad coverage.
- Require a clean source worktree, capture `HEAD`, spec digest, and a product-source digest excluding the review subtree, then run mutating probes in an isolated sandbox at that commit. Clean up and allow only memory/report proposals; otherwise fail without a clean claim. Spec or product digest mismatch makes every affected row stale by default; retaining freshness requires evidenced affected-path analysis.
- `--memory` names `<planning-dir>/reviews/workflow-adversarial/INDEX.json`; `--review` names absent `runs/<version>/<review-id>.json`. Both use schema version 1 and remain outside lifecycle state/init/validation.
- Each report records its scope, probes, observations, findings, review-context mode, selected spec path and SHA-256, tested Git `HEAD`, and time. A clean claim requires an executed probe and observable evidence, not code inspection or passing existing tests alone.
- Exact index fields are `schema_version`, `next_finding_number`, non-null `surfaces`, and non-null `findings`. Each unique normalized surface key has evidence refs, outcome (`clean|finding|inconclusive`), freshness (`fresh|stale`), spec/product SHA-256, tested HEAD, RFC3339-UTC time, unique finding IDs, and next angle. Findings use the exact fields/statuses below. JSON decoders reject unknown/null/duplicate data; byte cap applies to canonical indented UTF-8 output. One run adds at most three explained keys.
- A prior clean outcome is historical evidence, not present assurance, after its relevant spec or source snapshot changes. Mark freshness stale until deliberately reprobed; outcome and freshness remain separate, so an unchecked finding can be both finding-bearing and stale.
- Findings use stable, never-reused IDs and record severity, evidence, impact, first-seen and last-checked snapshots, status, rationale, and optional Taskrail task ID. Status is `open`, `tracked`, `resolved`, `not-reproducible`, `deferred`, or `obsolete`.
- `tracked` requires a human-created task reference; `resolved` requires a fresh reproduction attempt against the fixing snapshot; and `not-reproducible`, `deferred`, or `obsolete` requires evidence and rationale. Unchecked findings remain visible and stale rather than closing by omission.
- The summary distinguishes fresh clean, stale, finding-bearing, and untested scope. The index contains at most 256 KiB, 256 current surface rows, unresolved findings, and a monotonic number; closed detail stays in reports. Cap overflow stops for human compaction without discarding open/tracked/deferred findings.
- When review moves to another spec version, the rollover run report captures the prior closure snapshot, the same active index is rewritten for the new version, still-applicable `open`, `tracked`, and `deferred` findings retain IDs and origin, and relevant prior surfaces start stale. Closed findings and detailed runs remain in the prior version's run directory. This bounds routine context, not total Git history.
- Exact report fields are `schema_version`, `review_id`, `spec_path/spec_sha256`, `tested_head`, `product_sha256`, context mode, generated time, scope, non-null probes/observations/findings, and index SHA-256 before/after. Product SHA-256 hashes sorted Git-index path, mode, blob bytes, and submodule IDs outside the review subtree.
- The skill writes proposals, then `taskrail review publish-workflow --memory <index> --expect-memory-sha256 <digest|absent> --next-memory <proposal> --review-proposal <proposal> --review-destination <path> --expect-head <sha> --expect-spec-sha256 <digest> --expect-product-sha256 <digest>` acquires ordered repository/review locks, rechecks snapshots, validates subtree/schemas/caps and absent destination, publishes report no-clobber, and atomically CAS-replaces index. Conflict/interruption publishes neither final file and reports exact recovery; IDs cannot race.
- A human reviews and commits or deliberately discards the allowed memory/report diff before another clean run. Findings stay advisory; promotion uses task CLI/reviewed import, never this publisher or `validate`.

### Active-Spec Scoped Statistics

Add an opt-in read-only projection:

```text
taskrail stats --active-spec [--json]
taskrail stats --active-spec --format dot|mermaid
```

Requirements:

- Unfiltered text, JSON, DOT, and Mermaid output remain unchanged and continue describing the complete task ledger. `--active-spec` is a positive boolean filter derived only from `STATE.md`; it accepts no version value and does not replace `next --include-off-spec`, prompt `--spec`, or coverage `--area`.
- Canonicalize stored spec paths on every OS to slash-separated, case-correct repository-relative form without symlink traversal. `validate` enforces portable canonical spelling plus a matching `active_spec_version`/discoverable versioned path pair.
- Let `L` be the full ledger and subject set `S` contain every status whose parseable canonical `spec_ref` path equals active path, even with an invalid anchor. Unclassifiable refs are excluded from `S`, counted/listed deterministically, and never hidden as valid. Metrics total, all status buckets, percentages, blocked ratio, and blocker count use `S`; coverage and repository last verification retain existing scope.
- Resolve dependencies through `L`. Unmet count uses non-cancelled subjects with missing, cancelled, or non-completed dependencies. Longest chain starts from non-cancelled `S` and traverses non-cancelled nodes; missing/cancelled dependencies terminate that path. Graph nodes are `S` plus closure, with off-spec context marked; each missing reference emits deterministic synthetic `missing:<escaped-ref>` node/label/style, excluded from task counts and chain length, so no edge dangles.
- Scope JSON exact fields are `kind:"active_spec"`, canonical `active_spec_path`, `subject_task_count`, `excluded_task_count` (`|L|-|S|`), `dependency_context_task_count`, `malformed_subject_spec_ref_count`, and `malformed_ledger_spec_ref_count`; context is a subset excluded from subject metrics. Subject-malformed means classifiable active path with invalid/missing anchor; ledger-malformed additionally counts unclassifiable refs. Default JSON gains no scope. Graph comments use the same counts.
- A zero-match cohort is a successful zero-valued report with existing `N/A` percentage conventions where applicable. `--json` remains incompatible with graph `--format`; `--active-spec` composes with either output mode.
- `stats --active-spec` fails before output when active version/path is incoherent. Cancelled tasks remain in status totals but excluded from dependency metrics, preserving unfiltered semantics.
- This flag is reporting only. Do not add it to status, coverage/gaps, next, validate/repair, explicit task writers, spec/import/prompt commands, or loop. Those surfaces already have active, global, or explicit-subject semantics that filtering would weaken or duplicate.

### Optional Autonomous Run Policy

When present, `<planning-dir>/AUTONOMY.tsv` separates curated unattended policy
from lifecycle status. In the default layout this is `planning/AUTONOMY.tsv`.

Format:

```text
# comments are allowed
run<TAB>T-123<TAB>safe unattended implementation
hold<TAB>T-124<TAB>requires an operator credential
skip<TAB>T-125<TAB>parked for provenance
```

Parsing requirements:

- The file is UTF-8 without a byte-order mark and at most 1 MiB. LF and CRLF line
  endings are accepted and normalized for parsing.
- Blank lines are ignored. A comment begins when the first non-space character is
  `#` and occupies the rest of that line.
- Every data line has exactly three tab-separated fields. Policy and task ID are
  trimmed of surrounding ASCII space; the rationale is trimmed, non-empty, and
  contains no tab or control character. Policy values are lower-case and
  case-sensitive.
- Parse/validation errors name path and line. LF/CRLF normalize only for parsing; writers and loop postflight preserve all pre-existing policy bytes exactly outside authorized insertion, so line-ending/comment rewrites are mutations.
- The policy and every parent component are canonical in-repository regular paths with no symlink/reparse traversal; special files and outside-root resolution fail.

Static validation requirements:

- Allowed policies are exactly `run`, `hold`, and `skip`. Task IDs are unique and
  reasons are non-empty. Every referenced task exists.
- Open `run` rows belong to the active spec. An open `hold` may be active-spec or a narrow off-spec dependency-context hold: it must be in the unresolved transitive dependency closure of a later active-spec run/hold, never launches, and stops for operator handoff. Unrelated off-spec holds are invalid. Terminal rows are retired; `skip` may retain parked provenance.
- The file owns only curated order and unattended policy. Task files remain the
  source of lifecycle status, priority, dependencies, and spec linkage. The runner
  never writes lifecycle status into the policy file.
- For every open run/hold, each unresolved dependency appears earlier as active runnable `run` or operator/off-spec `hold`. Absent, later, skip, duplicate, or cancelled dependencies are invalid; completed dependencies need no row.
- While the file exists, active-spec tasks absent from it are outside unattended
  selection. This makes the policy an allowlist, not merely a sorting hint.
- `taskrail validate` validates the optional file when present. `taskrail loop
  --dry-run` also reports the resolved queue, task statuses, first action, and any
  policy violation without launching a child or writing state.
- Taskrail never creates `AUTONOMY.tsv` during default `init`. Repositories that do
  not need curated policy continue to use normal active-spec selection.
- Retired rows may be pruned deliberately after `loop --dry-run` proves first action and violations unchanged; preserve comments needed for operator provenance and commit pruning separately from an unattended iteration.

Runtime row semantics:

| Policy | `todo` | `in_progress` | `blocked` | `completed` / `cancelled` |
|--------|--------|---------------|-----------|---------------------------|
| `run` | launch only when dependency-eligible | stop non-zero for deliberate recovery | stop cleanly with blocker handoff | bypass |
| `hold` | stop cleanly with operator handoff | stop non-zero for deliberate recovery | stop cleanly with blocker handoff | bypass |
| `skip` | bypass | global active-task preflight still stops non-zero | bypass | bypass |

The scanner evaluates rows in order after bypassing retired and `skip` rows. It
never jumps past the first `hold`, blocked row, or recovery condition. A selected
`run` task may legitimately become blocked during its child process: the policy
remains structurally valid, postflight recognizes a fresh blocked/fail tuple, and
the row becomes a blocker handoff on the next dry run.

Writer integration:

- `task rename` atomically rewrites a matching policy task ID with its dependency
  and `STATE.md` references, preserving policy, rationale, and position.
- `spec activate` refuses before writing when unfinished `run` or `hold` rows
  would point away from the target spec. Its error directs the operator to finish,
  remove, or deliberately park those rows first. Terminal historical and `skip`
  rows do not block activation.
- `task repoint` evaluates the exact resulting static invariant: off-spec run is refused, while off-spec hold is allowed only when it remains required dependency context. Policy stays human-authored and validate-clean.

### Layout Compatibility And Upgrade

The recognized autonomy policy changes how work is selected, so an older binary
must not silently ignore it.

Requirements:

- `v0.5.0` raises layout to `2`. Preview builds/validates without writes. Apply requires operator-confirmed quiescence of older Taskrail processes, acquires the new writer lock, snapshots every semantic file, publishes an early migration fence and final marker atomically, rechecks snapshots, and post-validates. Failure restores only unchanged originals and never overwrites concurrent bytes; already-running old processes cannot honor the lock and explicitly make migration unsafe. No policy/override is created.
- Layout 2 raises `STATE.md` to state schema 2 and removes both the
  `continuation_notes` frontmatter field and the rendered `## Notes` section.
  State is a bounded current snapshot, not a per-task/session narrative or
  persistent event log. Task-specific context belongs in task `## Implementation
  Notes`, blocker reasons, portable verification summaries/reports, or follow-up
  tasks. Fresh layout-2 initialization writes schema 2 directly and never seeds
  bootstrap continuation prose.
- Upgrade preview decodes schema 1 explicitly and reports every legacy
  continuation note plus whether drop acknowledgement is required. Apply refuses
  to discard a non-empty list unless the operator supplies
  `--drop-continuation-notes`; empty or absent lists need no acknowledgement, and
  supplying the flag when no note needs removal is reported as unnecessary.
  Schema-2 decoding rejects the removed field rather than letting a later writer
  silently erase reintroduced prose. The migration and its rollback cover both
  frontmatter removal and body re-render as one transaction.
- `--drop-continuation-notes` is migration-only compatibility surface, not a
  state-editing command. It remains accepted while any direct or multi-hop
  upgrade from state schema 1 is supported, including a later old-to-current
  upgrade that traverses layout 2, and is removed only when schema-1 migration
  support is formally dropped.
- `AUTONOMY.tsv` is accepted only in a layout-2 repository. The v0.5 binary tells a
  layout-1 repository to run the normal `init --apply` upgrade before using it.
- Every v0.5 semantic writer (lifecycle/task/spec/import/review publisher and loop execution) requires layout 2 first; layout 1 permits read-only inspection and init migration only, preventing older writers from later erasing v0.5 IDs, v2 references, or policy semantics.
- Once upgraded, older Taskrail binaries refuse the newer layout through the
  existing command-wide compatibility guard instead of ignoring its selection
  policy.
- If committed packaged-skill destinations exist, apply requires the combined `taskrail init --apply --with-skills --force`; preview writes no skills, and refusal occurs before any marker/skill change. Repositories without installed skills are not forced to create them. Staged copies validate version/parity before marker publication.
- Acceptance covers candidate failure/rollback/interruption, v0.4 layout and skills moving together, older-binary refusal, no preview writes, and identical policy behavior before/after refresh. Downgrade is Git reversion of the complete upgrade, never hand-editing the marker.

### Cross-Platform Autonomous Loop

Add a foreground generic process runner:

```text
taskrail loop [--max-iterations <n>] [--allow-prompt-override-sha256 <digest>] [--dry-run] -- <command> <args...>
```

Execution contract:

- The child command is required for execution and is passed as an argument vector
  directly to the operating system. Taskrail never joins it into a shell string,
  evaluates shell syntax, or names a supported provider.
- A bare executable name resolves through the inherited `PATH`. A path containing
  a separator resolves against the caller's original working directory before the
  child cwd changes to the repository root, then is passed as an absolute path.
- `--max-iterations` is a positive integer and defaults to `1`. There is no
  unlimited value. A caller opts into a longer run explicitly.
- `--dry-run` rejects a child command, performs all read-only repository and policy
  checks, and supports `--json`. Its result has action `run`, `hold`, or `none`,
  plus reason, policy summary, violations, and selected task. It includes prompt
  source, SHA-256, and rendered content only for `run`; hold and no-work results
  do not fabricate a selected task or prompt. Valid hold and no-work results exit
  zero; invalid repository or policy results exit non-zero.
- Dry-run JSON exact top-level fields are `schema_version`, `action` (`run|hold|none|invalid`), `reason`, nullable `selected_task`, `policy` (`present,path,row_count`), non-null `violations`/`warnings`, nullable `prompt` (`id,source,path,sha256,override_authorized,content`), `git` (`head,branch,clean,detached`), `lock` (`available,owner`), and `delivery` (`local_commit_required,remote:"not_checked"`).
- Execution uses the built-in task prompt unless an override resolves and its exact SHA-256 equals `--allow-prompt-override-sha256`; otherwise refuse before launch. Dry-run always reports source/path/hash and authorization. Approval trusts only those committed bytes, not their safety; prompt files/source/path/hash are frozen for the invocation.
- The loop runs from the repository root and launches one fresh child process per
  selected task. It writes the exact UTF-8 rendered prompt bytes to child stdin,
  adds no framing or newline, closes stdin immediately, and streams child stdout
  and stderr to the corresponding Taskrail streams. Stream-copy failure fails the
  iteration. A provider CLI that cannot consume a finite stdin prompt requires a
  caller-supplied adapter process.
- The child inherits caller-owned environment/authentication. Before launch, copy the running executable bytes to a hash-named, no-replace file under the Git common directory, verify its SHA-256, and set child `TASKRAIL` to that immutable staged path plus expected digest. Delegated writers verify their own executable bytes against lock metadata before joining; pathname replacement, digest mismatch, or inherited conflicting override refuses. Cleanup removes only the invocation's staged copy after contained writers exit.
- `loop` has no `--json` execution mode because streamed child output cannot form
  one valid Taskrail JSON document.
- `--max-iterations` bounds child count only; there is no wall-clock timeout. Establish an isolated Unix process group or Windows job object before descendants can run, or fail launch. After leader exit, stream failure, or interruption, drain all contained descendants, request termination, wait 10 seconds, then force the tree; escaped/unassignable/surviving processes are `child_failed` and never permit postflight success. Platform containment cannot claim control over deliberate Unix `setsid` or Windows breakaway escape and reports detected escape.
- Execution in the Taskrail source checkout is unsupported in v0.5 because source-changing work makes the pinned running binary stale and native Windows cannot replace it safely. Dry-run names that boundary; installed adopter repositories are unaffected.

Selection contract:

- Require Git, a non-bare worktree with attached non-unborn `HEAD`, and equal Taskrail/worktree roots. Every Taskrail task/state/spec/policy/layout/import writer uses one Git-common-directory mutation lock for its whole candidate-validation/write/rollback transaction. Loop owns it through postflight and passes an unguessable child-only delegation token; matching child writers join without release, unrelated writers/loops refuse. Metadata records command/PID/host/start/repository/token digest, never token; stale locks are inspected/removed manually.
- Before the first child and between every iteration, run the same repository
  validation used by `taskrail validate` without writing state.
- Refuse to begin with a dirty working tree or an existing `in_progress` task.
  "Clean" means `git status --porcelain=v1 --untracked-files=all
  --ignore-submodules=none` reports no
  staged, unstaged, untracked, or submodule change; ignored verification artifacts
  remain ignored by Git. Recovery or continuation of interrupted work is
  deliberate human work, not an automatic retry hidden inside the loop.
- If `AUTONOMY.tsv` exists, select through its policy and barrier rules. Otherwise
  use the same read-only active-spec eligibility and ranking as `status`.
- No eligible task or a `hold` barrier is a clean stop and launches no child.
- Capture selected/every task bytes and parsed fields, active spec/config/layout digests, full attached ref/HEAD, verification IDs/artifact set, policy presence/path/bytes/rows, prompt source/path/hash, and staged executable path/hash before launch. These control inputs remain immutable; same prompt and executable bytes serve every iteration.

Postflight contract:

- After every child termination, including non-zero/signal, run validation and collect all lifecycle, Git, policy, prompt, lock, process, and mutation diagnostics. Outcome is exactly `completed_pass` (completed + fresh bound pass, exit 0), `blocked_fail`, `rework_fail`, `completed_unverified`, `completed_audit_fail`, `child_failed`, `no_progress`, or `invalid_postflight` (all non-zero). Only `completed_pass` may continue.
- Every delivered recognized lifecycle outcome leaves a clean tree, same full attached ref, descendant `HEAD` with at least one local commit, unchanged active spec/config/layout/prompt/policy presence, valid policy, and no contained process. Remote delivery is always `not_checked`. Child failure may leave dirty evidence but is never delivered.
- Pre-existing non-selected task files remain byte-identical. Selected ID/title/priority/spec_ref/dependencies and Description/Acceptance/Verification Notes remain unchanged; only canonical lifecycle fields, timestamps, blocker and Implementation Notes may change. At most two new live tasks are allowed, each a real follow-up of selected work. Any other ledger mutation is integrity failure in every outcome.
- Absent policy remains absent. Present policy retains every pre-existing byte/row/comment except deterministic insertion of at most two follow-up rows: `run` after existing runnable rows before first hold, or `hold` after runnable work. Creation/deletion, reordering, edits, or unrelated rows fail and never affect a later iteration.
- Fresh verification requires a new preflight-absent verification ID/path and exact task/result/time/completion-ID agreement across task, state, JSON, and report. A completed audit fail remains completed and stops for follow-up disposition; command failure after successful complete is completed-unverified and recovery reruns verify only.
- Final human diagnostics always report outcome, task, child exit/signal, lifecycle and verification IDs before/after, validation, Git/ref/HEAD, policy, prompt hash, mutation/process violations, local commits, remote `not_checked`, and safe next action. Only after all completed-pass conditions may selection repeat; reaching iteration cap succeeds and reports remaining work.

Safety boundary:

- `loop` is foreground-only and sequential. The common-directory lock coordinates linked worktrees but is not a distributed lease across clones.
- Taskrail does not inspect child conversations, tool calls, model output, review
  identity, token use, or provider state. Its evidence is process exit plus the
  repository contracts it already owns.
- Taskrail does not commit, push, merge, open pull requests, wait for remote CI, or
  reset failed work. Repositories express delivery policy in their prompt
  replacement and external automation.
- Every non-clean stop reports task ID, child exit or signal, lifecycle status,
  verification before/after, Git status, policy result, and safe next actions.
  Recovery is manual inspection followed by the existing `complete`, `block`,
  `unblock`, `verify`, and Git operations as appropriate; Taskrail never resets or
  rewrites the failed child outcome automatically.

### Skill And Prompt Behavioral Contract Tests

Extend the existing shippable-skill checks into one behavioral contract over the
shipped skills and built-in prompts, while retaining byte parity as a separate
packaging guarantee.

Requirements:

- **Commands/lifecycle**: every invoked Taskrail command exists; delineated golden/negative fixtures require complete-before-pass, block-before-fail, no complete on failure, writer exit checks, Git delivery tail, and recovery for completed-unverified/audit-fail.
- **Authoring quality**: task-authoring and decomposition fixtures require one meaningful outcome, observable acceptance, criterion-to-evidence mapping, an adequate public oracle, relevant negative/boundary cases, and regression-sensitive evidence without prescribing unnecessary internals; task-authoring rejects non-`todo` history.
- **Review contracts**: fixtures enforce exact lens/decomposition manifests, trace source one-of and bidirectional keys, immutable review passes, v1 compatibility, v2 body/manifest/digest binding, transactional rollback, dedicated subtrees, and no semantic writer in lenses.
- **Workflow memory**: sandbox isolation, product/spec freshness, schema/caps, CAS conflict, lock/interruption recovery, monotonic IDs, rollover, and clean commit/discard handoff are exercised.
- **Prompt/security**: registry-by-construction, UTF-8/size/token/path rules, exact list/show/render JSON, provider independence, override-hash authorization/pinning, and override/catalog mutation refusal are tested; arbitrary repository replacements remain outside semantic certification.
- **Process/writer integrity**: Go helper tests cover argv/stdin/cwd/environment/EOF/streams, delegated writer lock and unrelated refusal, attached branch/ancestry, every outcome, all-outcome byte allowlist, unique verification IDs, dirty/no-progress states, normal/signal descendant cleanup and detected escapes on supported OSes.
- **Policy**: LF/CRLF/comments/symlink boundaries, every status, run/hold ordering, off-spec context holds, presence freeze, bounded additions, byte preservation, pruning, rename/repoint/activation, and layout protection are covered.
- **Active stats**: omitted output compatibility, exact subject/context/excluded sets, malformed canonical paths, cancelled/missing dependencies, zero cohort, full-ledger closure/graph marks, coherent active pair, and read-only text/JSON/DOT/Mermaid.
- **Migration**: candidate failure, transaction rollback/interruption, no preview/skill writes, combined forced refresh when installed, old-binary refusal, and policy equivalence are automated and manually sandboxed.
- Skill package parity remains byte-exact; README, AGENTS, autonomous/human/agent workflow, skills, upgrade/recovery/review-evidence and CHANGELOG docs contain no stale lifecycle or artifact guidance.
- Manual evidence covers multi-iteration pass, hold/off-spec dependency, blocked/rework/partial-complete/audit-fail, external-writer refusal, policy presence mutation, stale verification, containment failure, override trust, authoring, both planning review workflows, memory CAS/rollover, stats scope, and v0.4 upgrade. Packaged smoke runs Linux, macOS, and native Windows.

### Verify Lifecycle Advisory

`verify --result pass` emits a non-gating advisory warning when the target task is
not `completed`.

Requirements:

- The warning names the task, its current status, and the expected order. It is
  advisory: `verify` still writes artifacts, records the result, and exits zero.
- Human mode writes stderr. JSON emits non-null `warnings` (empty when none); the exact object is `{"code":"verify_pass_before_complete","message":<string>,"task_id":<string>,"status":<todo|in_progress|blocked|cancelled>,"expected_status":"completed"}`.
- It covers every non-`completed` status, not only `in_progress`.
- It never makes `validate` fail and never changes task status.
- `verify --result fail` emits no corresponding warning: `in_progress`, `blocked`, and completed audit are valid failing records. It carries a verification ID but binds no passing completion.

## Caution

Do not turn `v0.5.0` into a general agent framework.

The loop is intentionally one foreground process repeated sequentially over
deterministic Taskrail state. The prompt system is intentionally a versioned
lookup, strict substitution, and local whole-file replacement. The review lenses
are intentionally advisory. Resist adding provider configuration, prompt graph
execution, retries, background operation, model-output parsing, automatic
planning writes, or semantic validation under these names.

The optional autonomy policy also must not become a second task database. It
contains only order, `run` / `hold` / `skip`, and a rationale. Status,
dependencies, priority, spec linkage, title, acceptance, and verification stay in
the existing task and state files.

Workflow-adversarial memory likewise stays an optional review index, not task
state or permanent assurance. Partition detailed runs by spec, keep the current
index compact, and treat old clean claims as snapshot-bound evidence.

Local replacement can remove supported guidance. That explicit repository choice
does not justify implicit merging, and Taskrail does not judge replacement quality.
Universal loop safety remains in mechanical preflight/postflight; semantic and
delivery policy remains in prompt text.

## Recommendation About LLM Support

Do not add direct LLM calls to Taskrail core.

`taskrail loop` starts a caller-supplied executable; it does not know whether that
process is a coding agent, a deterministic test double, or another local tool.
`taskrail prompt` emits text; it does not send that text to a provider. The
judgement-heavy parts of spec review and decomposition remain in prompts and
skills, while the binary provides deterministic inputs, validation, and reviewed
write paths.

This preserves the established order: repo-native CLI and file model first,
prompts and skills for external agents second, and no provider adapter until a
separate future spec demonstrates that one is necessary.

## Explicitly Excluded

Continue to exclude:

- direct model or provider API calls from the Taskrail binary;
- named provider adapters, provider configuration, model selection, token or cost
  management, and conversation/session persistence;
- shell-string evaluation or a shell-script runtime inside `loop`;
- background daemons, schedules, retries, worker pools, parallel task execution,
  distributed leases, and multi-agent coordination;
- skill interpretation, skill graphs, conditional workflow execution, or a
  general prompt-composition language;
- automatic continuation of an existing `in_progress` task;
- Git commits, pushes, merges, pull requests, remote-CI waiting, force operations,
  or rollback performed by Taskrail;
- semantic enforcement of independent reviewer identity or different model use;
- automatic spec edits, spec activation, task creation, or `import --apply` from a
  review or decomposition prompt;
- turning semantic spec findings into `validate` errors or conflating
  `spec-gaps` with mechanical `coverage --gaps`;
- a second lifecycle or dependency schema in `AUTONOMY.tsv`;
- automatic promotion of workflow-review findings or treating review memory as Taskrail state;
- physical task archival, automatic terminal-task moves, or an archive storage class in the task ledger;
- `verify` performing a lifecycle transition or hard-rejecting a misordered run;
- `reopen` / `uncomplete` recovery semantics; and
- Taskrail-owned autonomous-run databases, committed conversation logs, or required persistent execution receipts.

The narrow exception to prior automatic-loop and orchestration exclusions is the
explicit foreground `taskrail loop -- <command> <args...>` boundary specified
above. It selects deterministically, renders one supported prompt, launches one
opaque external process, verifies repository postconditions, and repeats only up
to a finite caller-visible limit. Nothing broader is implied.
