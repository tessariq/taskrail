# Taskrail v0.5.0

## Summary

Taskrail `v0.5.0` opens a **skill contract integrity** thread.

Through `v0.4.0`, the packaged skill set under `internal/taskrail/skills/` grew
into a real product surface: it is embedded, installed by
`taskrail init --with-skills`, mirrored into committed `.agents/`/`.claude/`
copies, and version-marked for skew detection. But the only contract binding a
shipped skill to the CLI is **byte parity** between the package and its committed
copies, plus a few spot assertions (entry point, no `go run`, `task new`). Nothing
asserts that a skill's documented flow can actually reach a terminal task status,
or that the commands a skill names exist at all.

That hole shipped a defect. `autonomous-backlog` and `autonomous-task` run
`verify` and then say, in prose, to "finish as `completed` or `blocked`" — but
`verify` is not a lifecycle transition, and neither skill ever invokes `complete`
or `block`. A skill run that succeeds leaves the task `in_progress`, so adopter
automation that requires `status: completed` rejects it, and a run that cannot
proceed leaves no recorded blocker. Adopters must patch installed skills by hand,
and `taskrail init --with-skills --force` restores the defective flow.

The underlying cause is not the two missing commands. It is that the repository
never wrote down **one** canonical transition order, so the skills, the workflow
docs, and the tests each encode a slightly different one. This version fixes the
skills, settles the order normatively, and makes the contract mechanically
enforced rather than prose-enforced.

`v0.5.0` adds no new lifecycle semantics and no new writer commands. It keeps
Taskrail provider-independent and free of any LLM integration in the core,
consistent with `v0.1.0` through `v0.4.0`.

## Goals

- Settle one normative transition order for tracked work, in one place, and make
  every skill, doc, and test derive from it instead of restating it.
- Make every shipped skill flow lifecycle-complete: a documented run reaches a
  terminal task status through real CLI commands, on both the success and the
  cannot-proceed branch.
- Extend the skill contract from byte parity to behavioral parity: assert that
  the commands a skill names exist, and that its lifecycle branches are correct.
- Keep `verify` a recording step, never a lifecycle transition, and make a
  misordered run visible without gating it.
- Prevent the completed-but-failed state from being reachable through the
  documented flow, without adding a recovery command for it.

## Potential Features

### Canonical Transition Order

Define one normative order for a tracked-work run, in
`docs/workflow/autonomous-contract.md`, and cite this heading from the skills,
`AGENTS.md`, and the contract tests rather than restating the order in each.

Success branch:

```text
validate -> start -> implement -> local checks -> complete -> verify --result pass
```

Cannot-proceed branch:

```text
validate -> start -> block --reason -> verify --result fail -> stop
```

Rework branch (findings exist but the task stays runnable):

```text
validate -> start -> verify --result fail -> stop (task remains in_progress)
```

Requirements:

- `complete` precedes `verify --result pass`. Verification records the outcome of
  an already-finished implementation; it does not decide it. This is the order
  `Verify` already assumes: on `pass` it sets `next_action` to select the next
  eligible task, which is only coherent for a task that is already terminal.
- **`complete` is never called when the verification result will be `fail`.** The
  completion decision is made by the local checks that precede it. A failing run
  ends `blocked` (with a reason) or stays `in_progress` for rework — never
  `completed`.
- A blocked run never calls `complete`, and `verify --result fail` is never
  described as the operation that blocks a task.
- Follow-up tasks may be created before `complete` (`task new`) or during
  verification (`verify --create-followup`). Both keep `STATE.md` counts correct,
  because `verify` re-projects the rendered state body. The existing "create
  follow-ups before the final transition" guidance in
  `docs/workflow/development-workflow.md` and `AGENTS.md` is narrower than the CLI
  requires and must be restated to match this order.

Rationale: the CLI enforces almost none of this. `Verify` has no status
precondition, and `finishTask` only requires `in_progress` (or `todo` for
`block`), so every ordering "works" and none is discoverable from behavior. The
order is a contract, so it belongs in the contract document, asserted by tests.

Boundary: this area writes down and tests an order. It adds no precondition that
makes a previously working command fail, and no new command.

### Lifecycle-Complete Skill Flows

Rewrite the `autonomous-backlog` and `autonomous-task` required flows to name
explicit success and cannot-proceed branches with real commands, replacing the
prose step "Finish as `completed` or `blocked`".

Requirements:

- The success branch invokes `${TASKRAIL:-taskrail} complete <task-id> --note "..."`
  before `${TASKRAIL:-taskrail} verify <task-id> --result pass --summary "..."`.
- The cannot-proceed branch invokes
  `${TASKRAIL:-taskrail} block <task-id> --reason "..."` before
  `${TASKRAIL:-taskrail} verify <task-id> --result fail --summary "..."`, then stops.
- The cannot-proceed branch never invokes `complete`.
- Both branches keep the existing source-checkout guard: `complete` and `block`
  are state writers, so `task taskrail:check` runs immediately before each in the
  Taskrail source checkout.
- `autonomous-verify` stays unchanged. It may legitimately verify a task whose
  lifecycle transition already happened, which is exactly the post-`complete`
  position this order defines.
- Committed `.agents/`/`.claude/` copies are regenerated from the package
  (`task skills:regen`) so byte parity holds, differing only by the installed
  `taskrail_version` marker.

Rationale: the skills are the adopter-facing encoding of the workflow. A skill
that cannot reach a terminal status is a broken product surface regardless of how
correct the CLI underneath it is.

### Skill Behavioral Contract Tests

Extend the shippable-skill assertions from spot checks to a behavioral contract,
alongside the existing byte-parity check.

Requirements:

- **Command existence**: every backticked `${TASKRAIL:-taskrail} <subcommand>`
  invocation in a shippable skill resolves to a real subcommand on the CLI
  surface. A skill may not name a command that does not exist.
- **Lifecycle branches**: for each skill that drives a full task run,
  `complete` appears before `verify --result pass`, `block --reason` appears
  before `verify --result fail`, and the cannot-proceed branch contains no
  `complete`.
- **Terminal reachability**: a skill that starts a task must name at least one
  terminal transition (`complete` or `block`).
- Assertions reuse the existing per-skill reference helper and the shippable-set
  registry, so a new shipped skill is covered by construction rather than by
  remembering to add a case.
- The byte-parity check is unchanged and remains the separate guarantee that
  installed copies equal the package.

Rationale: this is the check whose absence let the defect ship. Prose review of a
markdown flow does not scale across eleven skills and three copies of each;
mechanical assertions do.

Boundary: these are structural assertions over skill text — which commands appear
and in what order. They are not a skill interpreter, and Taskrail gains no ability
to execute a skill (see Explicitly Excluded).

### Verify Lifecycle Advisory

`verify --result pass` emits a non-gating advisory warning when the target task is
not `completed`.

Requirements:

- The warning names the task, its current status, and the expected order. It is
  advisory: `verify` still writes its artifacts, still records the result, and
  still exits zero.
- It covers every non-`completed` status, not only `in_progress`. A `pass`
  recorded against `todo` or `blocked` is the same misordering.
- The warning never makes `validate` fail, and never changes task status. It
  follows the existing advisory precedent set by `coverage` and `coverage --gaps`.
- `verify --result fail` emits no such warning: `blocked` and `in_progress` are
  both correct targets for a failing result.

Rationale: defense in depth for hand-run and non-skill flows. The skill correction
is the actual fix — verification must not silently become a lifecycle transition,
so this stays a warning and never a transition or a gate.

## Caution

Do not turn `v0.5.0` into:

- a skill runtime,
- a lifecycle state machine with enforced preconditions on every command,
- a linter for arbitrary markdown.

Keep it grounded in the existing surface: one written-down order, skills that
match it, tests that assert the match, and one advisory warning. The contract
tests inspect the shipped skill set only, and the advisory stays advisory.

## Recommendation About LLM Support

Unchanged from `v0.2.0` through `v0.4.0`. Do not add direct LLM calls into
Taskrail core. This version reinforces the stance rather than testing it: the
judgement-heavy parts of the workflow stay in skills, which makes the correctness
of those skills a product concern — the whole point of this thread.

## Explicitly Excluded

Continue to exclude everything excluded by `v0.4.0`, and additionally:

- `verify` performing a lifecycle transition, or auto-completing a task on a
  passing result,
- a `reopen`/`uncomplete` command. The completed-but-failed state is prevented by
  the "never `complete` when the result will be `fail`" rule, not recovered from
  after the fact,
- hard status preconditions on `verify` that reject a misordered run,
- conditional or branching execution semantics inside skills beyond the documented
  success and cannot-proceed branches,
- a skill execution, scheduling, or orchestration runtime inside Taskrail
  (carried forward from `v0.4.0`).
