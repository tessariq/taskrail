# Taskrail v0.5.0 Machine API

## Status And Authority

This file is the co-normative machine-contract companion to
`specs/v0.5.0.md`. The feature spec owns command behavior and repository
semantics. This companion owns envelope schema version 1, exact command result
members, nested shapes, nullability, collection ordering, warnings, errors, and
the command/error registry.

Implementation structs, help text, examples, generated JSON Schema, prompts, and
skills are not independent authorities. A conflict is resolved in favor of this
file for wire shape and `specs/v0.5.0.md` for behavior.

## Encoding Rules

- A document is one UTF-8 JSON object without BOM, duplicate keys, unknown keys,
  missing required keys, or trailing values.
- Object members appear in the order listed by this companion. Consumers must not
  depend on member order, but golden producers do.
- Required arrays are `[]`, never `null`. Required strings are non-empty unless
  an exact enum permits otherwise. Optional meaning is represented by an explicit
  nullable field unless a persisted artifact contract expressly requires omission.
- Digests are lower-case 64-hex SHA-256 over exact bytes. IDs and timestamps use
  the grammars in the feature spec.
- Managed semantic paths are canonical slash-separated logical repository paths.
  Local runtime/config/artifact paths are canonical repository-root-relative physical
  paths where their command explicitly reports a physical location. The loop
  result-file destination is canonical absolute because it must be outside the
  repository.
- Unless a command says otherwise, path arrays sort by unsigned UTF-8 bytes;
  violations sort by `code`, null-last `path`, then `message`; snapshots sort by
  `path_kind` then `path`; warnings sort by `code` and then their identifying
  fields.

Path-valued fields use these exact classes:

- Managed logical paths are canonical slash-separated repository-relative paths.
  Every task, spec, state, note, prompt, review destination/subject, and semantic
  write-entry path uses this class.
- Skill destination paths are canonical slash-separated repository-relative
  physical discovery paths beneath `.agents/skills/` or `.claude/skills/`. They
  use the same path in committed and local modes, are never mapped beneath
  `.taskrail/local`, and appear in init, promotion, exclusion, error, and skill
  inventory fields using this class.
- Repository-root physical paths are canonical slash-separated paths relative to
  the discovered Taskrail repository root; in a Git worktree that root is the
  worktree root. They remain meaningful for supported non-Git repositories.
  `LocalPathResult.config_path`, `storage_root`, `prompts_dir`, `artifacts_dir`, and
  `runtime_dir`, `StatusResult.storage.artifacts_dir`, `VerifyResult.artifact_dir`,
  `VerifyResult.plan_path`, `VerifyResult.report_path`, local storage roots, review
  proposal paths, and review file `source` fields use this class and may name
  `.taskrail/local`. Every verify artifact path is beneath the status-reported
  `artifacts_dir` from the same storage snapshot.
- `LocalPathResult.specs_dir` and `planning_dir` are managed logical directory
  paths; Taskrail maps them through active storage rather than exposing their
  physical local-overlay location.
- `StatusResult.storage.root` is a repository-root physical path with exact value `.` in
  committed mode and `.taskrail/local` in local mode.
- `StatusResult.storage.artifacts_dir` is the canonical repository-root-relative physical
  artifacts directory resolved through the active committed or local storage
  context. It is authority only for transient staging and never enters a managed
  semantic field or Git-visible provenance. In Git, a producer or publisher must
  separately prove its selected path effectively ignored, untracked, and unstaged;
  outside Git no ignore-state claim applies.
- In local mode, `StatusResult.storage.artifacts_dir` and
  `LocalPathResult.artifacts_dir` are byte-identical observations from one active
  storage snapshot.
- `LocalStatusResult.worktree_root`, `LocalStatusResult.git_common_dir`,
  `LockOwner.repository_root`, and `LoopDiagnostic.executable.path` are canonical
  absolute paths. The loop result-file destination is also canonical absolute and
  outside every repository/Git/managed root, but is reported only in applicable
  `path_blocked`, `destination_exists`, or publication diagnostics.
- Import/retrofit `source` and `target` strings are display labels, not path
  authority. Review `destination`, review file `destination`, and every receipt or
  durable artifact path remain managed logical paths.
- Error `paths` and violation paths use the subject command's class. Snapshot
  `path_kind` selects `managed` logical, `worktree` physical, or canonical
  absolute `git` metadata paths, allowing one durable transaction to bind semantic
  files, assistant discovery files, local runtime files, and the resolved
  effective exclusion store without conflating path classes. Physical
  local-overlay paths never enter durable semantic fields.
  The retained `worktree` enum label means repository-root physical for supported
  non-Git repositories as well as Git worktrees.

## Envelope

Every JSON-capable command and loop result file emits exactly one of:

```text
SuccessEnvelope {
  schema_version: 1,
  command: string,
  warnings: [Warning],
  result: CommandResult
}

ErrorEnvelope {
  schema_version: 1,
  command: string,
  warnings: [Warning],
  error: Error
}
```

`result` and `error` are mutually exclusive. `command` is the canonical command
path after `taskrail`, without executable, flags, operands, or `--`.

An error is:

```text
Error {
  code: ErrorCode,
  message: string,
  details: ErrorDetails | LoopDiagnostic
}

ErrorDetails {
  applied: boolean,
  violations: [Violation],
  paths: [string],
  snapshots: [Snapshot],
  recovery: RecoveryRef | null
}

Violation { code: string, message: string, path: string | null }

Snapshot {
  path_kind: managed | worktree | git,
  path: string,
  original_sha256: string | null,
  candidate_sha256: string | null,
  current_sha256: string | null
}

RecoveryPhase = prepared | fence_published | publishing | candidate_published |
                validating | rolling_back | recovery_restoring |
                recovery_accepting | recovery_clearing
RecoveryRef { transaction_id: string, command: string, phase: RecoveryPhase }
Validation { valid: boolean, violations: [Violation] }
```

`applied:true` means the selected command's complete semantic operation committed.
It is false for preview, refusal, partial publication, retained recovery, and
rollback failure even when diagnostic snapshots show bytes on disk. Only loop
postflight and parallel-batch errors use `LoopDiagnostic` instead of
`ErrorDetails`.

`InitResult.skills` and `InitResult.skill_exclusions` are `[]` whenever
`--with-skills` is absent, including plain `init --local`. Implicit local
bootstrap installs no skills and emits its selected command result plus
`local_initialized`, never an `InitResult`. When `--with-skills` is present,
`skills` contains every packaged installed file under `.agents/skills/` and
`.claude/skills/` in path order. Ordinary committed installation returns
`skill_exclusions:[]`. Local installation reports normal discovery paths, not
`.taskrail/local` paths, and `skill_exclusions` contains one exact
repository-relative subtree per packaged-skill destination in each supported
assistant root, in path order. A committed pending-skill refresh preserves and
reports its existing managed exclusions; only `local promote --with-skills`
removes them. A fresh
`init --local --with-skills` publishes its scaffold, exact skill exclusions, and
skill files under one recovery boundary. An initialized local repository uses
`init --with-skills --force` for an explicit refresh without repeating
`--local`.

Status rows use fixed order `todo`, `in_progress`, `blocked`, `completed`,
`cancelled`. Other arrays use the ordering rules in their feature contracts.

Workflow review artifacts use this closed terminal-evidence union:

```text
CommandEvidence {
  kind: command, summary: string, path: null, sha256: null,
  command: string, exit_code: integer
}
FileEvidence {
  kind: file, summary: string, path: string, sha256: string,
  command: null, exit_code: null
}

  kind: manual, summary: string, path: null, sha256: null,
  command: null, exit_code: null
}
TerminalEvidence = CommandEvidence | FileEvidence | ManualEvidence
```

`FileEvidence.path` is a durable repository-relative logical product or final-
review path and lexically rejects physical `.taskrail/local/...` paths. At
publication, a contextual validator additionally rejects file paths beneath the
frozen artifacts/proposal/runtime roots. Transient probe output uses command/manual
evidence or a digest-only summary instead. Historical `review show` decoding does
not re-resolve paths against a later active storage context. Free-form summary and
command portability, including aliases and producer-local paths, remains a human
review boundary rather than a claimed strict semantic certification.
Product file evidence must resolve to a regular blob in the report's bound Git
tree with matching SHA-256; final-review evidence must resolve to an immutable
published review file with matching digest. A lexical path alone is insufficient.

Promotion entries of kind `spec|state|task|note|review|prompt` use managed logical
paths. Entries of kind `config|artifact|runtime` use repository-root physical
paths and may expose `.taskrail/local/...` only in this transient inspection
result. Artifact/runtime entries are excluded from publication and never copied
into durable semantic content; config is the switched candidate that promotion
publishes atomically.

`config|spec|state|task|note|review|prompt`; `excluded` admits only
`artifact|runtime`. Any other array/kind combination is invalid.

each installed Taskrail-owned skill subtree. It never synthesizes an exclusion
for `.agents`, `.claude`, or either shared `skills` directory.

Local skills already occupy their normal repository discovery paths. A
`LocalPromoteResult.skills` action describes the selected candidate: with
`applied:false`, `promote` means the exact managed exclusion would be removed;
with `applied:true`, it was removed after the unchanged destination validated.
No skill byte is copied from local semantic storage or rewritten.
`preserve_local` leaves both destination and exclusion unchanged, and `absent`
means no packaged destination existed to promote.

After semantic promotion without `--with-skills`, committed storage may retain
valid installed Taskrail-owned skill destinations and their exact managed
exclusions. This is the only committed-mode input accepted by
`local promote --with-skills`; it returns `source_mode:committed`,
`target_mode:committed`, empty semantic entry arrays, and skill-only candidates.
The same command without `--with-skills`, any other committed repository, and a
second invocation after successful skill promotion are `unsupported`.

No other `(command, error.code)` pair is valid. Report-result nonzero exits remain
the exceptions in the command registry and do not become error envelopes.

Warning assignment is also exact:

- Every registry command may emit `unknown_skill_version` or
  `skill_version_skew` after repository discovery, and no command may emit another
  warning unless listed below.
- `empty_derived_slug` is limited to `task new`, `task rename`, and `import`.
- `selected_off_spec`, `selected_non_active_spec`, and
  `skipped_non_active_spec` are limited to `next` and `status`.
- `local_initialized` is limited to successful implicit bootstrap by `next`;
  `start`, `complete`, `block`, `unblock`, `verify`; `repair`; `task new`,
  `task rename`, `task repoint`, `task release`, `task author`; `task loop allow`,
  `task loop hold`, `task loop clear`; `spec add`, `spec activate`; `import`; and
  executing `loop`. Preview/read-only forms never emit it.
- `local_head_drift` may accompany any initialized local-mode command except
  `local status`, which reports drift in its result, and commands that refuse
  before initialized storage discovery.
- `verify_pass_before_complete` is limited to `verify`.

## Envelope Evolution

Schema version 1 describes the complete document contract in this file. A later
release that incompatibly changes any inherited result, warning, error detail,
enum, nullability rule, or interpretation increments the one outer
`schema_version` for every emitted command document. No v0.5 command emits an
older direct-result compatibility form.
