# Taskrail v0.7.0

## Summary

Taskrail `v0.7.0` adds **digest-bound planning-source interoperability**.

Taskrail already imports reviewed task drafts, but it does not mechanically bind
an import to the planning files from which a human or external agent derived it.
Adopters using another spec-driven planning tool must either discard that source
provenance or encode tool-specific details in task bodies and frontmatter.

This version adds a generic planning-source boundary with two built-in, versioned
profiles: `openspec` and `spec-kit`. A profile recognizes one deliberately narrow
repository layout, validates clean tracked UTF-8 files, and produces a
deterministic descriptor over source role, path, size, and SHA-256. Taskrail does
not interpret the prose. A human or external agent supplies a reviewed semantic
mapping and an `ImportDraft` v3 whose tasks point to real anchors in a local
Taskrail spec.

Preview is the default. Apply creates only new tasks, reprojects state, and writes
one strict immutable provenance receipt under
`<planning-dir>/provenance/planning-sources/`. The receipt binds the profile and
profile version, complete source snapshot, local spec, draft, mapping, and
resulting task references. All outputs publish in one transaction. Re-importing
the same profile/version/source digest is forbidden; changed source bytes form a
new snapshot and may create a new set of tasks and a new receipt, but never update
tasks from an earlier import.

This is an interoperability handoff, not synchronization. Taskrail does not call
a model, execute a source-system hook, infer semantic equivalence, accept external
`spec_ref` paths, or claim compatibility with every OpenSpec or Spec Kit fork.

## Goals

- Define one generic, deterministic contract for importing planning sources without embedding source-tool semantics in task frontmatter.
- Recognize bounded OpenSpec and Spec Kit layouts through explicit built-in, versioned profiles.
- Require every source snapshot to consist of clean tracked repository-relative regular files with no symlink, junction, or reparse traversal.
- Produce a stable sorted descriptor and aggregate SHA-256 over the exact source bytes and their roles and paths.
- Keep semantic judgement outside the binary through a human- or agent-reviewed mapping to real local Taskrail spec anchors.
- Reuse transactional `ImportDraft` v3, including generated and portable opaque task identities, without defining `ImportDraft` v4.
- Preview the complete task, state, and receipt outcome before any write.
- Publish new tasks, projected state, and one self-identifying immutable provenance receipt atomically.
- Make duplicate source-snapshot imports mechanically impossible while treating changed snapshots as new append-only imports.
- Preserve layout 3 and state schema 2 compatibility because existing task and state meaning does not change.

## Potential Features

### Planning Source Trust Boundary

Both commands operate on the Taskrail repository discovered by the existing root
rules. `--root` names a planning-source root inside that same repository; it is not
an arbitrary filesystem or remote repository location.

Requirements:

- `--root`, `--draft`, and `--mapping` are canonical slash-separated repository-relative paths. They are valid UTF-8, at most 1024 bytes, contain no empty, `.` or `..` component, and are not absolute, drive-relative, UNC, URL, or file-URI spellings. The existing portable component and Unicode alias rules apply.
- `--root` resolves to a directory beneath the repository root. Every component from repository root through every consumed file is opened without following symlinks, junctions, mount substitutions, or Windows reparse points. Unsupported no-follow identity checks fail closed.
- A Git non-bare worktree is required. The configured Taskrail root and worktree root are equal. Bare repositories, submodule roots, external worktrees used only as path containers, and non-Git repositories are unsupported for source import.
- Every entry beneath `--root`, in both the stage-0 index and worktree, is accounted for by the selected profile. Sparse, skip-worktree, assume-unchanged, conflicted, missing, untracked, ignored-but-present, symlink, gitlink, device, socket, FIFO, hard-link-identity ambiguity, nested repository, and unsupported entry types fail. Empty directories have no source meaning and are ignored.
- Every accepted source is a tracked stage-0 regular file whose `HEAD`, index, and worktree bytes and executable mode agree. Staged, unstaged, intent-to-add, racily changed, or filter-indeterminate content fails rather than choosing one representation. Digests use exact worktree bytes after equality is established; no line-ending or Unicode normalization occurs.
- The selected local spec, draft, and mapping are also tracked, clean, available stage-0 regular files reached without link/reparse traversal. They may be outside `--root`, but remain inside the same repository. Apply rechecks all of them under the mutation lock.
- Every consumed text file is valid UTF-8 without a byte-order mark or NUL. A source file is at most 2 MiB, a profile contains at most 256 source files and 16 MiB total source bytes, and the local spec, draft, and mapping are each at most 4 MiB. Limits are measured before decoding and apply equally to inspect and import.
- Profile layouts are case-sensitive and use canonical lower-case names. ASCII-case, NFC, or Unicode-case-fold aliases fail on every host rather than selecting a platform-dependent file.
- No network access, subprocess, source-system executable, repository hook, template, script, or generated command is run while identifying, hashing, mapping, previewing, or importing a source.

The complete consumed-file set and its Git/index identities are frozen for one
command. Inspect computes output only after a second read-set check. Import holds
the common repository mutation lock and rechecks the set immediately before first
publication; a change produces a conflict, not a descriptor for mixed snapshots.

### Deterministic Source Descriptor

Profile inspection produces this logical descriptor:

```json
{
  "profile": {"name": "openspec", "version": 1},
  "root": "openspec/changes/add-search",
  "aggregate_sha256": "<lower-case 64-hex>",
  "sources": [
    {
      "role": "proposal",
      "path": "openspec/changes/add-search/proposal.md",
      "size": 1200,
      "sha256": "<lower-case 64-hex>"
    }
  ]
}
```

Requirements:

- `profile.name` is the selected CLI name and `profile.version` is the exact built-in profile contract version. Both initial profiles are version `1`.
- `root` and each `path` are canonical repository-relative paths. `size` is the exact byte count and is emitted as a non-negative JSON integer that does not exceed the profile limits.
- `role` is an ASCII token assigned only by the selected profile. `sources` is sorted first by unsigned UTF-8 role bytes and then by unsigned UTF-8 path bytes. Duplicate role/path pairs or duplicate paths are invalid.
- A source SHA-256 is over the exact file bytes. The aggregate SHA-256 is over this unambiguous byte sequence, where `NUL` is one zero byte, decimal sizes have no sign or leading zero except `0`, and entries occur in descriptor order:

```text
taskrail-planning-source-v1 NUL
profile NUL <profile-name> NUL
version NUL <decimal-profile-version> NUL
root NUL <repository-relative-root> NUL
entry NUL <role> NUL <path> NUL <decimal-size> NUL <lower-case-sha256> NUL
... one entry record per source
```

- The spaces and line breaks shown above are explanatory and are not hashed. The magic literal is immediately followed by `NUL`; every subsequent labeled record is concatenated exactly. Path, role, and profile grammars prohibit `NUL`, making the sequence injective.
- Renaming a root or source, changing its role, adding or removing a source, changing exact bytes, or selecting another profile/version changes the aggregate. File timestamps, permissions other than regular-file classification, Git object IDs, invocation directory, and host path separators do not enter it.
- Text and JSON modes report the same ordered descriptor and digest. No successful result calls a snapshot clean unless every trust-boundary check completed.

#### Built-In Profile Registry

The profile registry is compiled into the binary. In v0.7, `--profile` accepts
exactly `openspec` and `spec-kit`; each selects version 1. There is no profile
search path, local override, executable plugin, hook, dynamic library, script, or
configuration-defined matcher.

A later profile contract must use a new profile version and preserve explicit
receipt interpretation. It must not silently widen version 1. The command may
eventually gain explicit version selection, but v0.7 resolves each accepted name
to its sole version and always displays that version in previews and receipts.

Profile names describe supported Taskrail interchange shapes, not blanket
compatibility certification for an upstream project, release, fork, extension,
or generated repository. A root that resembles a named system but does not match
the exact shape below fails as `unknown_layout`; Taskrail never guesses the
closest profile or silently drops an unrecognized file.

### OpenSpec Profile Version 1

The `openspec` v1 root is one OpenSpec-style change directory, not the repository's
top-level `openspec/` directory and not an archived changes collection.

Recognized files are exactly:

| Relative to `--root` | Role | Cardinality |
|---|---|---|
| `proposal.md` | `proposal` | exactly one |
| `tasks.md` | `tasks` | exactly one |
| `design.md` | `design` | zero or one |
| `specs/<capability>/spec.md` | `requirement` | one or more |

`<capability>` matches `^[a-z0-9][a-z0-9-]{0,62}$`. The `specs` directory has
exactly one capability-directory level. No other direct file, nested directory,
metadata file, archived change, alternate requirement filename, or generated
artifact is part of this profile. Presence of one is an unknown-layout refusal,
not an ignored extension.

The profile assigns roles and hashes content only. It does not parse proposal
sections, requirement scenarios, task checkboxes, capability names, completion
state, or upstream configuration. The mapping author decides what those bytes
mean and how they relate to a local Taskrail spec.

### Spec Kit Profile Version 1

The `spec-kit` v1 root is one Spec Kit-style feature directory containing the
planning outputs for one feature. It is not `.specify/`, a template directory, or
the repository-wide `specs/` parent.

Recognized files are exactly:

| Relative to `--root` | Role | Cardinality |
|---|---|---|
| `spec.md` | `specification` | exactly one |
| `plan.md` | `plan` | exactly one |
| `tasks.md` | `tasks` | exactly one |
| `research.md` | `research` | zero or one |
| `data-model.md` | `data-model` | zero or one |
| `quickstart.md` | `quickstart` | zero or one |
| `contracts/<name>` | `contract` | zero or more |
| `checklists/<name>.md` | `checklist` | zero or more |

`<name>` is one portable component, 1 through 128 ASCII bytes, matching
`^[A-Za-z0-9][A-Za-z0-9._+-]*$`; the existing reserved-device, trailing-dot, and
case/Unicode alias rules still apply. Contract names additionally end in `.md`,
`.json`, `.yaml`, `.yml`, `.graphql`, `.proto`, or `.txt`. The `contracts` and
`checklists` directories are each at most one level deep. Empty optional
directories are ignored; all other files and directories are unknown layout.

The profile does not execute `.specify` scripts, read templates or memory files,
interpret task completion markers, validate an API language, or infer which plan
statements deserve Taskrail tasks. Repositories with renamed files, extra
generator outputs, nested contract trees, or fork-specific structure need a
future built-in version or an explicit external conversion before import.

### Reviewed Semantic Mapping

Taskrail deliberately cannot derive tasks or local spec anchors from source prose.
An external human, agent, or human-and-agent workflow writes `mapping.json` after
reviewing the descriptor, source files, target spec, and final draft.

Mapping schema version 1 has exactly this shape:

```json
{
  "schema_version": 1,
  "review_session_id": "source-import-2026-08-05-01",
  "profile": {"name": "openspec", "version": 1},
  "source": {
    "root": "openspec/changes/add-search",
    "aggregate_sha256": "<lower-case 64-hex>"
  },
  "target_spec": {
    "version": "v0.7.0",
    "path": "specs/v0.7.0.md",
    "sha256": "<lower-case 64-hex>"
  },
  "draft_sha256": "<lower-case 64-hex>",
  "review": {
    "mode": "human-and-agent",
    "reviewer": "release planning review",
    "reviewed_at": "2026-08-05T10:00:00Z"
  },
  "items": [
    {
      "item_id": "search-query-contract",
      "sources": [
        {
          "role": "requirement",
          "path": "openspec/changes/add-search/specs/search/spec.md",
          "start_line": 1,
          "end_line": 24
        }
      ],
      "spec_refs": ["specs/v0.7.0.md#reviewed-semantic-mapping"],
      "task_keys": ["search-contract"],
      "disposition": "task",
      "rationale": "The local anchor owns the imported behavior."
    }
  ]
}
```

Requirements:

- JSON input is one UTF-8 object with no BOM, trailing value, duplicate key, unknown field, missing field, or `null`. Numbers use their schema integer form. The decoder rejects data it cannot represent exactly rather than applying JSON coercion.
- `review_session_id`, `item_id`, and draft-local task keys use the existing portable review/key grammar, are 1 through 128 bytes, and are unique in their namespace. `review_session_id` exactly equals the final `ImportDraft` v3 `review_session_id`.
- Profile, root, aggregate, target version/path/digest, and raw draft SHA-256 exactly match fresh command inputs. The mapping SHA-256 is over the exact mapping file bytes and is recorded separately in the receipt.
- `review.mode` is exactly `human`, `agent`, or `human-and-agent`. `reviewer` is trimmed UTF-8 of 1 through 256 bytes with no control character. `reviewed_at` is canonical RFC3339 UTC. These are review assertions, not authenticated identities or claims of model independence.
- `items` contains 1 through 4096 entries. Every rationale is trimmed UTF-8 of 1 through 2048 bytes and contains no control other than line feed. Arrays are non-null; duplicates within an array are rejected.
- Each source reference names an exact descriptor role/path pair and a valid inclusive one-based line range in the decoded source. Line counting treats LF and CRLF as one line boundary without changing hashed bytes; a final unterminated line counts. Every descriptor source appears in at least one mapping item.
- Each `spec_refs` member is a normalized reference to a live heading in the selected local spec. It uses the canonical local spec path plus `#` and its normalized anchor. External paths, source-system paths, URLs, bare source anchors, another Taskrail spec version, and path traversal are invalid.
- `disposition` is `task` or `no-task`. `task` requires one or more unique draft-local `task_keys`; `no-task` requires an empty `task_keys` array. Both require at least one source and one local `spec_ref`, so a deliberate no-task judgement remains anchored and reviewable.
- Every final draft key appears in at least one `task` item, and every named key exists in the draft. For each named key, that draft task's exact normalized `spec_ref` appears in the same item's `spec_refs`. Mapping item order carries no execution or allocation meaning.
- Mechanical checks prove internal consistency, source coverage at file granularity, real anchors, and complete draft-key linkage. They do not prove that every semantic requirement was noticed, that a rationale is correct, or that the resulting task set is sufficient.

Any mapping or draft edit changes its raw digest. The reviewer regenerates and
reviews the final mapping; Taskrail never repairs stale digest fields or rewrites
semantic entries.

#### ImportDraft V3 And Local Spec Anchoring

Planning-source import accepts exactly `ImportDraft` schema version 3 as defined by
v0.6: reviewed transactional v2 plus the presence-aware optional `TaskDraft.id`
for portable opaque IDs. Versions 1 and 2 remain supported by their existing
generic import surfaces but are rejected by `source import`; no schema version 4
is introduced.

Additional source-import constraints are mechanical:

- `target` is exactly `tasks`; `spec_sections` is absent. A source import cannot create or edit a Taskrail spec.
- The v3 `review_session_id` matches the mapping. Every task has a unique non-empty `key`, a non-empty reviewed v2 body, and exactly one normalized `spec_ref` into the `--spec` file.
- `--spec <version>` resolves through the existing versioned local-spec registry. The resolved path and version must match each other, the mapping, and every task. The selected spec need not be active; source import never activates it.
- No draft or resulting task may persist an OpenSpec path, Spec Kit path, URL, filesystem-absolute path, or source anchor in `spec_ref`. Source evidence belongs only in the receipt through the mapping digest and descriptor.
- Draft-local dependencies retain v3 meaning. External dependencies resolve through the complete live-plus-archive task ledger. Every new task is created live; imported tasks never overwrite, merge with, reopen, rename, re-slug, restore, or otherwise mutate an existing task.
- An absent `TaskDraft.id` allocates a fresh generated identity using the complete ledger. A present valid opaque ID is preserved. A changed source snapshot with a colliding requested opaque ID fails before writing; Taskrail never interprets the collision as permission to update the prior task.
- Existing generic v3 body, identity, dependency, cancellation, archive, YAML quoting, filename portability, and all-or-none preflight rules continue to apply.

The mapping is the semantic bridge. Taskrail validates that bridge's references
and digests, but the binary does not read prose to infer titles, acceptance
criteria, dependencies, task boundaries, priority, identities, or anchor choices.

### Source Inspect And Import Commands

Add commands:

```text
taskrail source profile list [--json]
taskrail source profile show <openspec|spec-kit> [--json]
taskrail source inspect --profile <openspec|spec-kit> --root <repo-path> [--json]
taskrail source import --profile <openspec|spec-kit> --root <repo-path> --spec <version> --draft <importdraft-v3> --mapping <mapping.json> [--apply] [--json]
taskrail source receipt list [--profile <openspec|spec-kit>] [--json]
taskrail source receipt show <receipt-id> [--json]
```

Profile list/show and receipt list/show are strictly read-only. Profile inventory
reports the exact built-in profile names, versions, required/optional roles, path
shape, and file/byte limits rather than requiring users to infer them from help.
Receipt inventory reads the canonical validated sidecar set in receipt-ID order;
list reports receipt ID, profile, source root/digest, target spec, and resulting
task refs, while show reports repository-relative path plus the exact canonical
receipt object. Filters never change validation scope or hide a malformed receipt.

`source inspect` is strictly read-only. It recognizes and validates the selected
profile, computes the descriptor, and writes no task, state, receipt, lock,
temporary repository file, or normalized source. It succeeds only for a complete
clean snapshot. It scans validated receipts and reports the existing matching
receipt summary or `null` for the exact profile/version/source-digest tuple, so a
reviewer can detect a prior import before authoring mapping and draft files.

`source import` previews by default. Preview performs every parse, digest,
duplicate-receipt, anchor, mapping, identity, dependency, allocation, candidate
task, state projection, receipt, and post-validation check that does not require
publication. It reports `applied:false`, predicted task references and paths, and
the exact candidate receipt ID/path. It does not reserve IDs or authorize a later
apply; apply repeats all checks against current bytes and may produce a different
valid allocation after intervening ledger changes.

`--apply` is the sole write opt-in. It is incompatible with any future dry-run
alias, accepts no confirmation bypass, and writes no source, local spec, draft, or
mapping file. `--json` changes representation only.

Machine output reuses the uniform v0.5 envelope and shared stable-error policy.
Empty arrays are `[]`, not `null`; JSON stdout is one document and diagnostics
never contaminate it.

Profile-list result fields are exactly non-null `profiles`; profile-show fields are
exactly `profile`, non-null `required_roles`, non-null `optional_roles`, `layout`,
and `limits`. Receipt-list result fields are exactly non-null `filters` and
non-null `receipts`; receipt-show fields are exactly `path` and `receipt` using
the canonical on-disk object below. Inspect `result` fields are exactly `profile`,
`root`, `aggregate_sha256`, `sources`, and nullable `matching_receipt`, using the
descriptor and receipt-summary shapes above. Import `result` fields are exactly:

- Each profile inventory entry is exactly `profile`, non-null ordered `required_roles`, non-null ordered `optional_roles`, `layout`, and `limits`. A role is exactly `role`, `path_pattern`, and `kind` (`file|directory`). Layout is exactly `root_pattern`, `recursive:false`, and `unknown_entries:"reject"`. Limits are exactly decimal JSON integers `max_files`, `max_file_bytes`, and `max_total_bytes`.
- Receipt-list `filters` is exactly nullable `profile`. Each receipt summary is exactly `receipt_id`, `profile`, `root`, `aggregate_sha256`, `target_spec` (`version`, `path`, `sha256`), and non-null ordered `resulting_task_refs`. `matching_receipt` uses that exact summary shape. Profile order is the built-in registry order; receipts and task refs use unsigned UTF-8 order.
- Profile-list `profiles`, receipt-list `receipts`, all role arrays, and resulting task refs are empty arrays rather than null. Profile-show unknown names and receipt-show unknown IDs use the common structured error without partial result data.

```json
{
  "profile": {"name": "openspec", "version": 1},
  "root": "openspec/changes/add-search",
  "aggregate_sha256": "<lower-case 64-hex>",
  "spec": {"version": "v0.7.0", "path": "specs/v0.7.0.md", "sha256": "<lower-case 64-hex>"},
  "draft": {"path": "planning/import/add-search/draft.json", "sha256": "<lower-case 64-hex>"},
  "mapping": {"path": "planning/import/add-search/mapping.json", "sha256": "<lower-case 64-hex>"},
  "applied": false,
  "receipt_id": "psr-<lower-case 64-hex>",
  "receipt_path": "planning/provenance/planning-sources/psr-<lower-case 64-hex>.json",
  "tasks": [
    {
      "key": "search-contract",
      "task_ref": "T-201",
      "task_id": "T-201-search-contract",
      "path": "planning/tasks/T-201-search-contract.md",
      "spec_ref": "specs/v0.7.0.md#reviewed-semantic-mapping"
    }
  ]
}
```

Result tasks are sorted by unsigned UTF-8 draft key. Warning objects are exactly
`code`, `message`, and nullable `path`. Error objects use exact `code`, `message`,
and `details`; details has exactly non-null sorted `paths` and non-null ordered `violations`. Each
violation is exactly `code`, `message`, and nullable `path`. Stable top-level
codes are `invalid_arguments`, `repository_invalid`, `unknown_profile`,
`unknown_layout`, `source_not_clean`, `input_too_large`, `invalid_utf8`,
`invalid_draft`, `invalid_mapping`, `digest_mismatch`, `invalid_spec_ref`,
`duplicate_source_import`, `identity_conflict`, `write_conflict`,
`partial_write`, `rollback_failed`, and `recovery_pending`. Human and JSON modes
have identical exit classification.

All input JSON, mapping nested objects, receipt objects, and command output golden
schemas reject unknown or missing fields. Errors are deterministic: paths sort by
unsigned UTF-8 bytes and violations retain validation-phase order, then path/order
within a phase.

### Immutable Planning Source Receipts

A successful apply creates exactly one receipt at:

```text
<planning-dir>/provenance/planning-sources/<receipt-id>.json
```

The directory is created on first apply without `.gitkeep`. It contains direct
regular lower-case `psr-<64-hex>.json` children only; aliases, subdirectories,
symlinks, reparse points, special files, and unexpected names fail validation and
source import. Receipts are provenance sidecars, never task frontmatter, task body
sections, state fields, archive metadata, or verification artifacts.

Receipt schema version 1 has exactly these fields:

```json
{
  "schema_version": 1,
  "receipt_id": "psr-<lower-case 64-hex>",
  "profile": {"name": "openspec", "version": 1},
  "source": {
    "root": "openspec/changes/add-search",
    "aggregate_sha256": "<lower-case 64-hex>",
    "entries": [
      {"role": "proposal", "path": "openspec/changes/add-search/proposal.md", "size": 1200, "sha256": "<lower-case 64-hex>"}
    ]
  },
  "target_spec": {"version": "v0.7.0", "path": "specs/v0.7.0.md", "sha256": "<lower-case 64-hex>"},
  "draft": {"schema_version": 3, "path": "planning/import/add-search/draft.json", "sha256": "<lower-case 64-hex>"},
  "mapping": {"schema_version": 1, "path": "planning/import/add-search/mapping.json", "sha256": "<lower-case 64-hex>", "review_session_id": "source-import-2026-08-05-01"},
  "resulting_tasks": [
    {"key": "search-contract", "task_ref": "T-201", "task_id": "T-201-search-contract", "spec_ref": "specs/v0.7.0.md#reviewed-semantic-mapping"}
  ]
}
```

Requirements:

- `entries` equals the descriptor's ordered source list, with `sources` renamed to `entries`. `resulting_tasks` is sorted by unsigned UTF-8 draft key and contains every and only newly imported task.
- Receipt task references and IDs describe the apply outcome without storing a physical task path. `task_ref` is the durable identity. Later supported re-slugging, archival, lifecycle transitions, or local spec evolution do not rewrite historical receipt fields or create durable path-scan blockers.
- The receipt payload is the complete object above without `receipt_id`. Serialize it as compact UTF-8 JSON in the listed field order, with standard JSON escaping, no insignificant whitespace, no HTML escaping, and array order as specified. The receipt ID is `psr-` plus lower-case SHA-256 of `taskrail-planning-source-receipt-v1`, one `NUL`, and those compact payload bytes.
- The on-disk receipt is the complete object, including `receipt_id`, serialized in the same field order as two-space-indented UTF-8 JSON with one final LF. Validation requires byte-canonical form, exact schema, a filename equal to `receipt_id + ".json"`, and a recomputed matching ID. Thus unknown fields, reformatting, truncation, or semantic mutation fail visibly.
- Taskrail writers never edit, replace, rename, or delete a receipt. There is no receipt repair, adoption, refresh, redaction, or migration command. A correction is a changed reviewed source snapshot and new import, or Git reversion of an entire erroneous apply before dependent work proceeds.
- Receipt validation is self-contained. It does not require source, draft, mapping, spec, or original task paths still to exist or retain their old bytes, and it never treats later task state as receipt drift. The sidecar records an import event; it is not a live synchronization database.
- Profile and receipt inventory are the only dedicated discovery surfaces. They never repair, rewrite, normalize, refresh, delete, or infer current task state from a receipt.
- Before preview or apply, scan all valid receipts. The tuple `(profile.name, profile.version, source.aggregate_sha256)` is repository-unique regardless of target spec, mapping, draft, or resulting identity. The aggregate already binds the canonical source root, so moving otherwise identical bytes to another root creates a distinct snapshot. A matching tuple fails `duplicate_source_import` and reports the existing receipt and task refs.
- A different aggregate digest is a distinct snapshot even when a reviewer believes the prose is semantically equivalent. It may import only fresh tasks and creates a separate receipt. Taskrail never diffs snapshots to update, cancel, supersede, deduplicate, or link old tasks automatically.
- A malformed or noncanonical existing receipt makes v0.7 receipt validation and new source import fail closed. It never grants permission to bypass duplicate detection. Git remains the recovery mechanism for deleted or edited receipt bytes.

#### Atomic Publication And Compatibility

Apply uses the common v0.6 repository mutation and durable recovery protocol.

Requirements:

- Acquire the repository writer lock before final ledger allocation and hold it through durable commit or complete rollback. Refuse an active or retained recovery transaction.
- Recheck profile layout, Git cleanliness, every exact input digest, receipt set, target anchors, complete ledger, dependencies, identities, destination absence, and state snapshot under the lock. Build all candidate task bytes, projected state bytes, canonical receipt bytes, and needed directories before publication.
- The write set is exactly the new live task files, `planning/STATE.md`, the new receipt, and provenance directories newly needed by this transaction. It excludes existing and archived task bytes, including their task-local loop policy, plus the local spec, source files, draft, mapping, verification artifacts, prompts, skills, config, and layout marker.
- Validate the complete candidate repository before first publication and after publication. Durable backups and compare-and-swap rollback cover every task, state, receipt, and created directory boundary. Ordinary failure leaves none of the candidate outputs; rollback ambiguity retains recovery evidence and reports every original/candidate/current digest without overwriting external edits.
- The receipt is not a commit marker that permits partial tasks. Tasks, projected state, and receipt are one semantic outcome; none is successful without all three and post-validation. Retry after complete rollback reruns duplicate detection and allocation.
- Preview and failed preflight create no provenance directory. Apply never replaces an existing path, and destination collision is a refusal even when bytes appear equal.

No layout or state migration is introduced:

- Layout remains version 3 and `STATE.md` remains schema version 2. `ImportDraft` remains at version 3.
- Receipts are additive immutable files outside both live and archived task roots. Existing task/state interpretation and every existing lifecycle writer's required write set remain unchanged.
- A v0.6 binary may ignore the provenance directory and continue valid lifecycle work because no task, state, dependency, identity, archive, or selection rule depends on receipt updates. It cannot perform `source import` and therefore cannot create a duplicate through this surface.
- v0.7 lifecycle, archive, repair, verification, spec, loop, and generic import writers preserve receipt bytes and paths exactly. `repair --apply` reprojects state only and never reconstructs or reconciles a receipt.
- Downgrade to a v0.6 binary does not erase receipts, but that binary cannot validate their schema or duplicate-source invariant. Operators use v0.7 for provenance inspection and new source imports. No claim is made that arbitrary pre-v0.7 tools understand the sidecars.

## Caution

Do not market a narrow profile as universal OpenSpec or Spec Kit compatibility.
Upstream projects and forks evolve independently. Exact recognition and an
actionable unknown-layout failure are safer than silently omitting an unfamiliar
file that may contain the requirement a reviewer most needed to see.

A digest proves byte identity, not semantic quality. File-level mapping coverage
does not prove every requirement was understood, and a review assertion does not
authenticate a reviewer. Human review remains responsible for source meaning,
local anchor choice, task boundaries, dependencies, acceptance criteria, and
whether a changed snapshot really deserves another task set.

Receipts are append-only historical evidence, not a live foreign key database.
Do not place them in task frontmatter or require later task writers to update
them. Doing so would force a layout/version boundary and make ordinary lifecycle
work capable of corrupting provenance.

Changed bytes intentionally permit a fresh import, which can create duplicate
semantic work. Taskrail reports identity/dependency collisions but never infers
semantic duplication. Review the preview and existing ledger before applying.

## Recommendation About LLM Support

Do not add direct model or provider calls to Taskrail core.

The binary should identify files, hash bytes, validate strict schemas and anchors,
detect duplicate snapshots, allocate identities, and publish transactions. A
human or external agent may read the source and author the mapping and
`ImportDraft` v3. Repositories may use existing prompts or Agent Skills to make
that handoff repeatable, but Taskrail treats their final files as untrusted,
reviewed inputs and does not inspect conversations, providers, or reasoning.

This split is especially important for interoperability: deterministic profiles
can be tested against exact layouts, while semantic translation remains explicit
and replaceable. A future built-in profile may add another declarative shape; it
must not smuggle a model call, executable converter, or hook into inspection.

## Explicitly Excluded

Continue to exclude:

- direct model/provider calls, model selection, prompt execution, conversation persistence, or semantic output parsing in the Taskrail binary;
- executable profile plugins, dynamic libraries, repository hooks, source-system scripts, templates, generated commands, or configuration-defined matchers;
- automatic semantic inference of tasks, priorities, dependencies, acceptance criteria, identities, source equivalence, or local spec anchors;
- external, OpenSpec, Spec Kit, URL, absolute, or cross-repository paths in task `spec_ref`;
- support claims for every OpenSpec/Spec Kit release, fork, extension, archive, template, or repository layout;
- fuzzy or best-effort profile selection, silently ignored unknown files, recursive unbounded source discovery, remote repositories, URLs, and non-Git source roots;
- lifecycle execution, task start/complete/block/cancel/verify behavior, autonomous-loop execution, or policy changes as part of source import;
- bidirectional synchronization, polling, watchers, source write-back, checkbox/status reconciliation, task updates, conflict merging, deletion propagation, or foreign-ID lifecycle ownership;
- updating, superseding, cancelling, merging, or deduplicating tasks created by an earlier receipt;
- embedding source descriptors, mapping records, or mutable provenance fields in task frontmatter, task bodies, or `STATE.md`;
- receipt editing, refresh, repair, redaction, deletion, compaction, migration, or reconstruction from current task state;
- a new layout 4, state schema 3, `ImportDraft` v4, or a compatibility fence whose only purpose is additive immutable receipts;
- importing spec sections or activating/editing the target Taskrail spec through `source import`;
- committing, pushing, opening pull requests, fetching upstream sources, or claiming remote delivery; and
- treating a matching digest, syntactically valid mapping, review mode, or successful transaction as proof of semantic completeness.
