## Revision Decision

Local mode now minimizes incidental Git-visible planning provenance without
claiming confidentiality. Outcome-required product bytes may embody Taskrail
requirements; local Taskrail identities in commit metadata require caller-owned
instruction outside managed planning. Generic repository-visible policy governs
ordinary Git conventions but cannot be laundered from ignored planning content.
Auxiliary refs remain forbidden, and loop postflight snapshots both `refs/*` and
dynamic uppercase root-ref candidates.

Storage-neutral skills obtain one exact repository-root physical
`status.storage.artifacts_dir` in committed and local modes. In Git, proposal/raw
paths must be ignored, untracked, and unstaged; non-Git paths retain containment
without an ignore claim. Physical transient paths never become structured durable
review paths. Repository ignores now cover the committed proposal and skill-eval
artifact roots.

Skill-evaluation release evidence has one strict paired candidate/baseline model
over every globally unique registered case, with committed and local coverage per
skill, exact digest framing, fixed v0.4.0 baseline commit, per-arm executable and
raw evidence identity, total outcome precedence, and a human-owned waiver
authority boundary. T-218 ships and sandboxes the evaluator; T-174 publishes the
final report after the evaluator exists, preserving one commit per tracked task.

Inherited v0.6 retains v0.5 status storage context under `storage` and uses
`task_storage` for live/archive counts. Task-targeting prompts gain explicit
contract v2, schema-aware historical task-path scanning has ordered ownership, and
IDEAS adoption is included in v0.6 release ancestry.

## Method

The review reconsidered the complete v0.5 feature spec, machine companion,
inherited v0.6 schema, all v0.5 task files, changed inherited task owners, local
storage and Git delivery, strict evaluation evidence, and release ancestry through
four questions:

1. Consistency: can exact schemas, task ownership, and inherited surfaces all be
   implemented without contradictory field, path, or lifecycle meanings?
2. Gaps: can every claimed result, provenance boundary, evaluation outcome, and
   release gate be observed through a named owner and complete dependency chain?
3. Additions: what is the smallest contract that closes real gaps without adding
   a policy engine, provider integration, confidentiality claim, or provenance
   database?
4. Adversarial: can ignored planning, transient paths, report selection, Git refs,
   waiver text, or cross-version drift satisfy a mechanical gate falsely?

Independent fresh contexts repeatedly reviewed the candidate as findings were
resolved. The final review round approved the complete contract except for two
narrow consistency corrections: T-218/final-report commit ownership and arbitrary
uppercase root refs. The maintainer applied only those exact corrections, verified
their task/spec alignment directly, and reran manifest, validation, task-body,
ignore, and diff checks. No unresolved high or medium finding remains.
